# 游戏原型求职成果转化指南

生成时间：2026-08-06　适用范围：ProjectVL 及后续同类原型项目（如「假装正在工作」）

## 0. 这份指南是什么

你收到的 ChatGPT 版本框架（六层展示体系）大方向是对的，但存在过度设计的问题：七份文档、十二字段案例表、六类附件清单，对一个还要自己动手整理的独立开发者来说执行成本过高，而且部分论断和 ProjectVL 的实际仓库状态对不上。

本指南做了三件事：

1. **精简**：把六层压成可执行的模板，去掉不产生招聘判断价值的字段。
2. **纠偏**：结合 2026-08-04 已完成的三份 ProjectVL 专项报告（`docs/作品集证据核对报告_2026-08-04.md`、`docs/Git事实核查报告_作品集用_2026-08-04.md`、`docs/Git版本迭代报告_作品集整理用_2026-08-04.md`），补一条原框架完全没有的原则——**AI 生成的分析本身需要人工核验**，因为那份 ChatGPT 报告曾把项目最强的证据（46 份真人遥测）误判成"空文件"。
3. **落地**：第 7 节直接把 ProjectVL 现状套进本框架，给出诚实的完成度和下一步，不是空转的方法论。

**用法**：第 4 节的母档模板是唯一需要为每个项目单独复制填写的文件；第 5 节的各层模板从母档抽取内容生成，不重新调研；第 6 节是执行时勾选的清单；第 7 节是 ProjectVL 当前的实例参考。

## 1. 五条修订原则

| # | 原则 | 原稿的问题 | 修订依据 |
|---|---|---|---|
| 1 | 层级按**招聘决策阶段**划分，不是详略递增 | 原稿说清楚了这点但没有强制执行——后续模板仍按"越来越详细"的直觉在写 | 每写一段内容前先问："这段话在回答招聘方哪一阶段的哪个具体问题？"答不出来就删 |
| 2 | 项目目标必须拆四类（产品假设/验证目标/迭代目标/求职目标），且每条目标要能追溯到**谁在什么时候拍板** | 原稿要求拆四类，但没要求溯源，容易把"我现在觉得应该这样"包装成"当时决定的" | ProjectVL 的 `docs/可玩原型_重启开发总计划.md`、`下一阶段_决策清单与任务计划.md` 里每条决策都有日期和状态标注，这是可复用的写法 |
| 3 | 案例结构从原稿的 12 步压成 **7 步可执行结构**，STAR 只用于简历行 | 十二个字段里"设计假设""备选方案""最终决策"经常是同一次讨论的产物，强行拆开只会让人为了填表而编造中间步骤 | 见第 5.3 节案例模板 |
| 4 | 结果必须按**五级强度**标注（已实现/已测试/初步验证/设计推论/产品目标），不允许用"提升了""优化了"这类模糊动词 | 原稿提了这个分级但只用在"最终结果"一节，没有要求贯穿全文 | ProjectVL 证据核对报告已经证明：一句"27300 局仿真全绿"和一句"验证了策略性"之间，前者面试官查不出问题，后者一查就穿帮 |
| 5 | **AI 生成的分析、报告、总结在进母档前必须人工用可复现命令核验** | 原稿完全没提这条 | ChatGPT 报告把 46 份、共 3MB 的真人遥测数据判定为"空内容"，还把测试数量、卡牌数量全部说错。这是这次实际发生的事故，不是假设风险 |

## 3. 项目分级

### 3.1 三级定义

- **A 类·旗舰**：与战斗策划高度相关、个人所有权清楚、有可玩版本、有明显迭代证据。数量控制在 1–2 个，六层全做。
- **B 类·支持**：补充旗舰项目没覆盖的能力（如资源系统、QTE、生产管线）。做到 L1–L3，L4/L5 按证据是否现成决定要不要做。
- **C 类·实验**：其余小型 Demo。只做一句话目标 + 一张 GIF + 一个设计结论 + Demo 入口，不单独立案例。

### 3.2 100 分评分表

| 维度 | 权重 | 判断问题 |
|---|---:|---|
| 岗位相关度 | 30 | 是否直接证明战斗策划能力？ |
| 个人所有权 | 20 | 能否明确说明你主导了什么？ |
| 证据完整度 | 20 | 是否有 Demo、视频、测试、配置、遥测这类可复现证据？ |
| 设计深度 | 15 | 是否存在值得展开的取舍问题？ |
| 完成度与可读性 | 10 | 能否稳定运行、容易理解？ |
| 差异化 | 5 | 能否让你区别于一般候选人？ |

80+ 旗舰 / 65–79 支持 / 50–64 只做速览 / <50 不进主作品集。

### 3.3 ProjectVL 初评（基于已核实事实，非最终结论）

| 维度 | 估分 | 依据 |
|---|---:|---|
| 岗位相关度 | 28/30 | 战斗循环、局内构筑、掉落经济、波次压力全部命中战斗策划核心能力 |
| 个人所有权 | 17/20 | 119/121 主线提交为个人；但存在真实第三方协作者做 Unity 移植（PR#4，`wlh219627-art`，120 commit），需要在母档里明确切割，见 4.4 |
| 证据完整度 | 14/20 | 94 测试文件/756 用例全绿、配置校验通过、46 份真人遥测是硬证据；但可试玩打包与视频完全空缺（见 7.3），扣分主要在这里 |
| 设计深度 | 14/15 | 27300 局仿真全绿→真人 90 秒判无聊→三段密度曲线重构，是完整闭环案例 |
| 完成度与可读性 | 6/10 | 引擎能跑但 README 数字过期（写 11 卡/108 测试，实际 60 卡/94 文件），需先修 |
| 差异化 | 5/5 | 遥测驱动的迭代证据链在同类作品集里少见 |
| **合计** | **84/100** | **旗舰项目**，但 L5（可试玩+视听）是当前唯一的结构性短板 |

### 4.4 个人贡献边界

必须明确区分六类：独立完成 / 主导完成 / 与 AI 协作完成 / 与其他成员共同完成 / 使用现成资产 / 使用开源代码 / 仅提出方案未实现。

**存在真实第三方协作者时的处理规则**（ProjectVL 特有情况，具有普遍参考价值）：不要隐藏，也不要把对方的工作算成自己的。正确措辞是"我设计的规则契约被协作者独立复刻验证"，而不是"我做了 Unity 移植"——前者对战斗策划岗位反而更有说服力，证明设计文档清晰到别人能照做。写作品集前先跟对方确认这部分是否可以公开引用。

```
协作者/第三方贡献记录：
　姓名/ID：
　贡献内容：
　与我的工作边界：
　是否已确认可在作品集中提及：
```

### 4.7 证据索引

| 陈述 | 证据类型 | 位置 | 可复现验证命令/操作 |
|---|---|---|---|
| | Demo/视频/截图/commit/配置/测试/遥测/表格 | | |

**强制要求**：每一行"可复现验证命令"必须真实可执行（如 `git log --oneline`、`npx vitest run`），不能写"参见文档"这种无法独立复核的说法。这条直接对应原则 5。

### 4.8 标记规则

写母档时，每条陈述句末尾用方括号标注：

- `[事实]` 已实现、记录或可直接观察到
- `[测试结果]` 通过明确测试/仿真/复现流程获得
- `[设计判断]` 根据分析得出但未经实测验证的结论
- `[产品假设]` 尚未验证，属于目标层
- `[后续计划]` 尚未完成

不带标记的陈述不允许进入案例正文。

## 5. 各层级模板

### 5.1 简历条目（L1）

三行结构，套用即可：

```
第一行·项目定位：独立设计并实现一款[时长]单局的[品类]原型，负责[职责范围]。
第二行·关键问题与方案：针对[具体问题]，引入[方案]，通过[机制]形成[效果]。
第三行·迭代与证据：建立[流程/工具]，基于[N轮测试/仿真/遥测]调整[具体参数]，
              保留[可试玩版本/配置表/测试记录]。
```

**成果表述的五级强度对照**（禁止越级）：

| 强度 | 可以写 | 不能写（无证据支撑） |
|---|---|---|
| 已实现 | 完成可运行的核心战斗循环、60 张卡/25 条配方、94 个测试文件全绿 | — |
| 已测试 | 完成 N 轮内部试玩、94 个自动化测试用例、46 份真人遥测会话 | — |
| 初步验证 | 密度从平铺改为分段曲线后 E1 同屏数命中设计目标（部分波次仍有偏差） | "验证了策略性"（没有对照数据） |
| 设计推论 | 根据当前测试，有限卡槽可能是比主动技能更低门槛的决策来源 | 把推论写成已验证结论 |
| 产品目标 | 目标首局通关率 30–40%（未测） | 把目标值写成实测结果 |

### 5.2 作品集速览卡（L2）

结构：项目定位（1句）→ 我的职责（1句）→ 关键设计（2–3条）→ 代表性迭代（1条，带前后对比）→ 完成度与限制（1句）。

不出现：大段规则说明、全量技能表、完整开发过程、AI 对话截图、无证据支撑的宏大结论。

### 5.3 案例正文七步模板（L3 核心）

```
标题：（问题式，不要用"XX系统设计"这类功能式标题）

1. 原始问题：观察到的具体现象（不要直接跳到方案）

2. 设计分析：为什么会发生，涉及哪些变量

3. 备选方案与取舍：列出真实考虑过的选项，说明放弃了什么、为什么
   （如果当时没有认真比较过备选方案，如实写"未系统比较"，不要事后编造）

4. 实现方式：流程图/配置字段/数值规则/状态机（贴关键片段，不贴全部代码）

5. 验证与结果：测试方法 + 版本对比 + 数据变化
   —— 每条结果标注第4.8节的五级强度标签

6. 遗留问题：当前仍未解决的部分（这一条比"完全成功"更能取信面试官）

7. 反思：这个方案的边界在哪、下一版会怎么处理、哪个原假设被推翻了
```

参照 ProjectVL 故事 A（见 7.2）：这个案例天然带全七步，且第 6 步"遗留问题"有真实数据支撑（E2 空窗超标、E7 冲刺失效、掉落经济中后期崩溃），是本框架的示范案例。

### 5.4 深度附件（L4）

按四类整理，每类只放"能支撑案例正文某个具体论断"的文件：

- **战斗设计类**：核心设计说明、技能/敌人表、波次配置、失败条件设计
- **数值类**：公式、成长曲线、掉率、数值模拟、参数敏感性
- **测试类**：测试计划、试玩记录、问题清单、参数调整记录、验收标准
- **工具/配置类**：配置界面截图、JSON/CSV 样例、校验工具、调参面板

不建议提交：未整理的聊天记录、巨量 AI 生成文档、无 README 说明的完整代码库、几十个重复版本、无注释配置文件。每个附件文件夹放一份一页 README，写清楚"这份文件证明案例正文里的哪句话"。

### 5.5 可试玩与视听证据包（L5）

最低组合（旗舰项目）：

1. 可直接运行的 Demo（免安装 Windows 版或稳定 Web 版）
2. 60–90 秒速览视频
3. 3–5 分钟讲解视频
4. 核心截图/GIF 一组
5. README（定位/操作方法/推荐体验顺序/当前完成度/已知问题）
6. 已知问题说明（单独一份，主动暴露而不是等面试官发现）

**60–90 秒速览视频节奏**：5s 项目定位 → 15s 核心循环 → 20s 关键构筑/操作 → 20s 敌人与压力变化 → 15s 代表性设计特色 → 10s 职责与材料入口。

**3–5 分钟讲解视频结构**：设计目标 → 核心循环 → 一个重要设计问题 → 解决方案 → 迭代前后对比 → 当前限制。

### 5.6 AI 工作流说明（L6，跨项目一份）

结构：问题 → 工作流（设计目标定义→任务拆解→AI生成初稿→人工审核→自动验证→集成→测试反馈→修订）→ AI 承担的任务 → **你承担的核心责任**（这一条必须写满，是防止"AI 主导"印象的关键）→ 质量控制手段 → 实际收益（无准确数据不编造百分比，改用"被替代的具体步骤"描述）→ 一两个 AI 输出错误案例及你如何发现纠正。

**好/坏表述对照**：

| 不要写 | 改写为 |
|---|---|
| "用 AI 生成了全部技能配置" | "定义了技能数据契约（触发器×效果原子），用 AI 批量生成 60 张卡的 JSON 配置，自己写校验脚本核对边界条件" |
| "AI 帮我提效 80%" | "把原本需要手工同步 Excel 与代码的流程改成双向脚本，人工只需最后确认差异行" |
| "AI 分析报告显示 XX" | 见原则 5：先自己跑一遍可复现命令核实，再引用 |

## 8. 红线清单

- 不把目标写成结果，不把推论写成结论（对照 5.1 五级强度表）
- 不隐藏也不侵占第三方协作者的贡献（4.4）
- 不引用未经人工核验的 AI 生成分析（原则 5）
- 不让作品集正文变成 GDD 堆积——完整规则表放 L4，正文只讲案例
- 每个案例必须有遗留问题或反思，"完全成功"式的案例不可信
- 数字口径全文档一致：简历、速览卡、正文、附件互相对不上是最容易被面试官抓到的破绽
- 不为凑数展开每个小 Demo 的完整案例——C 类项目只用一句话+一张 GIF
