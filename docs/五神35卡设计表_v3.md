### 0.1 唯一的新增引擎能力

`chainFrom` 每跳后对目标施加指定状态（不发完整 `onHit`，避免链式套娃）。建议实现为 `chain` 原子新增参数：

```
chain.spreadStatus?: 'vulnerable' | 'slow' | 'dot'   // 每跳施加的状态
chain.spreadParams?: { ratio?, duration? }           // 施加参数
```

融合契约：跨卡按 statusSystem 既有仲裁（取最强/取最长），写入 `interpreter.ts` 顶部契约注释并补 `fusionOrderInvariance.test.ts` 用例。

### 0.2 经济原子的两级归属（本轮细化）

避免"其他四神的转化接口无米下锅"：

| 级别 | 原子 | 归属 |
|---|---|---|
| **规则类**（改变经济规则）| `dropRateMul` `dropLifetimeMul` `xpMul` `expiryConvert` `mergePulse` `mergeMaterialRefund` `wildcardRewardBonus` | **丰饶独占**（磐垒例外持有 `mergeMaterialRefund`）|
| **数量类**（只多给一个）| `extraDrop` | 通用结果，但**其他神必须挂本神资源条件** |

这保证丰饶的经济稳定性不可被超越（它掌握乘数与规则），其他神只能拿"额外掉一个"。

### 0.3 全表通用红线（每张卡都已合规）

1. `onKill` / `onBreach` 绑定的效果**一律按事件坐标出效果**，禁止直接作用单体敌人
2. 6★ 不得重复声明分支已用的 `shield`/`novaOnBreak`/`expiryConvert`/`breachReduction`/`execute`
3. `requiresSource` 只允许 `weapon` / `chain` / `dot`
4. 所有 `requiresStatus` 效果必须有资源为 0 时的 fallback
5. 文案一律承诺「后续命中/击杀时兑现」，不承诺同一击立即连锁

### 0.4 关键引擎事实速查（写卡时反复用到）

| 事实 | 影响 |
|---|---|
| `fireTrigger('onHit')` 只在 `combatSystem:164`，且在 `hitIds` 去重后 | **贯穿每穿一个新敌人各发一次 onHit；分裂弹片各自命中各发一次**——这是"并发型"的唯一实现路径 |
| `chainFrom` / `explode` / zone tick 只走 `dealDamage`，不发 onHit | 雷链、爆炸、地面区域**无法触发 onHit 绑定** |
| zone 内的 `dot` 直接掉血、不叠状态 | 火场敌人 `requiresStatus:'dot'` 读不到，`requiresSource:'dot'` 读得到 |
| `novaOnBreak` 在 `absorbBreach` 里遍历 `[...state.enemies]` | **不踩尸体红线**，磐垒破盾反击安全 |
| `shield` 容量取最大、再生取最小 | 两张卡都发 shield ＝ 互相吃掉，不是联动 |

## 2. 迅霆 · 感电（并发型）

> 循环：贯穿/分裂/雷链铺开感电 → 主炮命中感电目标时逐个兑现 → 并发数越高收益越高
> 失败形态：敌人太散，串不起来

### 2.1 连锁闪电 `chainLightning` · 弹道｜弹道+控制 · **铺设锚**

**身份**：雷链在敌人之间跳跃，沿途铺感电。

|---|---|---|---|---|
| A 链弧 | 稳定 | `chain` @ `onHit` | 命中后雷链跳跃 2 次，**每跳施加感电**（`spreadStatus:'vulnerable'`）| 广度、跟随命中 |
| B 电轨 | 覆盖 | `beamMorph` @ `passive` | 换形持续光束，光束每次结算给路径上全部目标施加感电 | 线状、稳定覆盖 |
| C 雷暴 | 节奏 | `chain(targets=3)` @ `interval 2.2s` | 每 2.2 秒自动对最近 3 个目标各起一条链，每跳施加感电 | 不依赖命中、稀疏波次可用 |

**4★ amplify**：跳数 +1、搜索半径 +20（A/C）；光束宽度 +6（B）

## 3. 凛冬 · 寒意 → 冰封（阈值型）

> 循环：命中叠寒意 → 延缓推进争取时间 → 叠满自动冰封 → 对冰封/受控目标兑现
> 失败形态：叠不够快，敌人在冰封前就到了

## 4. 焚狱 · 灼烧 / 火场（条件型）

> 循环：铺开灼烧提高覆盖率 → 引燃兑现 → 爆炸/火场给新目标续上灼烧

> **两个关键词严格分家**：
> - **灼烧**＝`onHit → dot` 直接挂敌人，`requiresStatus:'dot'` **读得到**，**可被引燃**

## 5. 磐垒 · 壁垒（存量型）

> 失败形态：壁垒重建赶不上破裂速度

### 5.0 磐垒的结构性难题与解法（必读）

`shield` 的融合契约是**容量取最大、再生取最小**（`registry.ts:570`）。所以：

> **两张磐垒卡都发 `shield` ＝ 互相吃掉，不是联动。**

这是磐垒和其余四神最大的不同——它的资源无法靠"多张卡一起产"来放大。因此磐垒的"产资源"必须拆成两种正交形式：

| 形式 | 手段 | 谁做 |
|---|---|---|
| **供应容量** | `shield` | **只有神盾一张**（其余卡不得发 shield）|
| **延长壁垒寿命 / 制造承压点** | `breachReduction`（相加封顶 0.9）、`thorns`（相加）、`summon`（每卡独立实例）、`aura`（按来源并行）| 其余六张 |

`breachReduction` / `thorns` / `summon` / `aura` 的融合语义都是**可叠加或并行**，所以六张卡堆在一起是真加法。这是磐垒唯一可行的联动结构。

同理 `novaOnBreak` 跨卡是**分轴取最大**，所以**只有荆棘之外的一张卡可持有它**——本表指定为神盾 5★1，其余卡的兑现一律走 `onBreach`（按 point）或 `thorns` 缩放。
