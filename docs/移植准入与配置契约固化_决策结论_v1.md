# 移植准入与配置契约固化 · 决策结论

日期：2026-07-26 ｜ 版本：v1 ｜ 状态：结论（供你拍板 §11）
输入：你的两项"当务之急" + ChatGPT 的分析 + 本人对 `src/` 全量代码的核验与实测

---

## 摘要

**你要决定的不是"架构审查 vs 配置编辑器"二选一，而是：哪些契约必须先稳定、稳定到什么程度，Unity 与配置工具才能安全并行。**

裁决：

> **第一优先级 = 一个范围严格受控的"移植准入 + 配置契约固化"门（Stage 0）。**
> 通过准入门后立即拆成两条并行线：
> 1. Unity 开发者做**纵向切片移植**（不是全量复制）；
> 2. 你 + AI 先建**配置管线 v1**，再建**可视化配置编辑器 v1**，然后用它替换占位内容。

两个极端都不要：
- 不要等全部技能/遗物/文案正式设计完才开始 Unity；
- 也不要在数据契约仍会漂移时全面铺开量产移植，或先造一个功能齐全的大型编辑器。

一句话原则：**先冻结接口、不冻结内容；先打通一条完整链路、不全面复制；先做配置管线、再做精美编辑器。**

## 0. 本结论的依据（已核验，非推测）

与只能读文档的分析不同，以下结论基于对当前源码的直接核验与在沙箱中的实测：

- **类型检查全绿**：`npx tsc --noEmit` 退出码 0，整个 TypeScript 代码库无类型错误。
- **内容层冒烟通过**：`tests/skillsBatch1.test.ts`（21 用例，覆盖全部卡牌 1–6★ × 装备态/消耗态行为矩阵）在实测中通过。完整 72 个测试文件的套件可运行，但因运行在挂载盘上 I/O 过慢，未能在本次沙箱时限内跑完全部——**这不是失败信号，是环境限制**；已通过的部分与干净的类型检查共同表明核心处于健康可用状态。
- **效果参数确为松散字典**：`EffectDef.params` 是 `Record<string, unknown>`；校验器仅对 `restore`/`statBuff` 等少数原子做了参数校验，多数原子的参数无强约束（`registry.ts` 中大量 `num(p,'radius',120)` 式隐式默认值）。
- **定义存在多处重复**：`skillValidator.ts` 里手写了一份 `ATOMS`/`RUNTIME_STATS`/`CARD_STATS` 集合，与 `core/effects/defs.ts` 的类型、`docs/skills-schema.json`、注册表默认值**是四套并行来源**，改一处极易漏改另一处。
- **遗物存在双份文案**：`relics.json` 同时带 `textKey` 与内联 `title`/`desc`，与 `texts.json` 的本地化路线冲突。
- **`AFFIX_SINKS` 已是一份好契约**：`config/affixSinks.ts` 把每个词条映射到 operation/settlement/equipment/consumer/scalingTargets，是"单一权威契约"的正确样板——**说明你团队已经具备做契约的能力与审美，只是尚未推广到全部数据域**。

## 1. 现状稳固度：分层可冻，契约未冻

| 领域 | 状态 | 判断 |
|---|---|---|
| 核心分层（core 纯规则 / 注入 RNG / GameEvent） | 稳固 | 已具备移植基础，可冻结 |
| 技能通用解释器（8 触发器 × 33 原子） | 机制完整可跑 | 设计思想保留；**参数契约需强化** |
| 配置六域 + variant 深合并 | 已成型 | 结构好，但尚不适合策划长期手工维护 |
| 配置校验器 | 有明显进展 | 存在多套重复定义，会漂移 |
| 文案分离（texts.json） | 部分完成 | 遗物等仍有双份来源，未彻底统一 |
| 调参面板 | H5 可用 | 元数据分散三处，且不能原样移植 Unity |
| 自动测试（72 文件） | 覆盖良好 | 证明"结构合法/能跑通"，**不证明"设计正确/强度合理"** |
| 跨引擎一致性基建 | 缺 | 全量移植前的关键缺口 |

**结论的精确表述**：总体分层方向已可冻结；**具体数据契约、状态边界、若干仍在改的玩法规则尚不能冻结**。所以现在**不能**诚实地宣布"关键架构与逻辑已稳固不变"。这不是架构失败，而是项目正处在从"数据驱动"升级到"数据契约闭环"的阶段——最大生命词条那个 bug（配置合法、统计链在、却无消费者，后来补了 `totalMaxHp` 对账）就是这个阶段的典型症状。

## 2. 决策裁决：一个准入门 → 两线并行

你的两项"当务之急"咬合在同一个前置上——**冻结数据契约（schema）**：

- Unity 真正需要的**不是编辑器**，而是三样：冻结的 JSON 契约 + 核心规则规格 + 黄金回放基准。拿到这三样，另一位开发就能独立开工、直接读你导出的 JSON，**完全不依赖你的编辑器**。
- 配置编辑器是**建在这份冻结 schema 之上**的工具，服务于你填占位内容。它的"目标结构"就是那份 schema。

所以正确顺序是：**先做准入门这一件更聚焦的事**（比"全面审查整个项目"小得多、可交付得多），它**同时解锁**了 Unity 并行开发与配置编辑器两条路。

## 3. 准入门（Stage 0）的范围与"就绪定义"

### 3.0 前置：把神池重构收束到静止点（ChatGPT 漏了的一条）
git 历史显示，仅 2026-07-24 一天就连续改动了卡牌详情 UI、战斗反馈、最大生命词条、单卡进化分支、技能神祇配置、词条与配方进化、波间奖励、神池构筑。**C0–C8 神池/构筑系统是当前主线，仍在快速变化。**

> **你不能在半场重构上冻契约。** Stage 0 的第一步是把神池/构筑这条线推进到一个**自洽的静止点**：无半迁移系统、测试全绿、无已知会改数据结构的待办。到达静止点，才启动下面的固化。

### 3.1 契约四件套（Stage 0 的产出）

1. **核心更新契约**（Unity 与 H5 必须逐条一致）：单帧系统执行顺序、暂停/波间是否推进时间、RNG 调用位置、伤害结算顺序、触发器重入/递归规则、状态冲突仲裁、装备变化后的派生属性对账、配置是否允许局内热更。
2. **配置契约**：卡牌 / 神池 / 遗物 / 进化与配方 / 波次与敌人 / 调参参数 / 文案键格式 / ID 与引用规则 / schema 版本与迁移规则。
3. **效果原子契约**（当前最重要的一项）：每个原子声明——合法参数、类型、必填/可选、默认值、数值范围、允许的触发器、装备态/消耗态是否支持、结算结果、是否产生事件、是否允许嵌套。**把 `params: Record<string,unknown>` 升级为按 atom 判别的联合类型**（见 §7.2）。
4. **跨引擎黄金基准**：选少量代表场景，固定 seed + 输入 + 配置，录制 H5 的结束态（生命/敌余量/伤害/掉落序列/卡状态/事件序列/波次状态）为 fixture。Unity 必须重放出**统计一致**（非逐位一致）的结果。这是"复刻正确"的唯一客观验收标准。

### 3.2 Unity 开工的"就绪定义"（可被另一位开发拿来卡你）
以下**全部满足**即可开工，不必等 Stage 0 全部收尾：
1. 模块已分为"稳定 / 实验 / 延后"三类清单；
2. 第一版配置 schema 已定；
3. 核心状态与事件边界已定；
4. 已选定一组跨引擎黄金场景；
5. Unity 侧承诺**先做纵向切片**、不做全面复制。

## 4. 冻结什么、不冻结什么

**"稳固不变"的对象是契约，不是全部数值。** 按"改动成本"分类：

| | 贵（改一次伤筋动骨 → 必须先冻） | 便宜（随时可改，Unity 重读 JSON 即可） |
|---|---|---|
| 内容 | schema 结构、atom/trigger 命名、参数契约、GameEvent 契约、核心判定顺序、RNG/时间步语义、ID/引用规则、文案 key 结构 | 一切数值、卡牌/遗物/神池内容、文案文本、提示引导、表现/音效 |

你不需要等占位数值填完才开始 Unity——**那会永远等下去**。冻结的是结构，值一直变没关系。

---

## 5. Unity：纵向切片，不是全量复制

第一版 Unity **不追求**：全部卡牌、全部遗物、全部文案、完整调参编辑器、全部 VFX、全部怪物机制。

**只打通一条端到端链路**：读同一套配置 → 建基础 GameState → 固定时间步推进 → 一种敌人 → 炮台攻击与伤害 → 一次掉落与拾取 → 一次合成 → 一张卡的装备态 → 一张卡的消耗态 → 一个触发器 + 一个状态效果 → 核心事件传给表现层 → 与 H5 黄金基准对照。

通过后再**按原子类别逐类扩张**：弹道 → 控制 → 领域 → 防御 → 经济 → 神池/遗物/进化。

好处：接口验证前置、错误早暴露、你这边的契约漂移会被切片立刻照出来。

## 6. 配置工具：先管线后编辑器，先表单后节点图

### 6.1 单一事实来源 = JSON（引擎无关）
最易踩的坑：让 Unity 的 ScriptableObject 成为配置源头 → H5 与 Unity 配置分叉、双端对不上。

> **JSON / JSON Schema 是权威源；TypeScript、C# 类型与 Unity 资产由它生成或导入。** ScriptableObject 只作 Unity 内部缓存/资产，不作第二套真相。理由：你要保留 H5 原型；AI 更擅长读写文本；Git 对 JSON 的 diff 更清晰。

### 6.2 反过度工程：最小可用契约 vs 可延后的重型工具（我对 ChatGPT 方案的关键收敛）
ChatGPT 描绘的"内容编译器 + TS/C# 双端代码生成 + 语义校验 + 全功能编辑器 + 文件树爆破"方向正确，但**对一个个人开发者，存在先造工具城堡、后验证游戏好不好玩的风险**。因此明确分层：

**Unity 并行前必须有（小而硬）**：
- (a) 效果参数强类型化（判别联合）；
- (b) 原子/词条定义收敛到**单一来源**（删掉 `skillValidator` 里手抄的 Set，改为从类型/注册表派生，或从一份 JSON Schema 生成）；
- (c) 黄金回放 fixture；
- (d) §3.0 静止点冻结。

**可延后（Unity 真正需要时再做）**：
- C# 代码生成（等 Unity 开发实际提出再做，别提前）；
- 把 `skills.json` 爆破成 per-card 文件（**单作者场景下收益低**：其主要好处是减少多人合并冲突，你一个人维护，暂不值这笔迁移成本——**这是我与 ChatGPT 的一处分歧，建议延后**）；
- 节点图编辑器、批量平衡表、曲线图、模拟器面板。

### 6.3 复用你已经有的写回管线（ChatGPT 不知道的现成资产）
`vite.config.ts` 里已有 `/__tuner/preset`、`/__calibration/export`、`/__telemetry/*` 一组**能把 JSON 写回磁盘的 dev-server 中间件**。配置编辑器 v1 直接在现有 Vite app 里加一个路由：读 JSON → 按 schema 渲染表单 → 用现成 validator 实时校验 → 经中间件落盘。**几乎复用你的全部零件**，这就是你设想的"一个应用里直接改所有配置"，成本中等。

### 6.4 编辑器 v1 先做表单
技能模型本质是 卡→星级→进化分支→触发器→原子→参数 的树，最适合"左列实体 / 中间结构化表单 / 右侧校验预览说明"。v1 功能：搜索筛选分类、增删改复制、按原子类型自动显示合法参数、范围/单位提示、引用下拉、即时错误、变更 diff、H5 实时预览、Git 友好导出、一键校验+测试。节点图/批量表/模拟器后续再加。

## 7. 配置体系当前必须优先修的具体问题（已核验）

### 7.1 消除多套重复定义
`docs/skills-schema.json` + `defs.ts` 类型 + `skillValidator.ts` 手抄 Set + 注册表默认值 = 四套来源。收敛为一个来源，派生出：类型、校验器、编辑器表单元数据、默认值、文档。**这是投资回报最高的一项清理。**（做法可增量：先让校验器的 Set 从类型/注册表派生，而非另起一套代码生成框架。）

### 7.2 效果参数改判别联合类型（Unity 移植前最重要的数据层改造）
```ts
type EffectDef =
  | { atom: 'chain';  params: { bounces: number; damageRetention: number; searchRange: number } }
  | { atom: 'shield'; params: { absorbHits: number; regenSeconds?: number } }
  | { atom: 'summon'; params: SummonParams };
```
C# 端据此生成 DTO / 自定义反序列化。防止两端参数名、默认值、int/float、缺字段回退行为不一致。

### 7.3 统一调参元数据
`tuner.json`（min/max/step）、`tunerSchema.ts`（标签/分组/延迟生效）、`tunerPanel.ts`（特殊控件）三处合一：
```json
{ "path": "combat.defaults.damage", "type": "number", "labelKey": "tuner.combat.damage",
  "group": "combat", "min": 1, "max": 200, "step": 1, "applyPolicy": "immediate", "unit": "damage" }
```
H5 面板、Web 编辑器、Unity 调参面板读同一份。

### 7.4 彻底统一文案归属
`relics.json` 现同时有 `textKey` 与内联 `title`/`desc`。正式方案：配置只留 `nameKey`/`descriptionKey`，文本全部进本地化表；Unity Localization 原生支持 String Table，可由同一份外部文案表导入。

## 8. 其他任务的时间归位（按改动成本排，不按紧急排）

- **优化交互手感**：拆两类。可现在做（表现层）：点击区域、拖拽反馈、动画时长、音效震动、信息层级、卡牌详情、Toast、UI 布局。**暂缓频繁改**（会动跨引擎规则契约）：装备/合成规则、暂停时机、瞄准逻辑、消耗态落点语义、波间决策顺序。注意：**深度手感打磨终究是 Unity 的活**，H5 上过度打磨=丢弃性工作。
- **正式文案 / 提示 / 引导**：拆两步。现在做"**文案工程化**"（全部抽离、建 key、分类、清硬编码、占位检查、UI 只引用 key）；**稍后再写最终措辞与教程节奏**（机制未定案前不值得写死）。文案属配置/内容层，归配置线，**不归 Unity**。
- **卡牌融合数值词条**：**实现延后**，但**现在在 schema 预留结构位**（`fusionPolicy` / `affixTransferPolicy` / `conflictResolution` / `sourceCardIds` / 版本迁移位）。预留便宜、事后 retrofit 贵。→ 见 §11 需你拍板。
- **更多怪物机制**：延后。现在只需确保敌人可由 基础属性 + 行为组件 + 触发条件 + 技能列表 组合，而非现在就设计更多怪。Unity 一期先验证现有普通/高速/重装/Boss。
- **手动瞄准**：延后，且本就该延（与 P0-1"全自动炮台定案"冲突）。但 Unity 移植时把索敌抽象成接口 `ITargetProvider`（`AutoTargetProvider` / `ManualAimTargetProvider`），以后加手动瞄准不必重写攻击系统。

## 9. 与 ChatGPT 建议的差异（我改了/加了什么）

1. **加了"先到静止点再冻结"的前置**：神池/构筑重构仍在快速变化，不能在半场冻契约。
2. **加了实测依据**：类型检查全绿 + 内容层冒烟通过；ChatGPT 明确无法运行测试，我把这块补上了。
3. **收敛了工具野心**：把 ChatGPT 的"内容编译器 + 双端代码生成 + 全功能编辑器"拆成"Unity 并行前必须的小硬集"与"可延后的重型件"，防止个人开发者过度工程。
4. **反对现在爆破 `skills.json` 文件树**：单作者场景收益低、迁移有成本，建议延后（明确分歧）。
5. **指出可复用的现成写回中间件**（`/__tuner`、`/__telemetry`），让配置编辑器 v1 成本更低。
6. **其余方向（准入门、纵向切片、JSON 权威源、判别联合类型、黄金基准、延后项归位、`ITargetProvider`）与 ChatGPT 一致，且我核验后确认其针对本项目的具体主张（松散参数、重复定义、遗物双文案）属实。**

## 10. 风险登记

1. **在漂移中冻结** → 用 §3.0 静止点门槛卡住，不到静止点不冻。
2. **契约固化演变成大重构** → 严守"最小可用契约"，参数强类型化与定义收敛用增量派生，不起代码生成框架。
3. **Unity 浮点/时序漂移** → 统计验收而非逐位；判定顺序写进规格书。
4. **工具先行、游戏后验** → 编辑器 v1 只做表单必要功能；好不好玩靠 H5 快速验证，工具不得阻塞玩法迭代。
5. **测试给假安全感** → 现有测试证明"能跑"不证明"设计对"；正式内容设计阶段需补强度/差异化的语义校验。
