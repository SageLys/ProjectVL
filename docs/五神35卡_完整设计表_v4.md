### 0.2 stars 迁移锚点生成规则（机械生成，不逐卡写）

运行时绑定只读 `evolutionTree`（`resolveCardBindings` 已核实），`stars` 仅作展示与迁移锚点。统一规则：

- `stars['3']`（tier `core`）= 3★A（稳定型）绑定副本
- `stars['5']`（tier `dual`）= 3★A + 5★1（兑现）绑定副本
- `stars['6']`（tier `transform`）= 3★A + 5★1 + 6★ 公共绑定副本

### 0.3 4★ amplify 与 amplifyAxis

`sharedNodes[4★].amplify` 是一个扁平 `Record<param, "+n"|"*n">`，`applyAmplify` 只放大 3★ 分支中**实际存在**的参数键——所以三个分支各取所需，一张表即可覆盖 A/B/C。本表每卡给出完整 params；`amplifyAxis.description` 用每卡「4★」行文字，`amplifyAxis.params` 与 sharedNode 相同。校验 V4：amplify 的键不得与任何 5★ 选项强化的参数重叠。

### 0.7 唯一的新增引擎能力：`chain.spreadStatus`

```

chain.spreadParams?: { ratio?, duration? }
```

融合契约：跨卡按 statusSystem 既有仲裁（取最强/取最长），写入 `interpreter.ts` 顶部契约注释并补 `fusionOrderInvariance.test.ts` 用例。

### 0.8 全表通用红线（每张卡已合规；进 skillValidator）

1. `onKill` / `onBreach` 绑定的效果一律按**事件坐标**出效果，禁止直接作用单体敌人（V8）
2. 6★ 不得重复声明分支已用的 `shield`/`novaOnBreak`/`expiryConvert`/`breachReduction`/`execute`（V10）
3. `requiresSource` 只允许 `weapon` / `chain` / `dot`（V11）
4. 所有 `requiresStatus` 效果必须有资源为 0 时的 fallback（V5）
5. 文案一律承诺「后续命中/击杀时兑现」，不承诺同一击立即连锁（同击顺序不可依赖）
6. `requiresStatus:'dot'` 的条件必须由直接 dot 分支供给，不能只靠火场（V9）
7. 多来源同类强被动不相加（`shield` 取最大、`slow`/`vulnerable` 取最强、`novaOnBreak` 分轴取最大）——两槽组合必须是正交轴

### 0.9 关键引擎事实速查

| 事实 | 影响 |
|---|---|
| `fireTrigger('onHit')` 只在 `combatSystem:164`，且在 `hitIds` 去重后 | 贯穿每穿一个新敌人各发一次 onHit；分裂弹片各自命中各发一次——「并发型」的唯一实现路径 |
| `chainFrom` / `explode` / zone tick 只走 `dealDamage`，不发 onHit | 雷链、爆炸、地面区域无法触发 onHit 绑定 |
| zone 内的 `dot` 直接掉血、不叠状态 | 火场敌人 `requiresStatus:'dot'` 读不到，`requiresSource:'dot'` 读得到 |
| `novaOnBreak` 在 `absorbBreach` 里遍历 `[...state.enemies]` | 不踩尸体红线，磐垒破盾反击安全 |
| `shield` 容量取最大、再生取最小 | 两张卡都发 shield ＝ 互相吃掉，不是联动 |
| `slow` 多来源取最强不叠乘；`freeze/stun` 受 `ccResist` 与控制预算限制 | 凛冬卡不得假设「全场同时冰封」 |

### 5.0 磐垒的结构性难题与解法（必读）

`shield` 融合契约是**容量取最大、再生取最小**——两张磐垒卡都发 `shield` ＝ 互相吃掉。磐垒的「产资源」拆成两种正交形式：

|---|---|---|
| 供应容量 | `shield` | **只有神盾一张**（其余卡不得发 shield） |
| 延长壁垒寿命 / 制造承压点 | `breachReduction`（相加封顶 0.9）、`thorns`（相加）、`summon`（每卡独立实例）、`aura`（按来源并行） | 其余六张 |
