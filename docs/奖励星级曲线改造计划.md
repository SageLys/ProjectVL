# 奖励星级曲线改造计划

目标：万能卡星级随波数递增、验证期同时掉高星具体卡。已确认代码现状，以下为落地方案。

决策（本次已定）：
- BOSS 万能卡曲线封顶 **5★**（6★万能卡在当前规则下无法工作，5★万能卡即"造 6★卡"的奖励）。
- 数值**直接改 base 配置**，不走 variant。
- 验证期具体卡采用**构筑卡 + 转向卡混合**。

---

## 一、代码现状（已核对 `main` @ 36300cf）

| 问题 | 现状 | 位置 |
|---|---|---|
| BOSS 万能卡封顶 3★ | `star = 1 + floor((wave-1)/3)`，`starMax:3` → 波1-3=1★, 4-6=2★, 7-8=3★ | `waveBossSystem.ts` `computeWaveBossReward`；`waves.json` `waveBoss.reward` |
| 精英(Bounty)万能卡封顶 2★ | `base:1, every:4, max:2` → 波1-4=1★, 波5+=2★ | `bounty.json` `reward.wildcardStar*` |
| 验证期只掉万能卡 | 精英与 BOSS 奖励全部走 `spawnWildcardDrop`，无具体卡 | `waveBossSystem.ts`；`waves.json` `stagePlan.validation` |
| 6★万能卡不可用 | `maxStar:6`；`grantWildcards` 拒绝 `star >= maxStar`，万能卡只把目标 +1 星 | `wildcardSystem.ts`；`economy.json` |
| 配置无星级校验 | 校验器只查阶段结构，不查奖励星级 | `stagePlanValidator.ts` |

结论：主观判断成立。BOSS/精英万能卡确实过于保守；验证期确实只有万能卡，必须补高星具体卡。

---

## 二、目标曲线（8 波基础局）

数量统一为 ×1，取消现有"每 3 波翻倍 + 最终波额外份"。星级负责质量增长。

| 波 | 阶段 | BOSS 万能卡 | 精英/Bounty 奖励 | 验证期具体卡 |
|---|---|---:|---|---|
| 1 | selection | 1★ | 1★具体 + 1★万能 | — |
| 2 | selection | 1★ | 1★具体 + 1★万能 | — |
| 3 | build | 2★ | 2★具体 + 2★万能 | — |
| 4 | build | 2★ | 2★具体 + 2★万能 | — |
| 5 | build | 3★ | 3★具体 + 3★万能 | — |
| 6 | build | 4★ | 3★具体 + 4★万能 | — |
| 7 | validation | 5★ | Bounty 关闭 | 坦克精英掉 **4★构筑卡** |
| 8 | validation | 5★ | Bounty 关闭 | 坦克精英掉 **5★构筑卡**；高速精英掉 **3★转向卡** |

成长链（让 5★/6★ 真正参与验证战斗，而非结算展示）：
- 波6 BOSS 给 4★万能 → 波7 精英给 4★构筑卡 → 波7 BOSS 战前可合成出 5★卡
- 波7 BOSS 给 5★万能 → 波8 精英给 5★构筑卡 → 最终 BOSS 战前可合成出 6★卡

10 波变体（`validation-10.json`）自动兼容：BOSS 走同一阶段日程 `1,1,2,2,3,4,4,4,5,5`。

## 三、改动清单（按文件）

### 1. `src/config/base/waves.json`
- `waveBoss.reward` 由公式改为阶段日程：
```json
"waveBoss": {
  "reward": {
    "schedule": { "selection": [1, 1], "build": [2, 2, 3, 4], "validation": [5, 5] },
    "count": 1
  }
}
```
> 数组长度 < 阶段波数时取最后一项。build 用 `[2,2,3,4]`（8波）；10波下 build 有 6 波，取 `[2,2,3,4,4,4]` —— 两套都想精确命中，把 build 写成 `[2,2,3,4,4,4]`，8波取前 4 项即可。
- `stagePlan.validation` 奖励改为带 `kind` 的联合类型：
```json
"validation": [
  {
    "enemies": [
      { "type":"tank", "hpMul":14, "damageMul":2, "speedMul":0.75,
        "ccResistOverride":0.7, "knockbackResistOverride":0.8,
        "reward": { "kind":"card", "star":4, "count":1, "typePolicy":"build" } }
    ],
    "bossReward": { "kind":"wildcard", "star":5, "count":1 }
  },
  {
    "enemies": [
      { "type":"tank", "hpMul":20, "damageMul":2.5, "speedMul":0.7,
        "ccResistOverride":0.7, "knockbackResistOverride":0.8,
        "reward": { "kind":"card", "star":5, "count":1, "typePolicy":"build" } },
      { "type":"fast", "hpMul":10, "damageMul":2, "speedMul":1.1,
        "ccResistOverride":0.5, "knockbackResistOverride":0.6,
        "reward": { "kind":"card", "star":3, "count":1, "typePolicy":"pivot" } }
    ],
    "bossReward": { "kind":"wildcard", "star":5, "count":1 }
  }
]
```

### 2. `src/config/base/bounty.json`
`reward` 精确控制到波（新增按波日程数组，clamp 末项），精英万能卡 1→4★、具体卡 1→3★：
```json
"reward": {
  "cardCount": 1,
  "cardStarByWave": [1, 1, 2, 2, 3, 3],
  "cardStarMax": 3,
  "wildcardCount": 1,
  "wildcardStarByWave": [1, 1, 2, 2, 3, 4],
  "wildcardStarMax": 4,
  "dropLifetimeSeconds": 12,
  "repeatProtection": 1
}
```
> 保留 `*Max` 作兜底；`rewardStar()` 改为优先读日程数组、无则回退旧 `base+every` 公式（兼容旧变体）。Bounty 波7-8 已被 `bountySystem.ts:133` 的 validation 判定关闭，无需额外处理。

### 3. `src/config/types.ts`
- 新增联合类型并替换 `reward`/`bossReward`：
```ts
export type ValidationRewardSpec =
  | { kind: 'wildcard'; star: number; count: number }
  | { kind: 'card'; star: number; count: number; typePolicy: 'build' | 'pivot' | 'uniform' };
// ValidationEnemySpec.reward: ValidationRewardSpec
// ValidationWaveConfig.bossReward: ValidationRewardSpec
```
- `waveBoss.reward` 改为 `{ schedule: { selection:number[]; build:number[]; validation:number[] }; count:number }`。
- `bounty.reward` 增加可选 `cardStarByWave?/wildcardStarByWave?`。

### 4. `src/config/loader.ts`（或 `index.ts` 归一化处）
- 兼容旧配置：`reward`/`bossReward` 缺 `kind` 时默认 `kind:'wildcard'`（保证 `validation-10.json` 等旧变体不崩）。

### 5. `src/config/stagePlanValidator.ts`
新增奖励校验（需注入 `economy.maxStar`）：
- `kind ∈ {wildcard, card}`；`count` 为正整数；`star` 为整数。
- wildcard：`1 ≤ star ≤ maxStar-1`（**禁止 6★万能卡**，否则启动不报错、拾取时被静默过滤）。
- card：`1 ≤ star ≤ maxStar`；`typePolicy ∈ {build, pivot, uniform}`。
- `waveBoss.reward.schedule` 各阶段数组非空、每项 `1 ≤ star ≤ maxStar-1`。

### 6. `src/core/systems/waveBossSystem.ts`
- `computeWaveBossReward` 重写为读阶段日程（`resolveActiveWavePlan`/`stageForWave` 拿阶段 → 索引数组，clamp 末项），返回 `[{ star, count:1 }]`。
- 新增统一函数处理具体卡奖励：
```ts
function spawnValidationCardReward(state, config, rng, x, y, spec) {
  const type =
    spec.typePolicy === 'build'  ? selectBuildType(state, rng) :
    spec.typePolicy === 'pivot'  ? selectPivotType(state, rng) :
                                   selectUniformCardType(rng);
  spawnGroundDrop(state, config, rng, x, y, type, spec.star, 'validationElite');
  const drop = state.groundDrops[state.groundDrops.length - 1];
  drop.secure = true;
  drop.validationRewardWave = state.wave;
  drop.validationTypePolicy = spec.typePolicy; // 供遥测
}
```
- `grantValidationEliteReward` 与 `grantWaveBossReward` 按 `reward.kind` 分支：`wildcard` 走 `spawnWildcardDrop`（同现状，保留 `secure`/`validationRewardWave`），`card` 走上面的函数。签名补 `config, rng`。

### 7. `src/core/systems/damageSystem.ts`
- `killEnemy` 中调用改为 `grantWaveBossReward(state, config, rng, x, y)`、`grantValidationEliteReward(state, config, rng, enemy)`（作用域已有 `config, rng`）。

### 8. `src/core/systems/enemySystem.ts` / `src/core/systems/waveSystem.ts` / `src/core/types.ts`
- `Enemy.validationReward` 与 `spec.reward` 类型改为 `ValidationRewardSpec`（透传即可，`waveSystem.ts:52` 无需改逻辑）。
- `GroundDrop` 增加可选 `validationTypePolicy?: 'build'|'pivot'|'uniform'`。

### 9. 满手牌机会成本（保持）
- 高星具体验证卡**不自动绕过手牌容量**：`collectDrop` 现有逻辑对 `kind:'card'` 满手牌即返回 `cardsFull`（除非可立即合成），保持不变；卡槽容量是本作核心机会成本。
- `secure` 只保证不过期；`waveSystem.ts:143` 的完波门禁已等待 `drop.secure && drop.validationRewardWave===wave`，具体卡会正常挂起波次。
- `eventText.ts` 的 `cardsFull` 分支：当 `event.secure` 时改用专用提示——"验证奖励待处理：请消耗、合成或替换一张手牌"。（`cardsFull` 事件已带 `secure`。）

### 10. 遥测（`src/telemetry/*`）
- 具体卡验证奖励拾取补 `validationRewardPickup` 事件：`rewardKind(card/wildcard)`、`cardType`、`typePolicy(build/pivot)`、`star`、落地→首次操作(merge/equip/consume/unused)秒数、是否在最终 BOSS 前达 5★/6★。

## 五、验收指标（初始区间）

| 指标 | 初始目标 |
|---|---:|
| 验证期高星具体卡拾取率 | ≥90% |
| 拾取后 15 秒内被合成/装备/消耗 | ≥70% |
| 高星奖励整局未使用率 | ≤20% |
| 波7 BOSS 前后达 5★ 的局数 | 50%–80% |
| 最终 BOSS 战中实际持有 6★ 的局数 | 30%–60% |
| 安全奖励因满手牌阻塞 >10 秒 | ≤10% 局数 |
| 因奖励无法处理造成软锁 | 0 |

> 6★出现率不设 100%：否则验证期从"验证构筑成果"退化为固定发终极形态，前面的选择与合成失去意义。
