# 装备被动融合契约

装备槽顺序不得改变最终战斗行为。各类被动按以下规则融合：

| 效果类别 | 融合规则 |
|---|---|
| 数值乘数 | `dropRateMul`、`dropLifetimeMul`、`xpMul` 乘法叠加 |
| 加法数值 | `thorns`、`breachReduction` 加法叠加；后者上限 0.9 |
| 阈值 | `execute` 取最高 |
| 破盾新星 | `novaOnBreak` 同卡后声明覆盖；跨卡 `damage`、`knockbackDistance` 两轴分别取最大 |
| 过期转化 | `expiryConvert` 同卡后声明覆盖；跨卡按规范来源序计算 `1 - ∏(1 - ratioᵢ)` |
| 显式嘲讽 | `taunt` 同 `sourceKey` upsert；跨来源按 `priorityWeight`、`remaining`、`sourceKey` 仲裁，赢家失效后回退 |
| 状态施加 | `slow`、`vulnerable`、`freeze`、`stun` 由 `statusSystem` 取最强，时长取最大 |
| 光环/领域 | 按来源独立并行 |
| 触发型绑定 | 所有装备独立触发；所有攻击形态都经过 `onFire → resolveImpact → onHit/onKill` 管线 |
| 召唤物 | 每个（卡，绑定）单实例；装备/升星/卸载/换波由 `reconcileEquipmentPassives` 声明式同步 |
| 护盾 | `absorbHits` 取最大，`regenSeconds` 取最小 |
| 主炮形态 | 按 delivery、impact、cadence 三个正交轴确定性融合 |

## 来源与规范顺序

装备绑定统一按 `card.type → card.id → bindingIndex` 排序；卡内 `effects` 保持原始顺序。`novaOnBreak` 与 `expiryConvert` 先以卡实例 id 分组，同卡后声明覆盖，再跨卡融合。build 与词条缩放在聚合前完成，所以参与比较的是缩放后的最终值。

显式 taunt 的稳定来源键为 ``${cardType}/${cardId}/${bindingIndex}/${effectIndex}``，不含槽号；消耗态为 ``consume/${cardType}``。`priorityWeight` 默认 1。同来源重复施加不增加候选，剩余时间取新旧最大值，坐标与 `summonId` 使用新值。不同候选独立计时；关联召唤物死亡只删除对应候选。环境召唤物的 `tauntRadius` 仍是独立系统，不计入 `isControlled()`。

`novaOnBreak.chance` 与 `expiryConvert.chance` 在 passive 聚合路径不进入 `runEffects`，当前没有运行时语义；不得据此增加 RNG 抽取。

## 已知顺序依赖（清单）

以下路径必须持续由换槽回归测试覆盖；它们曾经读取物理槽位或依赖数组先后，本契约不把清单数量视为封闭集合：

- interval、aura、触发绑定和被动对账统一使用规范绑定顺序，保证事件与 RNG 消耗顺序稳定。
- `novaOnBreak`、`expiryConvert`、`taunt` 使用上述融合/仲裁规则，不以最后遍历者为赢家。
- 无威胁方向时，装备召唤物按稳定来源键计算方位，不读取装备槽号。
- 环境召唤物 `priorityWeight` 相等时按稳定来源键决胜；无来源的临时召唤物退化到 summon id。
- `replacesEarlier` 只删除同卡更早的召唤实例；规范排序仍保持同卡 `bindingIndex` 升序。

## 主炮形态

所有 passive 形态贡献先按 `cardType` 字典序（再按卡实例 id）排序，装备槽顺序不参与结果。`onFire` / `interval` 触发的 `mortarMorph` 仍走 rider 路径，不进入本节的 weaponFusion。

### delivery 覆盖轴：beam 取最强且不收叠加税

多张 beam 竞争同一个 delivery，不能同时生效，因此按 `damageRatio` 取最强者；相等时保留排序靠前者。胜者的 `damageRatio`、`interval`、`duration`、`tickInterval`、`width`、星级和来源卡必须成套采用且全额生效。衰减是叠加税，而 delivery 是覆盖轴，所以胜者不乘 `damping`。落败 beam 被完全丢弃，只有这些来源计入 `suppressedByFusion`。

delivery 判定为：存在 beam 时使用 `line`；否则存在 mortar 时使用 `lob`；两者都没有时使用 `projectile`。

### impact 叠加轴：mortar 独立追加

每张 mortar 向 `impacts[]` 追加一个 aoe。组内第一个全额生效；第 2 个及之后的伤害乘 `damping`，覆盖面积乘 `areaMul`（运行时半径乘 `sqrt(areaMul)`）。两项都是固定衰减、不复利，且衰减不算 suppression。

因此一张 beam 与一张 mortar 混装时，mortar 是本组第一个，不吃 `damping` / `areaMul`；结果为持续光束加完整规格的命中爆炸。当前正式配置只有一张 mortar 形态卡，所以同类叠加衰减暂处于休眠状态。

### 伤害预算分配

融合爆炸不能直接拿整道光束的完整周期预算：爆炸会对范围内多个敌人分别结算，直接复制完整预算会随命中人数重复超发。它改为从同源主炮周期预算中按固定 `impactShare` 分配一小块，因此与光束本体一样继承 damage、fireRate、multi，同时混装收益比例不会随成长衰减。

| delivery | 单次 impact 预算基数 | 成长继承 |
|---|---|---|
| `line` | `baselineDps × form.interval × impactShare` | damage、fireRate、multi |
| `lob` | `totalDamage × totalMulti` | damage、multi；fireRate 已由 `shotCd = 1 / totalFireRate` 继承 |
| `projectile` / rider | `totalDamage` | 保持原有触发式效果语义 |

其中 `baselineDps = totalDamage × totalFireRate × totalMulti`。`AttackInstance.baseDamage` 继续供 riders 与 legacy mortar fallback 使用；范围形态只读取按 delivery 快照的 `impactBudget`。正式 `impactShare = 0.41416083945517623`，以 S1 五目标场景校准后，`solarLance + splitBlast` 相对单装 `solarLance` 的总伤害比为 1.35。

### 调参旋钮

| 配置 | 控制内容 | 何时生效 |
|---|---|---|
| `impactShare` | mortar 融入 beam 时，每次爆炸取得的主炮单周期预算比例；混装强度的主要旋钮 | `line` 上存在 aoe impact |
| `damping` | 第 2 个及之后 mortar 的固定伤害倍率，不复利 | 同时装备 2 张以上 mortar 形态卡 |
| `areaMul` | 第 2 个及之后 mortar 的覆盖面积比例；半径按平方根缩放 | 同时装备 2 张以上 mortar 形态卡 |

旧字段 `radiusMul` 已改名为面积语义的 `areaMul`；基础配置由半径倍率 `0.6` 等价迁移为面积倍率 `0.36`，迁移本身不改变半径行为。

### 持续光束的伤害与触发预算（方向 A）

- 光束继承普通主炮的每秒直接伤害预算：`totalDamage × totalFireRate × totalMulti`。每周期总伤害为该预算乘光束周期与形态倍率，并均分到本周期的各个 tick；因此伤害、射速与多弹丸成长都会等比提高光束的直接伤害。
- 每道光束只创建一个攻击实例并只触发一次 `onFire`；同一道光束对每个敌人只在首次命中时触发一次 `onHit`，后续 tick 只结算直接伤害。射速与多弹丸不会额外生成连锁、冻结、灼烧等附加效果触发次数。
- 如后续需要补偿高频触发流，应另行评估带 `procCoefficient` 的 `virtualShotBudget`；该机制不属于当前契约。
