# ProjectVL 第七阶段设计思考历程报告
## 时间范围：2026 年 7 月 24 日—7 月 26 日

## 一、报告目的与证据口径

本报告用于重建 ProjectVL 第七阶段中，用户如何从实际试玩和项目推进压力出发，依次处理三类问题：

1. 复杂卡牌系统已经存在，但主界面既被长文案挤坏，又无法真正说明技能；
2. H5 原型已经积累大量系统，但何时、以什么条件开始 Unity 移植与配置工具建设仍不明确；
3. 卡间进化在代码中已经实现，但用户亲自试玩时没有感知到，说明功能交付与玩家可发现性之间存在断层。

报告服务于游戏战斗策划求职中的简历、作品集和面试叙述，不把聊天或 Git 提交简单复述为流水账，而是重点提炼：用户发现了什么、如何重新定义问题、提出了哪些设计边界、如何安排实现顺序、哪些判断随后进入仓库，以及哪些结论仍缺少真人验证。

证据分为四类：

- **用户明确提出的判断与要求**：可以直接视为用户的设计思考；
- **同期助手的代码分析和方案**：属于讨论产物，不能自动算作用户独立提出；
- **仓库中的提交、文档和测试**：可以证明方案进入工程，但不能自动证明体验已经变好；
- **后续版本事实**：用于确认本阶段思想是否产生持续影响，不能倒推为本阶段已经完成全部效果验证。

## 二、阶段结论摘要

第七阶段的核心，不是继续增加卡牌、敌人或成长系统，而是把已经膨胀的原型推进到三个更高标准：

> **复杂规则必须能被玩家理解，数据系统必须能被策划维护，已实现功能必须能被玩家发现。**

这一阶段形成了三次连续升级：

### 1. 从“卡牌上写更多说明”升级为“战斗信息架构”

用户同时发现两种看似矛盾的问题：

- 卡牌文字太多，撑大底部区域、挤压战场，已经影响正常游玩；
- 卡牌真正重要的技能效果、词条作用和进化分支又没有说清楚。

因此问题不是文案长度，而是不同信息被错误地塞进同一层界面。用户提出固定主卡面、点击进入暂停详情页、详情页展示当前效果、完整技能树、词条解释和已选路线。这是从“补文案”转向“按决策时机分配信息”的设计。

### 2. 从“先做哪个大任务”升级为“依赖关系与并行生产管线”

用户最初在“审查架构并启动 Unity”与“抽离配置并制作编辑器”之间犹豫。进一步分析后，真正的前置不是二选一，而是先确定哪些规则和数据结构必须稳定，达到什么程度后 Unity 与内容生产工具才能安全并行。

由此形成的阶段原则是：

> **先冻结接口，不冻结内容；先打通纵向切片，不全面复制；先做配置管线，再做可视化编辑器。**

### 3. 从“代码中有这个功能”升级为“玩家是否知道、理解并能使用”

用户没有因为代码宣称进化已完成就接受结论，而是用自己的试玩经历提出反证：如果功能真的完成，为什么自己从未见到？他进一步主动提出，两张可进化的不同卡牌应出现连线和文字提示，而且视觉语言必须与普通合成区分。

这说明用户开始以玩家侧完成标准审查功能：

> **功能完成 = 规则存在 + 触发可达 + 信息可见 + 操作可理解 + 反馈可辨认。**

综合来看，第七阶段是 ProjectVL 从“快速扩张系统的原型”转向“可理解、可维护、可移植、可验收的战斗产品”的生产化转折点。

## 四、7 月 24 日：从 UI 破版问题上升为完整的信息交付体系

### 4.1 用户发现的是一个“双重失败”

用户没有只说“字太多”或“字太小”，而是同时指出：

- 宏观上，当前卡牌描述会自动扩张，挤占上方主战场，使游戏无法正常游玩；
- 微观上，卡牌最重要的技能效果、数值词条和分支效果依然描述不清，甚至完全没有说明。

这是一项很有价值的诊断，因为它否定了两个简单修补方向：

- 继续缩小字体，不能解决信息不足；
- 继续增加卡面文字，会进一步破坏战场布局。

真正的问题是：**高频操作层和低频阅读层没有分离。**

### 4.2 用户提出的信息层级方案

用户明确要求主界面恢复固定布局，卡牌只保留：

- 大号技能名；
- 技能图标；
- 星级；
- 少量小字数值词条。

点击卡牌后进入暂停的二级菜单，承载：

- 当前卡牌的完整技能效果；
- 技能数值和词条到底如何生效；
- 当前卡牌完整的 1—6 星技能树；
- 当前已经点亮和选择的进化路线；
- 分支选项的具体效果及其差异；
- 高星复杂效果的完整说明。

这里最重要的不是某个弹窗样式，而是用户已经按照“玩家当下要做什么”来分配信息：

- 战斗主界面用于快速识别和拖拽操作；
- 详情菜单用于学习、比较和规划构筑；
- 分支弹窗用于作出不可逆选择。

### 4.3 对未来复杂度的提前设计

用户明确预见高星卡牌的技能描述会继续变复杂，因此要求主界面尺寸不随内容增长。这不是一次局部修图，而是在处理内容规模化之后的 UI 稳定性。

这说明用户已经意识到：

> **内容复杂度应当扩展数据与详情层，而不能无限侵占战斗操作层。**

这一判断对战斗策划很重要。技能系统越深，越需要控制信息暴露顺序，否则设计深度会直接转化为认知负担。

### 4.4 从“人工写死说明”转向“真实配置自动解释”

同期方案进一步提出：

- 精确数值和机制从 `skills.json` 与真实解释器结果生成；
- 构筑意图、新手说明和关键词解释由 `texts.json` 人工维护；
- 词条说明直接读取现有结算契约，区分装备态、消耗态、即时结算和限时生效；
- 技能树显示必须读取当前卡牌实例的实际路线，而不是复制一套静态文本。

这一方案并非用户在原始消息中逐项提出，但与用户的核心要求高度一致，并在同日主线提交中落地。其设计意义是把两类信息分开：

1. **客观机制事实**：应由配置和结算逻辑生成，防止调数值后文案失真；
2. **设计意图与学习辅助**：需要人工表达，说明“适合什么构筑、为什么选”。

### 4.5 仓库落地

7 月 24 日提交 `e02c5e8`“Add card detail UI and combat feedback improvements”实际新增或修改了：

- `cardDetailModal.ts`：详情弹窗与交互；
- `cardDetailModel.ts`：卡牌详情和技能树展示模型；
- `effectText.ts`：效果原子与触发器的玩家语言转换；
- `pauseState` 与 `game.ts`：详情打开期间暂停，但不破坏原有手动暂停状态；
- `slotFactory.ts`、`app.css`：固定卡面和点击查看详情；
- `modals.ts`：进化分支显示精确效果与构筑意图；
- 多项 UI、效果文案与测试。

这说明用户提出的信息架构并未停留在“做一个说明弹窗”，而是推动了数据、UI、交互、暂停语义和测试共同改造。

### 4.6 与前期思考的关系

此前阶段已经要求手牌与装备分别显示即时效果和常驻效果，并强调机制质变必须被玩家看到。第七阶段进一步承认：当卡牌数量、星级、分支和词条继续扩展时，仅靠卡面短句已经无法承担完整解释。因此，项目从“两种上下文短描述”升级为“主卡面快速识别 + 详情页完整理解 + 分支页即时决策”的三层结构。

这不是推翻此前设计，而是内容规模增长后对信息架构的再升级。

## 五、7 月 26 日 16:02：从任务优先级焦虑转向跨引擎生产架构

### 5.1 用户面对的真实矛盾

用户列出了两个当务之急：

第一，审查当前代码和关键架构，判断是否已经稳定到可以交给另一位开发者开始 Unity 移植。用户希望尽快并行开发，以免等待造成进度损失。

第二，当前大量技能仍是占位内容，后续必须由自己人工设计，因此需要把所有可手工配置内容独立出来，包括：

- 卡牌及其所有效果；
- 遗物；
- 神池；
- 调参面板中的参数；
- 文案、提示和引导。

用户还提出理想工具形态：一个可以直接编辑所有配置的“配置编辑器”。

真正的矛盾是：

- 过早全面移植，会把仍在变化的数据结构和临时规则复制到 Unity；
- 过晚移植，会浪费另一位开发者可以并行工作的时间；
- 先做大型编辑器，也可能在 schema 仍变化时反复返工；
- 等所有正式内容设计完再移植，又会把内容生产阻塞在工程前置上。

### 5.2 用户已经完成了初步任务分层

在请求建议之前，用户并非完全没有判断。他已经把后续事项分成两类：

**可以在 H5 或 Unity 阶段并行完成：**

- 优化交互手感；
- 完成正式文案；
- 优化提示与引导；
- 把文案和可调内容独立出来。

**困难、非必要、可以延后：**

- 不同卡牌融合数值词条；
- 更多怪物机制；
- 手动瞄准。

这体现了用户开始按“是否阻塞主线、是否影响底层契约、是否必须在迁移前完成”进行排序，而不是按功能吸引力排序。

### 5.3 关键重构：不是二选一，而是找到共同前置

同期分析将问题重新定义为：

> **哪些契约必须先稳定，稳定到什么程度后，Unity 与配置工具才能安全并行？**

由此产生“移植准入与配置契约固化”这一聚焦任务。它既不是全面重审全部代码，也不是立即重构所有内容，而是先固化跨引擎必须一致的部分：

- 核心更新顺序、时间、RNG、伤害和状态规则；
- 卡牌、神池、遗物、配方、敌人、波次、调参和文案键结构；
- 每个效果原子的合法参数、默认值、触发范围和结算语义；
- 固定 seed 与输入下的黄金回放基准。

这里形成了一个对项目管理非常关键的区分：

> **需要冻结的是昂贵的结构和接口，不是便宜的数值、文案和具体卡牌内容。**

这使“内容仍是占位”不再成为 Unity 开工的理由，只要 Unity 读取稳定 schema，数值和文案可以持续替换。

### 5.4 Unity 的正确启动方式：纵向切片

用户希望尽快让另一位开发者开工。同期方案没有简单回答“现在可以”或“还不可以”，而是定义了受控启动方式：

- 不做全部卡牌和全部系统的量产复制；
- 先读取同一套配置；
- 建立基础 GameState；
- 打通一种敌人、一次攻击、一次掉落、一次拾取、一次合成；
- 验证一张卡的装备态和消耗态；
- 验证一个触发器与状态效果；
- 将核心事件交给 Unity 表现层；
- 用 H5 黄金回放对比结果。

这种纵向切片的意义不是减少工作量，而是尽早验证：

- 跨语言数据是否真正一致；
- 核心规则是否足够明确；
- H5 是否能作为可执行规格；
- Unity 表现层与规则层边界是否成立。

### 5.5 配置工具的正确顺序：先管线，后编辑器

用户提出“配置编辑器”的目标非常合理，但同期方案对其做了重要收敛：

1. 先建立单一权威数据源；
2. 先建立 schema、引用和语义校验；
3. 先确保保存后能稳定生成运行时配置；
4. 再做表单式编辑器；
5. 节点图、批量平衡、曲线与模拟功能延后。

这一顺序避免了“编辑器看起来很完整，但写出的数据没有契约保障”的工具陷阱。

同时，配置权威源被设定为引擎无关的 JSON，而不是 Unity ScriptableObject。这是对项目现实的适配：

- H5 原型仍要继续使用；
- Unity 需要读取相同数据；
- AI Agent 更适合编辑和审查文本；
- Git 可以清晰追踪 JSON 差异；
- ScriptableObject 可作为 Unity 内部导入结果，而不是第二套真相。

### 5.6 仓库落地与连续执行

本轮讨论很快转化为连续提交：

- `docs/移植准入与配置契约固化_决策结论_v1.md` 明确记录“准入门后两线并行”和“先冻结接口、不冻结内容”；
- `ff1d1ce`“Solidify config contracts and golden replay pipeline”收敛效果原子参数、调参元数据、文案来源、配置校验和黄金回放；
- `8d36a77`“Deliver configuration editor v1”交付本地 Web 表单式编辑器，直接读取效果原子契约和调参元数据，并通过统一端点验证、保存配置。

这段仓库历史能够证明：用户的优先级问题最终没有停留在宏观建议，而是形成了决策文档、数据契约、验证基线和实际工具。

### 5.7 这一节点最值得展示的能力

从战斗策划求职角度，本轮最有价值的不是“我做了一个编辑器”，而是：

- 能识别内容设计、工程迁移和工具建设之间的依赖关系；
- 能区分哪些规则必须冻结、哪些数值可以持续迭代；
- 能为跨岗位协作定义可交付的接口和验收标准；
- 能控制过度工程化，先做最小可用管线和表单工具；
- 能把 AI Agent 纳入可审查、可回归、Git 友好的内容生产流程。

## 六、7 月 26 日 17:01：从“功能已实现”追问到“为什么玩家完全没有感知”

### 6.1 用户以试玩结果挑战工程结论

用户提出：照理当前版本已经实现卡牌进化，但自己亲自试玩时从未见到相关功能。这个问题的价值在于，用户没有把“代码里存在系统”当作完成证明，而是使用玩家经历进行反向审计。

他要求确认三件事：

1. 进化核心规则到底实现到什么程度；
2. 当前版本是否缺少提示和引导；
3. 当两张不同卡牌可以进化时，是否应有明确连线和文字，而且不能与普通合成特效混淆。

### 6.2 先消除术语歧义

代码调查发现项目同时存在两种“进化”：

- 同一卡牌通过普通二合升星，在 3★、5★选择分支并到 6★终态；
- 两张指定的不同 5★卡在波间组成配方，生成一张新的 6★卡。

用户这次真正质疑的是第二种“卡间配方进化”。区分这两个系统很重要，因为它们的材料、触发时机、操作路径和视觉语言都不同。

### 6.3 核心规则完成，但体验层未完成

代码审查表明，当时配方进化已经具有：

- 材料检测；
- 波间阶段限制；
- 精确消耗两张材料；
- 产物生成与放置；
- 波间确认界面；
- 遥测与规则测试。

但玩家侧只有极弱提示：

- 战斗中只显示“存在可进化配方：N”；
- 不说明是哪两张卡；
- 不说明会生成什么；
- 两张材料之间没有连线；
- 事件不弹 Toast；
- 材料卡详情不预告自己参与什么配方；
- 配方只能在波间主动确认，玩家可能直接结束整备。

因此用户没有看到功能，不是偶然，也不能简单归因于“触发概率低”。系统在规则层知道配方存在，但没有把这一事实转换为玩家可读、可定位、可操作的信息。

### 6.4 用户主动提出“不同机制必须有不同视觉语法”

用户明确要求进化连线与普通合成连线区分。这体现了比“加一个提示”更深的界面判断：

- 普通合成表示同类、同星级的常规成长；
- 卡间进化表示两张异类高星卡形成新产物；
- 两者的稀有度、结果和决策含义不同，因此必须具有不同的颜色、线型、动画、图标和文字。

这可以概括为：

> **视觉差异必须对应规则差异，而不是只为画面丰富。**

### 6.5 信息应在决策之前出现

调查还发现，当时配方说明主要出现在进化产物的详情里。玩家只有完成进化、获得产物后，才能看到它是由什么材料合成的。这形成信息倒置。

用户要求的思路意味着正确顺序应为：

- 材料卡从低星时就能预览未来配方；
- 凑齐材料后明确提示搭档和产物；
- 战斗中用专用连线定位两张材料；
- 波间提供清晰确认界面；
- 完成后再用结果反馈强化记忆。

这是一条完整的“预告—就绪—操作—结果”信息链。

### 6.6 仓库落地

同日提交 `5541afa`“Improve recipe evolution discoverability”加入：

- `.recipe-hints` 等独立进化提示层；
- 与普通白色虚线不同的专用连线、光效和核心图标；
- 逐条显示材料、星级、产物与“波间可确认”的完整文字；
- 首次配方就绪提示；
- 材料卡详情反向显示搭档与产物；
- 6 条配方覆盖与专用测试。

提交还明确限制：本任务只补表现和引导，不改变配方判定、材料、产物和数值。这种范围控制说明用户的问题被准确定位为可发现性缺陷，而不是借机重做核心规则。

### 6.7 本轮形成的功能验收标准

这一节点可以归纳出一套很适合作品集展示的完成标准：

1. **规则存在**：系统能检测、结算并生成结果；
2. **触发可达**：正常对局中有现实机会达成条件；
3. **状态可见**：玩家知道自己接近或已经满足条件；
4. **对象可定位**：玩家知道具体是哪两张卡；
5. **结果可预期**：玩家知道会生成什么；
6. **操作可理解**：玩家知道何时、在哪里完成；
7. **视觉可辨认**：不同规则不共用令人混淆的提示；
8. **结果有反馈**：玩家能确认操作已经成功。

这比“单元测试通过”更接近游戏设计意义上的功能完成。

## 七、三次讨论之间的统一逻辑

阶段七的三个主题表面不同：卡牌详情、Unity/配置工具、进化提示。实际上它们都在解决同一个问题：

> **内部系统已经变复杂，但复杂性尚未被转换为稳定的玩家语言、策划语言和协作语言。**

三次讨论分别建立了三种“翻译层”：

### 1. 规则到玩家的翻译

- 技能配置 → 精确效果说明；
- 高星分支 → 技能树和构筑意图；
- 配方状态 → 专用连线、文字和阶段提示。

### 2. 规则到策划的翻译

- 松散 JSON → 有 schema、默认值和语义校验的配置契约；
- 手改嵌套数据 → 表单式配置编辑器；
- 散落文案 → 可统一管理的文本键。

### 3. 规则到协作者的翻译

- H5 代码实现 → 核心规则规格；
- 当前运行结果 → 黄金回放基准；
- 全量迁移目标 → 可验收的 Unity 纵向切片。

因此，本阶段真正建立的是一条完整的生产闭环：

> **规则定义 → 配置契约 → 工具编辑 → 游戏解释 → 玩家反馈 → 试玩审查 → 再次修正规则或表现。**

## 八、本阶段体现的个人设计方法

### 8.1 从表面症状追到结构原因

- “文字太多”被重新定义为信息层级错误；
- “Unity 什么时候开始”被重新定义为跨引擎契约的准入问题；
- “进化没见到”被重新定义为功能可发现性和信息链缺失。

### 8.2 坚持以玩家侧完成标准验收

用户多次拒绝把以下事实当作完成：

- JSON 中存在技能；
- 测试能执行技能；
- 代码能检测配方；
- 波间有一个确认面板。

他关心的是玩家是否能读懂、看到、区分和使用。这延续了项目此前“规则实现不等于玩家交付”的方法，但在本阶段扩展到复杂构筑和配方系统。

### 8.3 对内容、结构和表现进行成本分级

本阶段开始明确：

- schema、原子参数、事件边界和时间/RNG 语义改动昂贵，应先稳定；
- 数值、文案、提示和具体卡牌内容改动便宜，可以持续迭代；
- 交互与表现可在不改核心规则的前提下并行优化；
- 手动瞄准、更多怪物、融合词条等高风险扩展应延后。

### 8.4 先建立单一事实来源，再建立工具

用户提出配置编辑器，但最终路线没有让工具反过来定义数据，而是让编辑器读取统一契约。这种顺序对 AI 辅助开发尤其重要：Agent 可以批量生成和修改配置，但必须经过同一套 schema、引用和语义校验。

### 8.5 通过视觉语言表达规则层级

普通合成与卡间进化必须使用不同提示；主卡面、详情页和分支弹窗承担不同信息；说明文字不是附属包装，而是战斗系统的一部分。

### 8.6 主动控制范围，避免借题扩张

在进化提示修复中，仓库任务明确不改配方规则和数值；在 Unity 规划中，先做纵向切片；在配置编辑器中，先做表单而非节点图；融合词条等功能只预留结构位，不立即实现。

这种范围控制是本阶段重要的项目管理能力。

### 案例 B：H5 原型到 Unity 的配置与规则交付

## 十、可用于简历的精炼条目

## 十一、面试叙述提纲

### 问题 1：你如何处理复杂战斗系统的信息量？

可回答：

> ProjectVL 扩展到多星级、多分支和随机词条后，我发现一个反常现象：卡牌文字已经多到把战场挤坏，但玩家依然不知道技能具体怎么生效。问题不是文案不够，而是高频操作信息和低频学习信息混在同一层。我把主卡面固定为名称、图标、星级和两行词条，点击后暂停进入详情页，读取真实技能配置展示装备态、消耗态、词条解释和完整技能树；分支选择页再额外说明构筑意图。这样内容复杂度可以继续增长，但战斗操作区不会继续膨胀。

### 问题 2：你如何判断一个功能是否真正完成？

可回答：

> 卡间进化在代码里已经有材料检测、波间确认和产物生成，自动测试也覆盖了规则，但我实际试玩时从未意识到它存在。我没有直接要求重写规则，而是先审查触发链，发现战斗中只显示“存在可进化配方：1”，不告诉玩家是哪两张卡、会变成什么，也没有连线。于是我把完成标准从“能结算”扩展为“可达、可见、可定位、可预期、可操作、可辨认”，增加与普通合成完全不同的进化连线、完整文字和材料卡前置配方说明。

### 问题 3：你如何安排原型移植和内容生产？

可回答：

> 当时另一位开发者准备开始 Unity，但技能和文案仍有大量占位。我没有等内容全部定稿，也没有让 Unity 直接全面复制，而是先区分昂贵结构和便宜内容：冻结效果原子、配置 schema、事件边界和时间/RNG 语义，数值与文案继续放在 JSON 中迭代。Unity 先做一条纵向切片，用 H5 固定 seed 的黄金回放做对照；我这边并行完成配置校验和表单编辑器。这样工程不被内容阻塞，内容也不被引擎绑定。

## 十二、证据边界与尚未解决的问题

### 12.1 信息架构已落地，不等于所有文案已经成熟

详情系统能够自动解释配置，但当时大量技能本身仍是占位内容。自动生成只能保证“配置写了什么就展示什么”，不能保证每个分支有足够设计差异、强度合理或表述已完成最终润色。

### 12.2 配置契约与编辑器证明了生产能力，不证明游戏内容质量

配置工具可以降低错误、支持协作和批量维护，但无法替代战斗设计判断。卡牌、遗物、神池和配方仍需人工设计、试玩和数值验证。

### 12.3 进化可发现性已有工程修复，但缺少行为数据

仓库能证明专用连线、文字和详情预告已经加入，但目前材料中没有前后对照数据，例如：

- 玩家首次发现配方的波次；
- 达成配方后完成进化的比例；
- 是否仍会误把进化线当普通合成；
- 材料卡详情是否真的被玩家查看。

作品集中应把它表述为“完成可发现性重构并建立验收项”，而不是“已经证明提示最优”。

### 12.4 Unity 准入方案的价值主要是可交接性

本阶段可以证明用户定义了跨引擎契约和纵向切片方法，并推动了配置固化与黄金回放；Unity 最终是否完整复刻、性能和触控体验如何，应由后续仓库和协作者成果单独证明。

## 十三、对第七阶段的最终评价

第七阶段最重要的变化，是用户开始系统性审查“内部完成”和“外部交付”之间的所有接口。

在玩家侧，他发现：

- 技能存在不等于玩家理解；
- 配方可结算不等于玩家发现；
- 文字更多不等于信息更充分；
- 不同规则必须有不同视觉语言。

在策划侧，他发现：

- 数据驱动不等于数据可安全维护；
- 配置编辑器不能建立在松散 schema 上；
- 文案、调参、卡牌和遗物必须有明确单一来源。

在协作侧，他发现：

- “代码看起来稳定”不足以支持移植；
- 必须定义契约、准入条件、纵向切片和客观回放基准；
- 需要冻结的是跨引擎接口，而不是所有仍在迭代的内容。

因此，这一阶段可以概括为：

> **从构建复杂战斗系统，转向构建让玩家能理解、让策划能生产、让协作者能复刻的完整交付体系。**

从求职展示角度，它能够证明用户不仅会提出技能和构筑机制，也能处理战斗信息、内容生产、工具边界、跨引擎协作和功能验收。相比单纯展示“做了多少张卡”，这一阶段更能体现中高级战斗策划所需要的系统收束能力。
