## 二、当前问题的代码根因

### 1. 卡牌和卡槽没有真正固定高度

当前手牌卡槽只有 `min-height:72px`，装备槽使用 `height:auto; min-height:88px`；卡牌本身也只有 `min-height`，没有固定 `height` 和内容裁切。

与此同时，`slotFactory.ts` 把以下内容全部放进了主卡面：

- 技能名和图标；
    
- 星级；
    
- 已选进化路线；
    
- 待选择提示；
    
- 技能效果描述；
    
- 全部随机词条。
    

因此，文本一旦增加，卡牌就会自动变高，整个 Dock 也随之变高。

### 2. 整个外层布局建立在“Dock 大约固定为 345px”的隐含假设上

`.game-shell` 的宽度计算直接减去了 `345px`，但实际 Dock 使用的是多个 `auto` 行，卡牌内容又允许继续增长。外层还设置了 `overflow:hidden`。这意味着内容增长后，布局不会正常扩容，而会压缩或裁切本应属于战场的空间。

### 3. 装备融合信息也被直接追加到卡面

`renderEquipment.ts` 会向装备卡牌内部追加一条融合说明，而且使用行内样式。这会进一步改变卡牌高度。

### 4. 当前文案基本是占位符

现在卡牌主描述使用的是：

- “连环闪电的即时释放”
    
- “连环闪电强化释放”
    
- “连环闪电终极释放”
    
- “连环闪电分支成形”
    

这些文字没有告诉玩家实际机制。

进化分支描述也普遍只是：

- “长链分支。”
    
- “高压分支。”
    
- “感电分支。”
    

因此，这不是单纯的 UI 容量问题，而是当前展示层没有读取和解释真实技能配置。

### 5. 点击卡牌目前没有行为

输入系统已经能可靠地区分点击和拖拽：

- 位移、时长低于阈值才算点击；
    
- 拖拽结束后会抑制浏览器随后生成的 `click`；
    
- 但卡牌没有注册点击后的详情行为。
    

当前卡牌如果没有进入拖拽，`pointerRouter` 最终会直接返回。

这意味着现有输入设施已经足够，只需接入卡牌点击事件，不需要重做拖拽系统。

### 6. 旧版本确实采用了固定卡面

旧单文件版本中：

- 卡槽固定为 `58px`；
    
- 卡牌固定为 `58px`；
    
- 主界面只显示名称、星级和一句极短说明。
    

所以你的判断是正确的：应恢复“固定卡面”，但在此基础上增加新的二级详情菜单。

## 4. 在 `src/game.ts` 中增加可靠的暂停原因管理

不建议在打开详情时简单执行：

```ts
state.paused = true;
```

然后关闭时直接：

```ts
state.paused = false;
```

这样会破坏“玩家原本已经手动暂停”的状态。

建议把手动暂停和详情暂停分开：

```ts
let manualPaused = false;
const uiPauseReasons = new Set<'cardDetail'>();

function syncPauseState(): void {
  state.paused = manualPaused || uiPauseReasons.size > 0;
}

function openCardDetail(): void {
  uiPauseReasons.add('cardDetail');
  syncPauseState();
}

function closeCardDetail(): void {
  uiPauseReasons.delete('cardDetail');
  syncPauseState();
}

function togglePause(): void {
  if (state.mode !== 'playing'
      || state.intermission.active
      || state.decisions.current) {
    return;
  }

  manualPaused = !manualPaused;
  syncPauseState();
  syncPauseButton();
}
```

这样可以保证：

- 正常战斗中打开详情：暂停；
    
- 波间倒计时中打开详情：倒计时也暂停；
    
- 玩家本来手动暂停：关闭详情后仍保持暂停；
    
- 关闭普通详情不会影响决策弹窗的暂停；
    
- 重开游戏时统一清空暂停原因。
    

核心循环目前已经在 `state.paused`、当前决策或待决队列存在时停止推进，所以不需要修改战斗系统。

### 1. 核心分层是目前最有价值的资产

当前工程明确规定：

### 2. 技能体系已经是数据驱动，但尚未达到真正安全的跨语言契约

当前技能采用：

- 9 种触发器；
    
- 33 种效果原子；
    
- JSON 卡牌定义；
    
- 通用解释器；
    
- 3、5、6 星锚点；
    
- 进化分支和公共节点；
    
- 消耗态效果；
    
- 词条池。
    

这是很好的基础。

但当前最重要的技术风险在这里：

```ts
export interface EffectDef {
  atom: AtomName;
  params?: Record<string, unknown>;
}
```

也就是说，效果类型是明确的，但参数仍是任意键值对象。

例如 `chain`、`shield`、`summon`、`groundZone` 各自允许什么参数，主要依赖：

- 文档里的参数说明；
    
- 手工校验器；
    
- 运行时代码中的字符串键；
    
- 运行时默认值。

- 参数名称不一致；
    
- 默认值不一致；
    
- 整数和浮点类型不一致；
    
- 缺字段时一个引擎报错、另一个静默回退；
    
- 新增原子后只改了一边。
    

因此，**必须先把“效果原子参数”从松散字典升级成正式的数据契约**。

## 五、“配置编辑器”应该怎样做

### 1. 不要把 Unity ScriptableObject 当成唯一配置源

ScriptableObject 很适合成为 Unity 编辑器内的数据资产和运行时缓存，但不适合作为 ProjectVL 的唯一权威源。

原因是：

- 你仍要保留 H5 原型；
    
- AI Agent 更适合读写文本；
    
- Git 对 JSON/YAML 的 diff 更清楚；
    
- H5 与 Unity 若各保存一套配置，会迅速分叉；
    
- ScriptableObject 主要作为 Unity Editor 中的资产使用，构建后的应用可以读取它，但不能像普通外部配置一样直接保存修改。([Unity 文档](https://docs.unity3d.com/6000.1/Documentation/Manual/class-ScriptableObject.html?utm_source=chatgpt.com "Unity - Manual: ScriptableObject"))
    

建议采用：

> **JSON/JSON Schema 是权威源；TypeScript、C# 类型和 Unity 资产由它生成或导入。**

ScriptableObject 可以作为 Unity 内部生成物，而不是人工维护的第二套真相。

### 2. 采用“创作格式”和“运行格式”分离

创作格式应便于人和 AI 编辑：

```text
content/
  schemas/
    card.schema.json
    effect.schema.json
    relic.schema.json
    god.schema.json
    text.schema.json

  cards/
    storm/
      chainLightning.json
      pierce.json
    winter/
      frost.json

  gods/
    storm.json
    winter.json

  relics/
    storm/
    winter/
    neutral/

  recipes/
  enemies/
  waves/
  tuning/

  locales/
    zh-CN/
      cards.json
      relics.json
      ui.json
      tutorial.json
```

构建时再生成：

```text
generated/
  web/content.bundle.json
  web/content-types.ts
  unity/ContentModels.cs
  unity/content.bundle.json
```

这样可以避免当前 `skills.json` 集中容纳所有卡牌、分支、词条和消耗效果的维护压力。

### 3. 需要一个“内容编译器”，而不仅是编辑器

配置编辑器只是表面 UI，真正重要的是后面的编译管线：

```text
策划配置
  ↓
Schema 校验
  ↓
跨引用校验
  ↓
语义校验
  ↓
生成运行时 Bundle
  ↓
生成 TypeScript / C# 类型
  ↓
执行冒烟与一致性测试
```

JSON Schema 本身适合声明 JSON 的类型、字段、约束和结构，并能作为不同工具之间的共同契约。([json-schema.org](https://json-schema.org/docs?utm_source=chatgpt.com "Welcome"))

还需要额外的语义校验，例如：

- 神池引用的卡牌必须存在；
    
- 配方产物必须存在；
    
- `textKey` 必须存在；
    
- 词条必须有实际结算落点；
    
- 原子参数必须适用于当前触发器；
    
- 进化节点不能形成无效组合；
    
- 最小词条值必须产生可观察变化；
    
- 所有 ID 全局唯一；
    
- 删除或重命名配置时检查引用。
    

当前 `AFFIX_SINKS` 已经是这类“语义契约”的良好开端。

### 4. 配置编辑器首先做表单，不要先做节点图

你理想中的编辑器可以实现，但第一版不应追求类似 Unreal Blueprint 的复杂节点系统。

当前技能模型本质上是：

```text
卡牌
  ├─ 星级
  ├─ 进化分支
  ├─ 触发器
  │   └─ 效果原子
  │       └─ 参数
  ├─ 消耗态
  └─ 词条池
```

它更适合：

- 左侧实体列表；
    
- 中间结构化表单；
    
- 右侧校验、预览和说明；
    
- 可折叠的触发器与效果树；
    
- 表格化星级对比。
    

配置编辑器 v1 应当包括：

1. 搜索、筛选和分类；
    
2. 新建、复制、重命名和删除；
    
3. 根据原子类型自动显示合法参数；
    
4. 参数范围和单位提示；
    
5. 引用下拉选择；
    
6. 即时错误提示；
    
7. 变更 diff；
    
8. H5 实时预览；
    
9. 导出、保存和 Git 友好格式化；
    
10. 一键执行校验和测试。
    

批量平衡表、曲线图、节点图和模拟器可以后续再加。

### 5. 建议编辑器采用独立 Web 工具

你们已经使用 TypeScript、Vite 和 JSON，最合适的个人开发方案是：

```text
tools/content-editor/
```

建立独立的本地 Web 编辑器。

优点：

- H5 与 Unity 都能使用；
    
- AI Agent 容易操作；
    
- 可以直接读写 Git 内 JSON；
    
- 表格、搜索、批量修改更容易实现；
    
- 不会把策划工作绑定到 Unity 安装环境；
    
- 未来仍可添加 Unity 内部入口。
    

Unity 侧可以另做一个较轻的 UI Toolkit `EditorWindow`，负责：

- 导入配置；
    
- 显示校验结果；
    
- 定位资源；
    
- 启动配置编辑器；
    
- 重新生成 ScriptableObject；
    
- 运行 Unity 预览。
    

Unity 官方目前建议使用 UI Toolkit 扩展编辑器，它比旧式 IMGUI 更适合构建规模较大的现代编辑工具。([Unity 文档](https://docs.unity3d.com/cn/current/Manual/editor-EditorWindows.html?utm_source=chatgpt.com "Unity - 手册: 使用 IMGUI 创建自定义Editor窗口"))

H5 面板、Web 配置编辑器和 Unity 调参面板都读取同一份元数据。

- `textKey`；
    
- `title`；

这会产生两套文案来源。

正式方案应为：

```json
{
  "id": "proj_damage",
  "nameKey": "relic.proj_damage.name",
  "descriptionKey": "relic.proj_damage.description",
  "effects": [...]
}
```

文案统一放入本地化表。Unity Localization 原生支持 String Table 和本地化字符串资源，可由同一套外部文案表导入。([Unity 文档](https://docs.unity3d.com/ja/current/Manual/com.unity.localization.html?utm_source=chatgpt.com "Unity - マニュアル: Localization"))

## 二、卡间进化的实际实现状态

### 1. 材料检测：已实现

系统会同时检查：

- 手牌；
    
- 装备栏；
    
- 卡牌类型；
    
- 星级是否达到最低要求；
    
- 是否为正在等待分支选择的临时卡。
    

符合条件时，`availableRecipes()` 会返回可执行配方和两张具体材料卡牌的实例ID。材料选择优先使用较低星级卡，并优先使用手牌，避免无必要地消耗更高星卡或已装备卡。

### 2. 波间限制：已实现

实际确认进化时，系统会再次检查：

- 当前是否处于波间；
    
- 两张材料是否仍然存在；
    
- 类型和星级是否仍然符合；
    
- 两张材料是否为不同实例；
    
- 是否有位置放置进化产物。
    

不在波间时会返回“卡间进化只能在波间完成”。

### 3. 材料消耗和产物生成：已实现

确认后会：

1. 精确删除选中的两张材料；
    
2. 创建对应6★配方卡；
    
3. 优先放入空手牌槽；
    
4. 如果手牌已满，则使用材料A原来的位置；
    
5. 记录已完成配方；
    
6. 触发合成事件和装备被动重新计算。
    

### 4. 波间操作界面：已实现

当波间进入自由整备阶段，且存在可进化配方时，会出现配方面板：

> 5★材料A ＋ 5★材料B → 6★产物

并提供“确认进化”按钮。

如果材料在装备栏内，玩家还必须勾选“消耗已装备的某卡”；点击后还会再次弹出浏览器确认框。这个安全确认逻辑是合理的。

### 5. 测试：核心路径有覆盖

专门的测试覆盖了：

- 星级不足时不可进化；
    
- 战斗阶段不可进化；
    
- 精确消耗两张材料；
    
- 手牌满时的产物放置；
    
- 装备卡需要明确勾选；
    
- 产物可以正常装备、消耗；
    
- 配方产物不会进入普通随机掉落池；
    
- 遥测记录；
    
- 战斗中出现文字提示。
    

因此，**从代码结构判断，这不是占位接口，而是一套已经接入主流程的真实功能。**

## 三、为什么你在试玩中没有见到

主要有五个原因。

### 原因1：触发门槛较高

当前为二合规则，正常掉落主要是1★。

纯靠1★卡合成时：

- 1张5★卡需要16张同类型1★卡；
    
- 两张指定5★材料合计需要32张1★等价材料。
    

虽然Boss高星奖励和万能卡可以降低实际成本，但正常随机构筑中仍然属于明显的后期条件。

### 原因2：不是任意两张不同卡都能进化

必须恰好是6组固定配方之一。

同时，一局只选择一主神、两副神；本局名册和每波活跃池都受到神池选择限制，活跃池最多7张。因此，某些配方材料可能根本没有进入本局名册，或者只在部分波次进入活跃池。

### 原因3：只能在波间主动确认

即使战斗中已经凑齐材料，也不会自动进化，也不能直接拖动两张卡完成进化。

玩家必须：

1. 等到当前波结束；
    
2. 完成神池、成长等奖励决策；
    
3. 进入自由整备阶段；
    
4. 在配方面板中主动点击确认。
    

如果玩家习惯迅速点击“准备完成”，就会直接跳过这次机会。当前“准备完成”按钮不会因为存在可进化配方而阻止玩家，也不会二次警告。

### 原因4：战斗中只有一条很弱的文字

当前检测到配方后，仅在卡牌区域上方显示：

> 存在可进化配方：1

没有写：

- 哪两张卡可以进化；
    
- 会进化成什么；
    
- 需要等待波间；
    
- 应当如何操作。
    

更关键的是，代码没有在两张材料之间画任何进化连线。

这个提示的CSS只是一个小型胶囊文字，字号为10px，不具备强提醒性质。

### 原因5：系统故意不弹Toast

进入波间且存在配方时，核心层会产生 `recipeAvailable` 事件，但UI明确把这个事件翻译为 `null`，也就是：

- 不弹Toast；
    
- 不弹Banner；
    
- 不播放明显提示；
    
- 只依靠配方面板和那条小文字。

## 五、配方详情存在一个“信息倒置”问题

卡牌详情界面确实支持显示：

> 材料A ≥5★ + 材料B ≥5★ → 产物6★

但这段说明只会显示在 `recipeOnly` 的进化产物卡详情中。也就是说：

1. 玩家必须先完成进化；
    
2. 获得产物；
    
3. 点击产物详情；
    
4. 才能看到这张卡原本是怎么进化出来的。
    

这不能帮助玩家在进化前理解配方。

当前材料卡的详情页面不会告诉玩家：

- “这是某个进化配方的材料”；
    
- “需要与哪张卡组合”；
    
- “最低需要几星”；
    
- “会产生什么结果”。
    

这是目前引导缺失中最根本的一项。

## 六、建议的正确提示方案

### 战斗中的普通合成

保留现有表现：

- 白色虚线；
    
- 小白点；
    
- 轻微流动；
    
- 表示“同类型同星级可以普通合成”。
    

### 战斗中的卡间进化

应创建完全独立的视觉层，不能复用普通合成线：

- 使用青蓝—紫色渐变实线或双线；
    
- 线宽明显更粗；
    
- 中央放置菱形、星核或“进化”图标；
    
- 粒子从两端向中央汇聚；
    
- 两张材料卡增加独立的 `recipe-ready` 外框脉冲；
    
- 不使用普通合成的白色虚线动画。
    

文字应明确显示完整信息，例如：

> **卡间进化已就绪**  
> 连锁闪电 5★ + 冰霜 5★ → 冻雷 6★  
> 波间阶段可确认进化

若同时有多个配方，应逐组显示，而不是只写“存在2个配方”。

### 首次凑齐时

应至少出现一次明显Banner或Toast：

> 已凑齐卡间进化材料，当前波结束后可完成进化。

当前 `recipeAvailable` 事件已经存在，只需要让表现层真正消费这个事件，不必改动核心规则。

### 波间阶段

配方面板应成为最高优先级整备信息。

当存在可进化配方时，“准备完成”应改为以下两种方案之一：

1. 按钮显示“仍有可进化配方”，点击后要求确认跳过；
    
2. 显示两个明确按钮：“完成进化”和“跳过进化”。
    

不应允许玩家在没有任何提示的情况下直接错过。

### 卡牌详情

所有作为配方材料的卡都应增加“卡间进化”区域，例如：

> **进化配方**  
> 本卡达到5★后，可与冰霜5★在波间进化为冻雷6★。

这段信息应在1★时就可见，而不是等玩家获得产物之后才出现。
