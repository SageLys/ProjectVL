是的，**“随着解锁内容增加，随机池越来越稀释”几乎是所有肉鸽构筑游戏都会遇到的问题**。但要修正一点：

> 肉鸽设计并不追求消灭卡池稀释，而是要把稀释控制在“迫使玩家适应”与“让玩家无法构筑”之间。

真正需要权衡的不是“总共有多少张卡”，而是：

> 玩家在一局中，有多大概率看到对当前构筑有意义的东西。

《杀戮尖塔》每个角色拥有独立卡池，战斗后通常从三张随机卡中选择一张，而且可以跳过；商店还允许删除牌。开发者也曾表示，每个角色约75张可用牌是他们认为相对合适的平衡，再继续扩大就可能令构筑变得过于偶然。([维基百科](https://en.wikipedia.org/wiki/Slay_the_Spire?utm_source=chatgpt.com "Slay the Spire"))

《哈迪斯》虽然有大量祝福，但每次通常从某位神的三个祝福中选择；“神的主题”天然把总池拆成了多个局部池。([维基百科](https://en.wikipedia.org/wiki/Hades_%28video_game%29?utm_source=chatgpt.com "Hades (video game)"))

《吸血鬼幸存者》则使用三至四选一、六武器槽和六被动槽；获得物品后，后续升级会继续出现已有物品，因此总内容池很大，但实际运行中的有效选择池会逐渐收缩。([维基百科](https://en.wikipedia.org/wiki/Vampire_Survivors?utm_source=chatgpt.com "Vampire Survivors"))

所以行业里的通用做法不是简单保持小池，而是管理**有效卡池**。

# 一、先区分三种“卡池”

讨论肉鸽卡池时，必须区分三个概念。

## 1. 总内容池

游戏里总共有多少张卡、多少武器、多少祝福。

例如正式版有11种卡。

它主要决定：

- 长期内容丰富度；
    
- 局与局之间的差异；
    
- 解锁和收集价值；
    
- 玩家能探索多少种构筑。
    

总内容池大，通常是好事。

## 2. 单局可出现池

本局理论上能够出现哪些卡。

例如：

- 总卡池11种；
    
- 角色限定后剩8种；
    
- 本局初始武器进一步限定后剩6种。
    

这个数比总内容池更重要。

## 3. 当前有效池

玩家在当前时刻真正愿意拿的卡。

假设本局可出现11种，但玩家当前只有以下需求：

- 已持有的3种卡；
    
- 1种能补足控制能力的新卡；
    
- 1种通用强卡。
    

那么当前有效池大约只有5种。

肉鸽卡池设计的核心不是控制总池，而是控制：

> 有效卡在当前随机结果中所占的比例。

# 二、卡池权衡的五组基本矛盾

## 1. 内容丰富度与构筑稳定性

池越大：

- 局与局越不同；
    
- 玩家越可能发现意外组合；
    
- 长期重复游玩越丰富。
    

但池越大：

- 指定卡更难出现；
    
- 套路更难完成；
    
- 新手更难理解系统；
    
- 玩家容易感觉“系统不让我玩想玩的东西”。
    

所以大池负责提供多样性，小型有效池负责提供可控性。

## 2. 适应随机与表达意图

随机性太弱时，玩家每局都可以复制同一套最优构筑。

随机性太强时，玩家根本没有构筑，只是在接受系统发下来的东西。

理想状态是：

> 玩家不能精确指定最终构筑，但可以不断把概率推向自己想要的方向。

也就是：

- 不能保证获得某张具体卡；
    
- 但可以选择某一类卡；
    
- 可以提高某个标签的出现权重；
    
- 可以排除不需要的卡；
    
- 可以准备两个或三个备用方向。
    

## 3. 前期探索与后期收束

前期需要让玩家探索：

- 看到不同方向；
    
- 尝试新卡；
    
- 根据随机结果决定构筑。
    

后期则需要逐渐收束：

- 已有构筑更频繁出现；
    
- 升级和进化更容易完成；
    
- 不再频繁塞入全新的基础方向。
    

因此很多优秀肉鸽实际上采用的是：

> 前期宽池探索，后期窄池强化。

如果整个流程始终保持完全均匀随机，后期通常会变得非常挫败。

## 4. 槽位压力与操作摩擦

有限槽位可以产生有意义的取舍：

- 是否放弃旧卡；
    
- 是否转型；
    
- 是否为了未来组合暂时保留弱卡。
    

但如果槽位压力过强，玩家就不是在构筑，而是在处理垃圾。

判断标准不是“玩家有没有丢卡”，而是：

> 丢卡行为是否反映了构筑决策，还是只是在清理随机造成的堵塞。

## 5. 元进度奖励与卡池污染

解锁新卡通常被包装成奖励，但它可能在数学上降低已有构筑的稳定性。

这是典型的“负向解锁”：

- 玩家获得了更多内容；
    
- 却更难抽到真正想要的东西；
    
- 总体胜率甚至下降。
    

因此解锁卡牌不能只考虑“新不新”，还要考虑它加入随机池后是否污染既有系统。

# 三、衡量卡池不能只看卡牌数量

最基本的变量有六个：

|变量|含义|
|---|---|
|(N)|当前可出现的卡牌种类|
|(V)|当前对玩家有价值的卡牌种类|
|(K)|每次展示几个选项|
|(T)|一局提供多少次选择机会|
|(C)|玩家能同时容纳多少卡|
|(Q)|完成构筑需要多少张目标卡或多少次重复|

## 1. 有效选项命中率

假设当前池中有 (N) 种卡，其中 (V) 种对玩家有用，每次展示 (K) 个不重复选项。

至少出现一个有效选项的概率约为：

[  
P(\text{有效选择}) =  
1-\frac{\binom{N-V}{K}}{\binom{N}{K}}  
]

例如：

- 可出现池11种；
    
- 当前有3种卡有用；
    
- 每次三选一。
    

则至少看到一个有效选项的概率约为66%。

如果不是三选一，而是像你们当前这样一次只掉一张：

[  
P = \frac{3}{11} \approx 27.3%  
]

这就是为什么“11种池、单张掉落”和“11种池、三选一”完全不是同一种随机强度。

## 2. 重复卡需求

假设目标卡均匀占卡池的 (1/N)，经历 (T) 次掉落，那么目标卡的期望数量是：

[  
E(\text{目标卡数量})=\frac{T}{N}  
]

如果构筑要求32张同型1★合成一张6★，理论平均掉落需求约为：

[  
32N  
]

- 5种池：约160次；
    
- 11种池：约352次。
    

这还只是数学期望，没有考虑槽位堵塞、错过拾取、不同星级和培养多个方向。

因此：

> 越依赖同名重复，系统对卡池扩张越敏感。

## 3. 需要看方差，而不只是平均值

平均获得8张目标卡，不代表玩家通常都能获得8张。

实际会出现：

- 有人获得14张；
    
- 有人只有3张；
    
- 极端倒霉局几乎看不到目标卡。
    

因此高重复需求系统必须做随机模拟，而不能只用平均值判断。

# 四、不同肉鸽系统对卡池扩张的敏感度不同

不是所有肉鸽都同样怕大池。

## 低敏感系统

特征：

- 每张卡拿到后立即完整生效；
    
- 不依赖重复；
    
- 大部分卡有独立价值；
    
- 玩家可以跳过；
    
- 每次有多个选择；
    
- 牌库没有严格容量上限。
    

典型是部分卡牌肉鸽。

池可以相对大，因为拿到一张就能产生价值。

## 中敏感系统

特征：

- 有固定装备槽；
    
- 已有物品可以继续升级；
    
- 新物品与升级物品共享选择池；
    
- 有重抽、排除、锁定等工具。
    

典型是幸存者类。

它们一般在玩家填满武器槽后，自动停止继续引入新武器，随机池随之收缩。

## 高敏感系统

特征：

- 必须获得相同种类才能升级；
    
- 槽位非常少；
    
- 每次只出现一个随机结果；
    
- 不需要的卡仍会占用空间；
    
- 没有跳过、重抽、分解或转换机制。
    

你们目前的系统接近这一类。

它同时具备：

1. 同种卡二合；
    
2. 高星需要大量重复；
    
3. 只有7槽；
    
4. 每次获得单张卡；
    
5. 卡牌还承担一次性使用与装备等多种用途。
    

因此，ProjectVL面对的卡池稀释问题，比《杀戮尖塔》一类传统卡牌肉鸽更严重。

仓库中的当前原型确实仍以5种教学占位卡运行，并预留后续正式替换。

# 五、肉鸽控制卡池的通用方法

这些方法通常不是单独使用，而是组合使用。

## 方法一：拆分总卡池

不要让所有内容进入同一个随机池。

常见拆分方式：

- 按角色；
    
- 按职业；
    
- 按武器；
    
- 按流派；
    
- 按阵营；
    
- 按关卡区域；
    
- 按玩家开局选择；
    
- 按本局获得的核心道具。
    

例如游戏有60张卡，但玩家选择某个角色后，实际只有25张可出现。

这种方法的优势是：

- 规则清晰；
    
- 容易平衡；
    
- 不需要暗中操控概率；
    
- 不同角色天然产生重复游玩价值。
    

缺点是单局跨流派组合可能减少。

## 方法二：分阶段开放卡池

不要从第一分钟开始就让全部卡牌出现。

例如：

- 第一阶段只出现基础卡；
    
- 第二阶段加入构筑方向；
    
- 第三阶段加入进化和终局卡；
    
- 后期不再出现新的低级基础方向。
    

这解决两个问题：

1. 新手不会一开始面对过多概念；
    
2. 后期不会因为新卡不断进入而无法完成已有构筑。
    

这种方法尤其适合单局较短的游戏。

## 方法三：根据当前构筑动态加权

当玩家拿到某个标签后，提高同标签卡牌的出现概率。

例如玩家已经持有：

- 两张投射物卡；
    
- 一张暴击卡；
    
- 一张控制卡。
    

之后随机权重可以变成：

- 60%来自已有构筑标签；
    
- 25%来自通用卡；
    
- 15%来自新方向。
    

这样仍然有随机性，但不会完全均匀。

关键是不要把它做成百分之百锁定，否则玩家一旦早期拿错一张卡，系统就会不断强化错误方向。

比较合理的是：

> 软性倾斜，而不是硬性锁定。

## 方法四：扩大每次选择宽度

同样是11种卡池：

- 每次掉一张，玩家几乎没有控制；
    
- 二选一，控制力明显提高；
    
- 三选一，可以支持较大的池；
    
- 五选一，系统会越来越接近定向选择。
    

扩大选项数是最直接的控制随机方法。

但选项越多：

- 决策时间越长；
    
- 信息负担越高；
    
- 即时节奏越容易被打断。
    

对你们这种强调即时反应的游戏，不能频繁弹出复杂三选一。因此可以把多选留给：

- 波间；
    
- Boss奖励；
    
- 升级节点；
    
- 构筑转折点。
    

普通战斗掉落仍保持快速操作。

## 方法五：允许跳过

“不要任何一张”必须是一种合法选择。

如果玩家不能跳过，每次奖励实际上都是强制污染。

跳过可以获得：

- 少量金币；
    
- 经验；
    
- 万能碎片；
    
- 下一次重抽资源；
    
- 短期战斗增益。
    

这样玩家不会觉得“没拿牌就是浪费奖励”。

## 方法六：重抽、排除、锁定

三种工具承担不同作用。

### 重抽

解决单次坏运气。

适合：

- 临时修正；
    
- 资源消耗；
    
- 不永久改变池。
    

### 排除或封印

解决长期池污染。

适合：

- 玩家明确知道某张卡本局绝对不需要；
    
- 减少后续无意义出现；
    
- 强化构筑承诺。
    

### 锁定或冻结

解决“现在买不起，但之后想要”。

适合商店型系统。

这三种机制不能互相完全替代。

## 方法七：加入万能资源

当重复需求较高时，需要一种跨卡种的进度保底：

- 万能卡；
    
- 通用碎片；
    
- 任意同星素材；
    
- 两张废卡转换为一张目标卡；
    
- 分解卡牌后定向制作。
    

它的功能不是消灭随机，而是防止玩家的所有非目标掉落都变成零价值。

万能资源过多会使卡池失去意义，因此通常应当：

- 转换效率低于直接获得；
    
- 主要处理废牌；
    
- 不能无限无损转换。
    

## 方法八：让非目标卡也有即时用途

这是你们项目特别适合的方法。

一张卡即使不适合长期装备，也可以：

- 立即释放一次主动效果；
    
- 作为消耗品解决战场危机；
    
- 分解；
    
- 献祭；
    
- 转化为临时增益；
    
- 给其他卡提供升级经验。
    

这样“不是我构筑需要的卡”不等于“垃圾”。

关键指标是：

> 非目标卡是否能产生低于长期培养、但仍然有意义的短期价值。

这能让大卡池从纯粹污染变成战术资源。

## 方法九：设计宽协同，而不是只有精确配方

窄协同：

- 必须A＋B＋C；
    
- 缺少任何一个都不成立；
    
- 卡牌只服务一套构筑。
    

宽协同：

- 所有“投射物”都能配暴击；
    
- 所有“控制”都能触发处决；
    
- 所有“持续伤害”都能延长或引爆；
    
- 某张桥接卡能把控制转化为伤害。
    

宽协同允许玩家用不同组件完成类似功能。

它能支持更大的卡池，因为玩家需要的是“某一类效果”，而不是唯一的一张指定卡。

## 方法十：设置随机保底

常见保底包括：

- 连续若干次未出现已有卡，则下一次必出；
    
- 连续若干次没有可合成结果，提高匹配卡权重；
    
- Boss必掉高星卡；
    
- 波末至少提供一个当前构筑升级；
    
- 某一核心卡长期未出现时逐渐提高权重。
    

保底最好修正极端坏运气，而不是操纵每一次普通结果。

玩家应该感觉：

> 我运气不好，但还能够继续玩。

而不是：

> 系统明显在按我的构筑发牌。

# 六、卡池的最佳目标不是“每局都完成理想套路”

这是肉鸽设计中非常容易走偏的地方。

如果玩家每局都能稳定完成指定构筑：

- 随机性变成表演；
    
- 玩家不会准备备用路线；
    
- 重玩内容快速枯竭；
    
- 最优构筑被机械复制。
    

但如果大部分局都无法形成任何完整构筑：

- 选择缺乏累积意义；
    
- 玩家只看单卡强度；
    
- 协同系统形同虚设；
    
- 失败被归因于运气。
    

合理目标应是：

1. 玩家通常能够形成一套**可辨认的主构筑**；
    
2. 不一定获得所有理想组件；
    
3. 通常需要接受一个替代组件；
    
4. 偶尔完成特别理想的“天胡构筑”；
    
5. 极端坏运气不会让整局完全失去成长。
    

也就是说：

> 保证构筑成形，不保证构筑完美。

# 七、实践中应该监控哪些数据

不能只看胜率或某张卡的选择率。

## 1. 无效奖励率

一次奖励中，没有任何选项能改善当前构筑的比例。

要结合玩家状态判断，不能仅按卡牌强度判断。

## 2. 强制拿废牌率

玩家明知不适合，但因为不能跳过或奖励过于珍贵而被迫拿取的比例。

## 3. 重抽率与重抽后选择率

- 重抽率高：原始池可能过于嘈杂；
    
- 重抽后仍然跳过：有效池结构有问题；
    
- 玩家从不重抽：重抽资源可能太贵或没必要。
    

## 4. 条件选择率

不能只看：

> 某张卡在所有选择中被拿了多少次。

应该看：

> 这张卡在被展示时，有多少次被选择。

即：

# [  
\text{条件选择率}

\frac{\text{被选择次数}}{\text{被展示次数}}  
]

否则低权重卡会因为很少出现，看起来选择率也很低。

## 5. 构筑成形时间

例如定义：

- 拥有一个明确主标签；
    
- 三张以上卡围绕同一机制；
    
- 至少有一个核心协同成立。
    

然后统计它通常在单局多少百分比时发生。

构筑成形太晚，玩家几乎体验不到构筑成果。

## 6. 构筑完成率

分别统计：

- 基本成形；
    
- 中度完成；
    
- 完美完成。
    

不要只用“有没有获得6★”作为单一指标。

## 7. 卡槽满载时间占比

卡槽满并不一定是坏事，但需要进一步区分：

- 满槽且存在可执行合成；
    
- 满槽但可以主动使用；
    
- 满槽且全部无法处理；
    
- 因满槽错失掉落。
    

最后一种才是真正的死锁压力。

## 8. 构筑多样性

观察通关构筑是否集中在少数路线。

但也要区分：

- 玩家偏爱某套构筑；
    
- 某套构筑过强；
    
- 系统随机权重偏向；
    
- 其他构筑难以成形。
    

## 9. 早期选择对最终构筑的影响

如果第一张随机卡几乎决定整局，锁定过强。

如果前期拿什么都不影响最终构筑，选择又缺乏意义。

合理状态是：

> 早期选择提高某条路线的概率，但不完全锁死路线。

# 八、一套实际的卡池调试流程

## 第一步：列出所有构筑路线

对每种构筑记录：

- 核心卡；
    
- 替代卡；
    
- 支援卡；
    
- 必须重复次数；
    
- 最晚成形时间；
    
- 最低可玩版本；
    
- 完美版本。
    

重点区分“必须”与“最好有”。

## 第二步：计算理论可达性

对每条构筑计算：

- 一局总掉落次数；
    
- 目标卡出现权重；
    
- 所需重复数量；
    
- 选择次数；
    
- 重抽次数；
    
- 保底次数。
    

不要只用期望值，还要进行随机仿真。

## 第三步：跑不同池规模

至少测试：

- 小池基准；
    
- 目标正式池；
    
- 比目标更大的压力池。
    

例如：

- 5种；
    
- 8种；
    
- 11种。
    

这样能看出指标在哪个区间突然恶化，而不是只比较两个极端。

## 第四步：逐个加入控制工具

不要一次把所有补偿机制都加进去。

推荐顺序：

1. 纯均匀随机；
    
2. 加跳过；
    
3. 加重抽；
    
4. 加已有卡权重；
    
5. 加废卡转换；
    
6. 加保底；
    
7. 加定向Boss奖励。
    

观察每个机制具体修复了什么。

## 第五步：真人测试认知感受

仿真只能判断“能否构筑”，不能判断“玩家是否感觉被操纵”。

真人测试需要问：

- 你觉得自己是在主动构筑，还是被系统发牌？
    
- 哪次选择最难？
    
- 哪次掉落最失望？
    
- 有没有明知无用但不得不拿的卡？
    
- 你什么时候确定了本局方向？
    
- 失败是因为决策、操作，还是始终抽不到牌？

# 九、回到你们现在的11种卡、7槽问题

我上一轮提出“11种总卡池、单局最多5种活跃卡池”，这是一个**稳妥方案**，但不是唯一的通用答案。

更准确地说，你们现在有三种值得测试的模型。

## 模型A：硬限制活跃池

- 总卡池11种；
    
- 单局选择5种进入掉落池；
    
- 7槽；
    
- 池内接近均匀随机。
    

优点：

- 最容易平衡；
    
- 现有5卡测试最能迁移；
    
- 重复合成稳定；
    
- 玩家理解成本低。
    

缺点：

- 单局意外组合较少；
    
- 开局选择可能过早锁定。
    

## 模型B：11种全局池＋动态集中

- 11种理论上均可出现；
    
- 初期较为开放；
    
- 玩家持有卡牌后，提高已有卡权重；
    
- 新类型仍有低概率出现；
    
- 配合重抽、分解或主动使用。
    

例如可以先测试：

- 65%掉落来自当前已持有种类；
    
- 20%来自未持有种类；
    
- 15%由特殊奖励、Boss或保底决定。
    

这不是最终数值，只是实验起点。

优点：

- 既有探索感，也能逐渐收束；
    
- 11种卡可以在同一局发生意外组合；
    
- 不需要硬性宣布“本局禁用哪些卡”。
    

缺点：

- 数学和遥测更复杂；
    
- 玩家可能感到系统暗中控制；
    
- 权重不当容易形成早期锁死。
    

## 模型C：11种完全均匀随机

- 11种都能出现；
    
- 权重一致；
    
- 单次掉一张；
    
- 7槽；
    
- 无定向修正。
    

这个模型应该作为**压力测试对照组**，而不应直接默认是正式方案。

它可以帮助你们确认：

- 卡槽多快被堵死；
    
- 合成次数下降多少；
    
- 高星可达性下降多少；
    
- 玩家是否不得不频繁使用废卡；
    
- 哪些补偿机制是必需的。

# 我的结论

肉鸽卡池的通用原则可以浓缩成一句话：

> **总池负责丰富，局部池负责成形，随机负责变化，控制工具负责让玩家表达意图。**

对你们项目而言，还要加上一条：

> **重复合成需求越高，单次选择宽度越窄，卡槽越有限，就越不能依赖完全均匀的大卡池。**

因此你们下一阶段不应该先争论“单局到底只能有5种还是必须有11种”，而应该把这三个量独立测试：

1. **可出现种类数**；
    
2. **已有卡牌的权重倾斜程度**；
    
3. **玩家处理非目标卡的能力**。
    

最合理的实验组是：

- 5种均匀池；
    
- 11种均匀池；
    
- 11种动态权重池；
    
- 11种动态权重＋废卡转换池。
    

然后比较构筑成形时间、合成频率、满槽死锁率、最高星级、无效掉落率和真人主观控制感。这样才能判断你们真正需要的是缩池、改权重，还是增加卡牌出口。

## 结论

**“万能卡”应当从卡 10 · 同调中拆出来，作为一套独立的、星级固定的稀有合成资源。**

它不是普通技能卡，不进入普通卡池，不占手牌格，不能装备，不能拖入战场释放。它的唯一功能是：

> 将一张 `X★万能卡` 拖到任意一张 `X★技能卡` 上，消耗万能卡，将目标升级为 `X+1★`。

例如：

- `1★万能卡 + 1★贯穿 → 2★贯穿`
    
- `2★万能卡 + 2★冰霜 → 3★冰霜`
    
- `5★万能卡 + 5★圣域 → 6★圣域`
    

这等价于“替代合成所缺少的另一张同型同星卡”，不会改变二合的基础价值。

卡 10 · 同调则变成**围绕合成和万能卡展开的技能卡**，而不是万能卡系统的解锁条件。

# 一、为什么必须拆成独立系统

P2 原设计把万能卡放在同调 6★：

> 精英/Boss 击杀必掉万能卡，可与任意类型同星合成。

这个方案有三个根本问题。

### 1. 解锁时间太晚

做出一张 6★ 同调，本身需要大量同调素材。此时局内已经进入后半段，玩家能够利用万能卡的剩余时间很短。

这会形成悖论：

> 玩家需要万能卡帮助完成高星构筑，但必须先完成最高难度的高星构筑，才能获得万能卡。

因此，万能卡不能由同调 6★“首次解锁”。

### 2. 万能卡不属于普通技能卡语义

当前普通卡天然具有三种行为：

- 同型同星自动合成；
    
- 3★以上可以装备；
    
- 可以拖入战场消耗释放。
    

如果简单给普通卡增加一个 `type: "wildcard"`，它会立刻产生问题：

- 可能被拖进装备槽，成为没有任何技能定义的死装备；
    
- 可能被拖进战场直接消失；
    
- 可能被自动合成系统错误选中；
    
- 满手时可能无法拾取；
    
- `resolveCardMeta()` 找不到正常名称和描述。
    

现有 `mergeRule` 原子虽然已经写入类型，并被 `getModifiers()` 收集，但目前只是一个空修饰，`cardSystem` 完全没有读取这些规则。

所以这不是“往 `skills.json` 补一张卡”就能完成的功能，而是一个独立的经济系统。

### 3. 稀有奖励不能因手牌已满而丢失

当前地面卡在满手时，只有“拾取后能立即合成”才允许拾取，否则会返回 `cardsFull`。

普通卡这样处理合理，但万能卡如果是 Boss 或 bounty 的稀有奖励，玩家因为当时满手而无法领取，会非常糟糕。

因此万能卡不应进入普通手牌。

# 二、推荐的万能卡规则

## 1. 万能卡必须有固定星级

不要设计成“一张万能卡可以匹配任意星级”。

万能卡获得时就确定星级：

- 1★万能卡只能匹配1★卡；
    
- 2★万能卡只能匹配2★卡；
    
- 以此类推；
    
- 最高只需要5★，因为6★已经不能继续升级。
    

这是最重要的经济约束。

如果一张万能卡能适配任意星级，最优策略永远是：

> 一直不使用，等到出现5★卡，再直接补成6★。

这样所有低星使用都是错误决策，系统看似自由，实际上只有一个最优答案。

固定星级则会产生真实判断：

- 现在用2★万能卡，快速做出首件3★装备；
    
- 还是保留它，等待另一个更适合本局构筑的2★目标；
    
- 3★万能卡用于补强主装备，还是用于建立第二条构筑线。
    

## 2. 万能卡必须显式使用，绝不自动使用

现有手牌会自动扫描同型同星卡并连续合成。

万能卡不能参与这套自动扫描。否则出现多个合法目标时，系统无法知道玩家想升级哪一张。

例如玩家拥有：

- 2★贯穿
    
- 2★冰霜
    
- 2★万能卡
    

如果自动合成，游戏必须擅自选择贯穿或冰霜，这会直接毁掉构筑决策。

正确规则是：

> 普通卡继续自动合成；万能卡永远由玩家指定目标。

## 3. 万能卡不占普通手牌

新增一个独立的“万能卡储备区”。

最简UI可以显示成一排小型资源卡：

```text
万能卡
1★ ×2    2★ ×1    3★ ×0    4★ ×0    5★ ×0
```

只有数量大于0的星级需要突出显示。

它仍然具有“卡”的视觉表现，但底层是星级计数资源：

```ts
type WildcardStar = 1 | 2 | 3 | 4 | 5;

interface WildcardInventory {
  1: number;
  2: number;
  3: number;
  4: number;
  5: number;
}
```

这样不会：

- 占用7格手牌；
    
- 受满手限制；
    
- 在地面过期；
    
- 被普通自动合成；
    
- 被误装备或误释放。
    

## 4. 万能卡应当能够升级手牌和装备

合法目标包括：

- 手牌中的同星技能卡；
    
- 装备栏中的同星技能卡。
    

这与现有“喂养已装备卡”逻辑一致。当前系统允许手牌同型同星卡拖到已装备卡上，将装备升星。

万能卡只是把“必须同型”改为“万能替代”，不能限制只能作用于手牌，否则已装备卡的成长会被割裂。

## 5. 万能合成必须算作一次正常合成

使用万能卡后必须：

- `state.merges += 1`
    
- 触发 `onMerge`
    
- 触发同调的合成脉冲；
    
- 计入“每波合成次数”；
    
- 计入遥测。
    

事件载荷应当仍然是最终目标类型：

```ts
fireTrigger(state, config, rng, 'onMerge', {
  merge: {
    cardType: target.type,
    resultStar: target.star,
  },
});
```

不能把 `cardType` 写成 `wildcard`，因为战斗效果关心的是最终合成出的构筑卡。

建议额外产生一个表现事件：

```ts
{
  type: 'wildcardMerged',
  cardType: target.type,
  consumedStar: wildcardStar,
  resultStar: target.star
}
```

这样UI可以播放特殊动画，但效果系统仍走统一 `onMerge`。

# 三、完整操作逻辑

## 推荐主操作：点选，再点目标

考虑到这是触屏、快速选择型游戏，我更推荐“两次点击”，而不是要求精确拖拽。

具体流程：

1. 玩家点击 `2★万能卡`。
    
2. 游戏进入“选择同调目标”状态。
    
3. 所有合法的2★技能卡发出金色高亮。
    
4. 其他星级卡、空槽、6★卡全部变暗。
    
5. 玩家点击某张2★卡。
    
6. 显示短暂预览：
    
    `2★冰霜 → 3★冰霜`
    
7. 立即完成升级，扣除一个2★万能卡。
    
8. 播放特殊合成动画，退出选择状态。
    

点击空白处、再次点击万能卡或按取消，应退出选择状态，不消耗资源。

## 拖拽作为快捷操作

同时保留：

> 从万能卡储备区拖到技能卡上。

这样熟悉现有操作的玩家可以直接拖，触屏精度不高的玩家则可以点选。

## 合法性规则

只有以下条件全部满足时才能完成：

```ts
target !== null
target.star === wildcardStar
target.star < cfg.economy.maxStar
target 是普通技能卡
```

错误情况：

|情况|结果|
|---|---|
|2★万能卡拖到1★卡|拒绝，提示“需要2★目标”|
|拖到空槽|取消|
|拖到6★卡|拒绝，提示“已达最高星级”|
|拖到战场|取消，不消耗|
|拖到装备空槽|取消|
|普通卡拖到万能卡区|取消|
|万能卡数量为0|不可选中|

## 结果触发连续合成

假设手牌中有：

- 2★贯穿
    
- 3★贯穿
    
- 2★万能卡
    

使用万能卡升级2★贯穿后：

1. 万能合成得到3★贯穿；
    
2. 手牌中现在存在两张3★贯穿；
    
3. 现有自动合成继续结算；
    
4. 最终得到4★贯穿。
    

事件顺序应当是：

```text
wildcardMerged：2★ → 3★
merged：3★ + 3★ → 4★
```

即万能合成可以引发正常连锁合成。

# 四、同调卡应该怎样重构

同调的核心幻想应继续是：

> 合成本身就是攻击；合成越频繁，战斗反馈越强。

不应变成“必须装备同调才能使用万能卡”。

推荐结构如下。

## 1★消耗态

保留现设计：

> 根据本局合成次数造成一次范围伤害。

但最好设置伤害上限或递减，防止后期一次消耗产生异常爆发。

例如：

```text
基础伤害 + min(本局合成次数, 30) × 系数
```

## 3★装备态

保留现设计：

- 每次合成产生全场同调脉冲；
    
- 合成结果星级越高，伤害越高；
    
- 合成后获得短暂射速提升。
    

这部分当前系统已经具备：

- `onMerge` 触发器；
    
- `mergePulse` 原子；
    
- `Buff.kind = fireRateMul` 的状态基础。
    

## 5★装备态

原设计是每次合成约25%概率返还一张同型1★素材。

建议改成确定性节奏，避免经济结果被随机数主导：

> 每完成4次合成，返还1张“最近一次合成类型”的1★卡；每波最多触发1次。

相比25%随机，这个版本：

- 玩家可以预测；
    
- 更容易平衡；
    
- 更容易做进度提示；
    
- 不会出现连续返还造成经济失控；
    
- 可以通过“3/4”进度明确鼓励玩家再完成一次合成。
    

配置可表达为：

```json
{
  "atom": "mergeRule",
  "params": {
    "rule": "refundLastMergedType",
    "every": 4,
    "star": 1,
    "capPerWave": 1
  }
}
```

## 6★形态·万能同调

建议改为：

> 每波第5次合成时获得1张1★万能卡，每波最多一次。

同时保留强化后的合成脉冲。

这意味着：

- 万能卡基础系统所有玩家都能接触；
    
- 6★同调不是解锁系统，而是成为万能卡的稳定生产构筑；
    
- 因为有每波上限，不会无限滚雪球；
    
- 即使同调已经6★，玩家仍可用万能卡培养另外两件装备。
    

示例：

```json
{
  "atom": "mergeRule",
  "params": {
    "rule": "grantWildcard",
    "every": 5,
    "wildcardStar": 1,
    "capPerWave": 1
  }
}
```

“精英/Boss必掉万能卡”则应当移到基础奖励配置，而不是写死在同调技能定义里。

核心结算大致为：

```ts
export function useWildcard(
  state: GameState,
  config: Config,
  rng: Rng,
  wildcardStar: WildcardStar,
  targetKind: SlotKind,
  targetIndex: number,
): GameEvent[] {
  const targetCollection =
    targetKind === 'cards' ? state.cards : state.equipment;

  const target = targetCollection[targetIndex];

  if (!target) {
    return [{ type: 'wildcardMergeRejected', reason: 'empty' }];
  }

  if (target.star >= cfg.economy.maxStar) {
    return [{ type: 'wildcardMergeRejected', reason: 'maxStar' }];
  }

  if (target.star !== wildcardStar) {
    return [{ type: 'wildcardMergeRejected', reason: 'star' }];
  }

  if (state.wildcards[wildcardStar] <= 0) {
    return [{ type: 'wildcardMergeRejected', reason: 'invalidTarget' }];
  }

  state.wildcards[wildcardStar]--;
  target.star++;
  state.merges++;

  const events: GameEvent[] = [{
    type: 'wildcardMerged',
    cardType: target.type,
    consumedStar: wildcardStar,
    resultStar: target.star,
    targetKind,
  }];

  events.push(
    ...fireTrigger(state, config, rng, 'onMerge', {
      merge: {
        cardType: target.type,
        resultStar: target.star,
      },
    }),
  );

  if (targetKind === 'cards') {
    const chain = autoMergeCards(state, config, rng);
    events.push(...chain.events);
  }

  return events;
}
```

## 3. 合并现有重复结算

当前普通手牌合成和装备喂养分别自行执行：

- `target.star++`
    
- `state.merges++`
    
- 生成事件；
    
- 调用 `fireTrigger(onMerge)`。
    

新增万能卡后会出现第三处重复。

应抽出一个统一函数，例如：

```ts
commitMergeResult(...)
```

统一负责：

- 增加合成次数；
    
- 发出合成事件；
    
- 触发 `onMerge`；
    
- 记录遥测。
    

否则以后非常容易出现“普通合成触发同调，但万能合成不触发”之类的漏接。

## 4. 输入层

当前 `SlotSource` 只有：

```ts
'cards' | 'equipment'
```

指针路由也只识别手牌槽和装备槽。

```ts
type DragSource =
  | { kind: 'card'; slotKind: SlotKind; index: number }

```

这样规则层可以明确判断：

- 普通卡拖到战场：消耗释放；
    
- 普通卡拖到装备：装备或喂养；
    
- 万能卡拖到普通卡：万能合成；
    
- 万能卡拖到其他地方：取消。
    

## 5. UI层

新增：

```text

```

不要复用普通 `createCardElement()`，因为普通卡元素会调用 `resolveCardMeta(card.type, card.star)`，并天然带有装备/消耗语义。

万能卡应有独立组件：

```ts

```

视觉建议：

- 金色或虹彩边框；

- 普通掉落系统不认为玩家多了一格手牌；
    
- 第8个视觉位置专属于万能卡。
    

## 2. 普通自动合成不能接触万能卡

现有自动合成只扫描 `state.cards`，寻找“类型相同且星级相同”的卡，然后连续合成。

因此万能卡只要完全独立于 `state.cards`，就天然满足：

- 不自动使用；
    
- 不与万能卡自身自动合并；
    
- 不被普通满手逻辑计算；
    
- 不被拖到战场释放；
    
- 不被装备。
    

这也是为什么不应添加：

```ts
type: 'wildcard'
```

形式的普通 `Card`。

## 3. 装备喂养已经提供了正确的交互参考

当前装备升级是：

- 手牌卡拖到同型、同星装备；
    
- 目标装备原地 `star++`；
    
- 消耗来源卡；
    
- `state.merges++`；
    
- 触发 `onMerge`；
    
- 保留目标卡ID，用于升级反馈。
    

万能卡升级应该使用同一种“目标卡原地升星”语义，只是把来源从手牌卡改成独立库存。

## 4. 当前拖拽路由只认识手牌和装备

现有拖拽源类型只有：

```ts
'cards' | 'equipment'
```

拖拽目标则只有：

```ts
slot
arena
cancel
```

因此需要扩展“拖拽源”，但不需要新增“万能卡目标”。万能卡只能作为来源，目标仍然是现有手牌槽或装备槽。

## 5. 新升级反馈系统可以直接复用

最新版本已经让：

- 普通合成事件携带 `resultCardId`；
    
- 装备喂养事件携带 `targetCardId` 和 `slotIndex`；
    
- UI刷新后再根据卡ID寻找目标卡，播放升级脉冲与里程碑提示。
    

万能合成事件只要同样携带：

- `targetCardId`
    
- `targetKind`
    
- `targetIndex`
    
- `resultStar`
    

就可以复用当前升级反馈，不需要新做一套动画系统。

## 2. 生成万能卡

```ts

  count: number;
```

```ts
export function grantWildcards(
  state: GameState,
  grants: WildcardGrant[],
): GameEvent[] {
  const applied: WildcardGrant[] = [];

  for (const grant of grants) {
    if (
      grant.star < 1 ||
      grant.star >= cfg.economy.maxStar ||
      grant.count <= 0
    ) {
      continue;
    }

    state.wildcards[grant.star] =
      (state.wildcards[grant.star] ?? 0) + grant.count;

    applied.push(grant);
  }

  return applied.length
    ? [{ type: 'wildcardsGranted', grants: applied }]
    : [];
}
```

## 3. 将万能卡用于目标槽


伪代码：

```ts
export function useWildcardOnSlot(
  state: GameState,
  config: Config,
  rng: Rng,
  targetKind: SlotKind,
  targetIndex: number,
): GameEvent[] {
  const check = checkWildcardTarget(
    state,
    targetKind,
    targetIndex,
  );

  if (!check.ok) {
    return [{
      type: 'wildcardMergeRejected',
      reason: check.reason,
      requiredStar: check.requiredStar,
    }];
  }

  const target = check.target;
  const consumedStar = check.requiredStar;

  state.wildcards[consumedStar]--;
  target.star++;

  if (targetKind === 'equipment') {
    state.equipOps++;
  }

  const events: GameEvent[] = [{
    type: 'wildcardMerged',
    cardType: target.type,
    consumedStar,
    resultStar: target.star,
    targetKind,
    targetIndex,
    targetCardId: target.id,
  }];

  events.push(
    ...commitMerge(
      state,
      config,
      rng,
      target.type,
      target.star,
    ),
  );

  if (targetKind === 'cards') {
    const chain = autoMergeCards(state, config, rng);
    events.push(...chain.events);
  }

  return events;
}
```

# 五、统一“正常合成”的公共结算

当前有两处分别手写：

```ts
state.merges++;
fireTrigger(..., 'onMerge', ...);
```

分别在：

- 普通自动合成；
    
- 装备喂养。
    

加入万能卡后会出现第三处。为了确保万能合成确实属于“正常合成”，建议在 `cardSystem.ts` 抽出：

```ts
export function commitMerge(
  state: GameState,
  config: Config,
  rng: Rng,
  cardType: CardType,
  resultStar: number,
): GameEvent[] {
  state.merges++;

  return fireTrigger(state, config, rng, 'onMerge', {
    merge: {
      cardType,
      resultStar,
    },
  });
}
```

然后三种合成都调用它：

```text
普通自动合成 ─┐
装备喂养     ├─ commitMerge()
万能卡合成   ┘
```

这比仅在万能卡代码里复制一次 `state.merges++` 更安全。以后任何 `onMerge` 机制都不会漏掉万能合成。

# 六、万能合成事件设计

在 `GameEvent` 中新增：

```ts
| {
    type: 'wildcardsGranted';
    grants: Array<{
      star: number;
      count: number;
    }>;
  }
| {
    type: 'wildcardMerged';
    cardType: CardType;
    consumedStar: number;
    resultStar: number;
    targetKind: SlotKind;
    targetIndex: number;
    targetCardId: number;

| {
    type: 'wildcardMergeRejected';

      | 'emptyTarget'
      | 'maxStar'
```

不要为了复用表现而伪造普通 `merged` 或 `fed` 事件。

原因是：

- `merged` 当前代表手牌中的自动二合；
    
- `fed` 当前代表手牌卡喂养装备；
    
- 万能合成是第三种明确的玩家操作；
    
- 遥测和调试时应能识别它。
    

但它在底层仍然通过 `commitMerge()` 计入正常合成并触发 `onMerge`。

# 七、连续合成的具体结算顺序

例子：

```text
手牌：
1★A
2★A

万能库存：
1★ ×1
```

玩家将万能卡槽拖到1★A上。

第一步，万能合成：

```text
1★A + 1★万能卡 → 2★A
```

第二步，自动扫描手牌：

```text
2★A + 原有2★A → 3★A
```

最终：

```text
万能库存1★：1 → 0
state.merges：+2
手牌结果：3★A
```

事件顺序：

```ts
[
  {
    type: 'wildcardMerged',
    consumedStar: 1,
    resultStar: 2,
    // ...
  },

  // 万能合成对应的 onMerge 效果事件

  {
    type: 'merged',
    resultStar: 3,
    // ...
  },

  // 自动连锁合成对应的 onMerge 效果事件
]
```

必须先完成万能合成的 `onMerge`，再进入后续自动合成，这样每一次合成都保持独立的正常结算时点。

装备目标不会触发手牌自动扫描，因为当前装备升级与手牌自动合成是两套不同规则。万能卡升级装备后只升一级。

# 十、`game.ts` 中的分流

当前控制器将：

- 拖到战场解释为消耗释放；
    
- 拖到装备解释为装备或喂养；
    
- 其他槽位解释为移动交换。
    

改为优先判断万能卡：

```ts
onDrop: (source, index, target) => {
  let events: GameEvent[] = [];

  if (source === 'wildcard') {
    if (target.kind === 'slot') {
      events = useWildcardOnSlot(
        state,
        config,
        rng,
        target.slotKind,
        target.index,
      );
    }

    // 拖到战场或其他区域：取消，不做任何事。
  } else if (target.kind === 'arena') {
    events = consumeCard(
      state,
      config,
      rng,
      index,
      target.x,
      target.y,
      source,
    );
  } else if (
    target.kind === 'slot' &&
    target.slotKind === 'equipment' &&
    source === 'cards'
  ) {
    events = moveOrSwap(
      state,
      config,
      rng,
      source,
      index,
      'equipment',
      target.index,
    );
  } else if (target.kind === 'slot') {
    events = moveOrSwap(
      state,
      config,
      rng,
      source,
      index,
      target.slotKind,
      target.index,
    );
  }

  dispatch(events);
}
```

万能卡分支必须排在战场消耗分支之前，防止万能卡被错误传给 `consumeCard()`。

## 一、结论：这不是“小改 Bounty”，而是重建一个独立的遭遇系统

你提出的新机制与当前实现的底层模型完全不同。

当前 Bounty 是：

> 每波开始掷一次骰子 → 下一只普通敌人被挂上 Bounty 标记 → 玩家点击这只敌人 → 该敌人增加血量和速度 → 击杀后随机掉几张更肥但更快过期的卡。

代码证据：

- 每波只进行一次 `spawnChancePerWave` 判定，并设置一个布尔值 `bountyPending`。
    
- 下一只非 Boss 普通敌人生成时，直接把 Bounty 标记挂到它身上。
    
- 点击接受后，只强化这一只敌人的 HP 和速度。
    
- 当前 Bounty 奖励仍然随机抽取卡牌类型和星级，只是提高二星权重。
    
- 当前索敌是“已接受 Bounty 绝对优先”，不会被更近的紧急威胁覆盖。
    
- 当前视觉只有金色倒计时弧线或金色描边。
    

你需要的新 Bounty 应当是：

> 独立生成报价标记 → 玩家预先看见确定奖励 → 主动接受或忽略 → 从标记方向额外生成一组强化敌人 → 消灭完整敌群 → 统一生成确定奖励。

所以，正确的代码抽象不再是 `Enemy.bounty`，而应当是独立的：

**Bounty Director + Bounty Offer + Bounty Encounter。**

# 二、新机制应当采用的完整生命周期

建议将生命周期明确为：

```text
等待生成
  ↓
Offer：画面边缘出现赏金标记
  ├─ 玩家未点击，倒计时结束 → Expired
  └─ 玩家点击接受 → Accepted
                         ↓
                   Spawning
                   额外敌群分批生成
                         ↓
                     Active
              玩家与赏金敌群交战
                 ├─ 全部消灭 → Completed
                 └─ 任一成员突破 → Failed
```

推荐状态：

```ts
type BountyEncounterStatus =
  | 'spawning'
  | 'active'
  | 'completed'
  | 'failed';
```

这里有一个必须提前拍板的规则，我建议如下：

- 未接受的 Offer 不影响波次结束。
    
- 接受后生成的敌人属于真实战场敌人，因此会阻止波次结束。
    
- Bounty 敌人全部消灭后才统一发奖。
    
- Bounty 成员突破炮台，整个任务判定失败，不再发奖。
    
- 被诱饵、反伤或其他技能正常消灭，仍计入完成进度。
    
- 保底保证的是“每波出现至少多少次报价”，不是强迫玩家接受多少次战斗。
    

最后一点很重要。否则“主动选择”会被保底机制破坏。

# 三、数据模型重构

## 1. 删除旧的敌人级 Bounty 状态

当前类型只有：

```ts
bounty?: {
  accepted: boolean;
  markRemaining: number;
}
```

而 `GameState` 只有一个：

```ts
bountyPending: boolean;
```

这只能描述“一只被标记的普通敌人”，无法描述独立报价、方向、奖励、敌群和任务完成状态。

建议替换为：

```ts
interface BountyOffer {
  id: number;

  /** 玩家接受前就已经确定 */
  rewardCardType: CardType;

  /** 标记位于哪一边，同时也是敌群出生方向 */
  side: 'top' | 'right' | 'bottom' | 'left';

  /** Canvas 上可点击的锚点 */
  x: number;
  y: number;

  remaining: number;

  /** 本次是否由每波保底强制生成 */
  guaranteed: boolean;
}

interface BountyEncounter {
  id: number;
  offerId: number;
  rewardCardType: CardType;
  side: 'top' | 'right' | 'bottom' | 'left';

  status: 'spawning' | 'active' | 'completed' | 'failed';

  /** 所有已经生成、尚未结算的成员 */
  memberIds: number[];

  pendingSpawnCount: number;
  spawnTimer: number;

  /** 完成后奖励出现的位置 */
  rewardX: number;
  rewardY: number;
}
```

敌人只保留归属引用：

```ts
interface Enemy {
  // 原有字段……

  bountyEncounterId?: number;
  bountyRewardType?: CardType;
}
```

`GameState` 增加：

```ts
interface BountyDirectorState {
  offersThisWave: number;
  acceptedThisWave: number;
  completedThisWave: number;

  nextCheckAt: number;
  cooldownUntil: number;

  /** 最近一次实际受到突破伤害的游戏时间 */
  lastHpLossAt: number;

  /** 奖励类型洗牌袋，避免连续重复 */
  rewardBag: CardType[];
}

interface GameState {
  // 原有字段……

  bountyOffers: BountyOffer[];
  bountyEncounters: BountyEncounter[];
  bountyDirector: BountyDirectorState;

  nextBountyOfferId: number;
  nextBountyEncounterId: number;

  /** 用于计算本波生成进度，不能只看不断减少的 spawnLeft */
  waveSpawnQuota: number;
}
```

初版可以限制：

```ts
maxConcurrentOffers = 1;
maxConcurrentEncounters = 1;
```

但数据结构使用数组，避免以后增加“两种奖励同时报价”时再次推翻结构。

# 六、动态生成概率的具体算法

你的要求可以拆成两部分：

1. 玩家状态越好，额外出现 Bounty 的概率越高。
    
2. 玩家状态再差，每波也至少看见一定次数的报价。
    

二者不冲突。动态概率负责“额外机会和出现时机”，保底负责“最低报价次数”。

建议每隔固定秒数检查一次，而不是每帧掷骰，也不是只在波次开始掷一次。

```ts
function calculateBountyOfferChance(
  state: GameState,
  config: BountyConfig,
): number {
  const offer = config.offer;

  const hpRatio = state.hp / state.maxHp;

  const healthyScore = clamp01(
    (hpRatio - offer.healthyHpThreshold)
    / (1 - offer.healthyHpThreshold)
  );

  const noDamageSeconds =
    Math.max(0, state.time - state.bountyDirector.lastHpLossAt);

  const noDamageScore = clamp01(
    noDamageSeconds / offer.noDamageRampSeconds
  );

  const recentDamageScore = clamp01(
    1 - noDamageSeconds / offer.recentDamagePenaltySeconds
  );

  return clamp(
    offer.baseChancePerCheck
      + healthyScore * offer.healthyHpBonusMax
      + noDamageScore * offer.noDamageBonusMax
      - recentDamageScore * offer.recentDamagePenalty,
    offer.minChancePerCheck,
    offer.maxChancePerCheck,
  );
}
```

效果是：

- 刚受到伤害：近期受伤惩罚最高，概率下降。
    
- 长时间不受伤：无伤奖励逐渐抬升。
    
- 高血量：再获得额外概率。
    
- 低血量：不会降到零，因为存在 `minChancePerCheck`。
    
- 到本波 55% 进度仍未出现最低次数：直接触发保底。
    

波次进度不能仅使用时间，因为每波时长会随玩家 DPS 改变。建议使用：

```ts
waveProgress =
  1 - state.spawnLeft / state.waveSpawnQuota;
```

当：

```ts
offersThisWave < minOffersPerWave
&& waveProgress >= guaranteeAtWaveProgress
```

则强制生成一次 Offer。

必须在 `checkWaveClear()` 之前执行 Bounty Director，否则高速清场时可能还没有机会触发保底。

# 七、奖励类型选择：随机“报价”，确定“结果”

“不依赖运气”不等于整局奖励类型完全固定。

合理模式是：

- Offer 生成前，由系统选定一个奖励类型。
    
- Offer 出现后，类型、星级和数量全部固定并展示。
    
- 玩家接受后，结果不再重新掷骰。
    
- 使用洗牌袋而非每次独立随机，避免连续出现同一种卡。
    

建议：

```ts
rewardBag = shuffle([
  'pierce',
  'chainLightning',
  'splitBlast',
  'frost',
  'decoy',
  'impact',
  'scorch',
  'sanctum',
  'harvest',
  'aegis',
  'thorns',
]);
```

袋子抽空后再洗牌。

如果配置 `repeatProtection = 1`，就禁止与上一次完全相同。

这样仍有局间变化，但玩家面对每一次 Bounty 时拥有完整信息和真实决策权。

# 八、敌群生成必须独立于普通波次预算

当前普通敌人由 `spawnEnemy()` 生成，并消耗 `spawnLeft`。

新版需要先把敌人构造与普通波次生成拆开：

```ts
function createEnemy(
  state: GameState,
  type: EnemyType,
  wave: number,
  position: Point,
  modifiers?: EnemySpawnModifiers,
): Enemy;
```

然后分成：

```ts
spawnRegularEnemy(...)
spawnBountyEnemy(...)
```

Bounty 敌群必须：

- 不消耗 `spawnLeft`。
    
- 不消耗 Budget 波次的正常配额。
    
- 不改变当前普通敌人的概率池。
    
- 从 Offer 所在方向出现。
    
- 在短时间内分批生成，而不是同一帧全部出现。
    
- 每个成员带相同 `bountyEncounterId`。
    
- 每个成员使用奖励卡牌的色系。
    

例如：

```ts
const count = Math.min(
  enemyCountBase
    + Math.floor((wave - 1) * enemyCountPerWave),
  enemyCountMax,
);
```

敌群构成可先按权重抽取普通、高速、重装敌人，但奖励类型与构成随机性相互独立。

# 九、奖励结算必须从“逐敌掉落”改为“任务完成统一掉落”

当前逻辑是，只要某只敌人身上有已接受 Bounty，死亡时就立刻调用 `rollBountyDrops()`。

新版必须改为：

```ts
if (enemy.bountyEncounterId !== undefined) {
  notifyBountyMemberResolved(...);
  // 不执行普通掉落，也不执行逐敌 Bounty 掉落
} else {
  rollDropOnKill(...);
}
```

当最后一个成员被解决：

```ts
completeBountyEncounter(...)
```

统一生成：

```text
指定类型卡牌 × N
万能卡 × N
```

这能避免：

- 每杀一只都单独抽奖。
    
- 最后一只没杀完却已经拿到大部分奖励。
    
- 敌群数量越多，奖励意外倍增。
    
- 普通掉落池和 Bounty 奖励池互相污染。

# 十、万能卡必须支持地面掉落

万能卡系统本身已经存在，并且已经是独立库存：

```ts
state.wildcards[star]
```

`grantWildcards()` 可以直接发放资源。

但目前万能卡没有地面掉落实体，而你的要求是：

> 敌群清除后，奖励掉在地面上，等待玩家拾取。

因此 `GroundDrop` 需要从单一结构改为判别联合类型：

```ts
interface GroundCardDrop {
  kind: 'card';
  id: number;
  x: number;
  y: number;
  type: CardType;
  star: number;
  life: number;
  maxLife: number;
  pulse: number;
}

interface GroundWildcardDrop {
  kind: 'wildcard';
  id: number;
  x: number;
  y: number;
  star: number;
  count: number;
  life: number;
  maxLife: number;
  pulse: number;
}

type GroundDrop =
  | GroundCardDrop
  | GroundWildcardDrop;
```

拾取规则：

- 普通卡牌仍受手牌容量约束。
    
- 万能卡不占手牌格。
    
- 即使手牌已满，万能卡仍然可以拾取。
    
- 万能卡拾取后调用 `grantWildcards()`。
    
- Bounty 卡牌和万能卡可以以小扇形散落，避免完全重叠。
    
- Bounty 奖励使用独立寿命，不受普通敌人掉落寿命随机影响。

# 十三、索敌规则应改成“紧急威胁覆盖 Bounty”

当前逻辑是：

```text
已接受 Bounty > 烙印 > 最近敌人
```

这会导致一只普通敌人已经贴脸时，炮台仍然攻击远处 Bounty，产生不合理失误。

建议改成：

```text
1. 突破线附近的紧急威胁
2. 已接受 Bounty 敌群
3. 烙印 focusPriority
4. 射程内最近敌人
```

具体实现：

```ts
const emergency = enemies
  .filter(enemy => distanceToTurret(enemy) <= emergencyOverrideDistance)
  .sort(byDistance)[0];

if (emergency) return emergency;

const bountyTarget = enemies
  .filter(enemy => isActiveBountyMember(enemy))
  .sort(byDistance)[0];

if (bountyTarget) return bountyTarget;
```

`emergencyOverrideDistance` 必须暴露在调参面板里。

它不能简单等于突破线距离。应该比突破线更宽，让炮台提前处理即将突破的敌人。

# 十九、最终验收标准

新版机制只有同时满足以下条件，才算完成：

1. 第一波开始就可能出现 Bounty Offer。
    
2. 标记出现时，玩家一眼能看懂奖励类型、奖励星级、奖励包含万能卡。
    
3. 不接受时没有惩罚，也不会生成强化敌人。
    
4. 接受后从标记方向额外生成完整敌群。
    
5. 额外敌群不占普通波次出怪配额。
    
6. 全部赏金敌人使用奖励类型色系和图标标识。
    
7. 炮台一般优先攻击赏金敌群，但贴近突破线的敌人可以覆盖优先级。
    
8. 未清完整组前不发奖励。
    
9. 完整清除后固定掉落对应类型卡牌和万能卡。
    
10. 奖励不调用普通敌人的随机掉落池。
    
11. 动态概率会随无伤、高血量、近期受伤变化。
    
12. 每波最低 Offer 次数有确定性保底。
    
13. 所有核心数值都能在调参面板修改并导出。
    
14. 遥测能回答“出现、接受、完成、失败、拾取”的完整漏斗。
    
15. 普通敌人的生成和掉落逻辑不因本次改造发生非预期变化。
    

最合理的开发顺序是先完成阶段 1–4，形成完整可玩的规则闭环；随后再做视觉强化和参数标定。这样不会先花大量时间制作特效，最后却因任务完成规则或经济结构变化而返工。
