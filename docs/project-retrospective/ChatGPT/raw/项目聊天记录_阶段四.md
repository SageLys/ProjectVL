我想知道吸血鬼幸存者或其他类似的roguelike游戏的随机奖励池概率是怎么算的。最好的办法似乎是找到开源或解包的游戏文件找到相关逻辑。这能做到吗？请搜集信息，找到可行的办法

你想查的不是单纯的“某个奖励出现率”，而是完整的随机奖励生成机制：哪些东西进入候选池、各自权重是多少、系统是否优先已有装备、一次如何生成多个不重复选项，以及重抽、封印、幸运值如何改变最终结果。

结论是：**能做到，而且《吸血鬼幸存者》旧版本的核心算法已经可以从社区保存的反混淆代码中还原。当前版本也能查，但需要针对你本地的具体游戏版本进行 Unity IL2CPP 反编译和运行时记录，不能直接把旧版公式当作当前版公式。**

## 一、已经找到的《吸血鬼幸存者》旧版算法

社区保存的旧 Phaser 版本 `LevelUpFactory` 代码显示，升级奖励大体按以下流程生成。

### 1. 默认显示3个选项，幸运可能增加到4个

旧代码中的判断是：

```text
随机数 > 1 / Luck
```

因此：

```text
出现第4个选项的概率 = 1 - 1 / Luck
```

例如：

- Luck = 1.0：0%
    
- Luck = 1.2：16.67%
    
- Luck = 1.5：33.33%
    
- Luck = 2.0：50%
    

这说明幸运值并不只是影响“稀有奖励”，还可能增加升级页面的选项数量。

### 2. 候选池首先经过资格过滤

初始化时，系统会排除：

- 进化武器；
    
- 尚未解锁的武器；
    
- `rarity = 0` 的内容；
    
- 被封印、放逐或其他规则排除的内容。
    

之后还会根据当前武器槽和被动槽是否已满，排除不能新取得的武器或被动；已经持有但尚未满级的项目仍然可以继续出现。可读的 TypeScript 重实现保留了这些规则。

因此，某件武器的真实概率不是固定值，而是：

```text
该物品当前有效权重
──────────────────
当前所有合格候选的有效权重之和
```

### 3. `rarity` 实际上是权重，不是百分比

抽取方式是典型的累计权重抽样：

```text
总权重 W = w1 + w2 + ... + wn
r = [0, W) 内的均匀随机数

选择第一个“累计权重 ≥ r”的候选
```

反混淆代码直接表现为：累计所有候选的 `rarity`，生成随机数乘以总权重，然后寻找第一个累计权重超过随机值的候选。

旧版数据中可以看到这些权重：

- Whip：100
    
- Magic Wand：100
    
- Axe：100
    
- Cross：80
    
- King Bible：80
    
- Garlic：70
    
- Pentagram：60
    
- Peachone：50
    
- 一些角色专属武器：1
    

这些数字不是“100%”“80%”，只是相对权重。

假设当前合格池只有：

```text
A：100
B：80
C：50
D：20
```

单次首抽概率就是：

```text
A = 100 / 250 = 40%
B = 80 / 250  = 32%
C = 50 / 250  = 20%
D = 20 / 250  = 8%
```

但升级页面会抽取多个不重复选项。若一次抽3个不同选项，A出现在最终页面中的概率约为93.25%，而不是简单的 `40% × 3`。

原因是每抽中一个候选后，后续的有效分母发生变化。这实际上相当于**加权无放回抽样**。

### 4. 前几级会强制偏向新武器

旧代码显示，在角色等级不高于3级、且武器槽尚未满的情况下，补充奖励选项时只从“真正的武器”中抽取，而不是从武器和被动的混合池中抽取。

这是一种早期构筑保护机制：

```text
前期：保证玩家尽快拿到攻击手段
中后期：武器和被动进入混合奖励池
```

因此，即使某被动的 `rarity` 很高，它在最初几级仍可能完全没有出现资格。

### 5. 系统会额外尝试塞入已有装备升级

旧版有一条独立的“已有装备优先”分支。其基础概率是：

```text
奇数等级：0.3 + 1 - 1 / Luck
偶数等级：0.6 + 1 - 1 / Luck
```

当结果大于1时，由于代码是拿 `Math.random()` 与它比较，实际效果相当于100%。

在 Luck = 1 时：

- 奇数等级：30%
    
- 偶数等级：60%
    

在 Luck = 1.5 时：

- 奇数等级：约63.33%
    
- 偶数等级：约93.33%
    

但抽中的已有装备还需要通过其他检查，例如是否已满级、当前角色等级是否足够，以及是否已被放逐。系统最多尝试预填两个已有装备选项，再用普通权重池补足剩余位置。

这意味着升级页面不是简单地“一次从全部装备池抽3张”，而更接近：

```text
步骤1：尝试安排已有装备升级
步骤2：检查前期武器保底
步骤3：从普通加权池补足剩余选项
步骤4：拒绝重复结果
步骤5：打乱或反转显示顺序
```

### 6. 重抽会排除刚刚出现的选项

旧版重抽逻辑会重新计算奖励权重，并将上一轮已经出现的选项传入排除列表。也就是说，重抽不是简单重新掷一次完全相同的池，而是至少在这一轮中避免立即重复原来的奖励。

这对概率影响很大。例如某件高权重武器刚刚出现但被玩家重抽后，它可能在该次重抽中直接变成0概率。

## 二、旧版概率模型可以写成什么公式

设当前游戏状态为 (s)，经过过滤后的候选集合为：

[  
E(s)  
]

候选 (i) 的有效权重可写成：

# [  
w_i(s)

r_i  
\times l_i(s)  
\times m_i(s)  
\times a_i(s)  
]

其中：

- (r_i)：配置中的 `rarity`；
    
- (l_i(s))：幸运值修正，只有部分项目受幸运影响；
    
- (m_i(s))：模式、角色或特殊事件修正；
    
- (a_i(s))：是否可用，通常是0或1。
    

单次权重抽取：

[  
P(i\mid s)=\frac{w_i(s)}{\sum_{j\in E(s)}w_j(s)}  
]

若要抽取 (k) 个不重复选项，则第二次抽取时应移除第一次选中的权重：

# [  
P(j\mid i,s)

\frac{w_j(s)}  
{\sum_{x\in E(s)}w_x(s)-w_i(s)}  
]

旧代码虽然采用“重复就拒绝并继续抽”的写法，但其成功接受的序列分布等价于这种加权无放回抽样。

真正的“某物品出现在整个升级页面中的概率”必须把所有可能顺序相加，不能简单使用：

```text
单抽概率 × 选项数量
```

## 三、为什么旧版文件这么容易查

旧 Phaser/Electron 版本的大量数据和逻辑曾打包在：

```text
resources/app/.webpack/renderer/main.bundle.js
```

公开的解析工具会直接读取这个文件，提取角色、武器、被动、关卡等配置，其中明确包含武器和被动的 `rarity` 字段。

这条路线现在仍有价值，因为它提供了一个可以完整复现的历史基线：

1. 奖励池怎么初始化；
    
2. 权重怎么计算；
    
3. 幸运怎么介入；
    
4. 多选项怎么生成；
    
5. 重抽和放逐怎么改变池子。
    

但是它不能自动证明2026年当前版本仍然逐行使用同一套实现。

## 五、当前版本的实际调查流程

### 第一步：固定游戏版本

先记录：

```text
游戏版本号
Steam构建时间或Build ID
主要DLC状态
使用的平台
是否开启合作模式
```

概率系统可能随补丁改变。必须让每份结论对应一个明确版本，而不是笼统写“《吸血鬼幸存者》的概率”。

只对自己合法取得的游戏文件进行研究，不公开分发提取出的完整代码、资源或程序集。

### 第二步：复制安装目录作为研究副本

不要直接在正常游玩的目录中反复修改。

建议目录：

```text
VS_Research/
├─ original/          原始备份
├─ working/           安装模组和测试
├─ decompiled/        反编译结果
├─ extracted_data/    导出的配置
├─ runtime_logs/      运行日志
└─ reports/           概率结论
```

### 第三步：用 MelonLoader 获取运行时接口

当前的社区技术参考使用 MelonLoader，并要求引用：

```text
Il2CppVampireSurvivors.Runtime.dll
Il2CppVampireSurvivors.PhaserPort.dll
MelonLoader assemblies
Unity assemblies
```

技术资料也明确要求准备 IL2CPP 反编译程序集。

MelonLoader 会建立模组、插件和日志目录，适合加载一个只记录数据、不修改游戏结果的观察模组。

### 第四步：用 ILSpy 搜索关键类和方法

优先搜索：

```text
LevelUpFactory
GetLevelUp
GetAvailable
GetRandom
CalculateWeight
WeightedStore
PullExisting
PullEvolution
Reroll
Banish
Seal
rarity
dropRateAffectedByLuck
excludeWeapon
LootManager
TreasureFactory
```

不要先从升级界面 UI 入手。UI 通常只是显示最终结果，真正的池子构建和抽取位于 `LevelUpFactory`、数据管理器及装备门面系统中。

公开模组参考已经展示过对 `LevelUpFactory` 方法进行 Harmony Patch 的方式，说明这是可操作的挂钩点。

### 第五步：若程序集只有类型签名，使用 Cpp2IL

IL2CPP 会把原始 C# 编译为原生代码，因此普通反编译有时只能看见类名、字段和空方法。

Cpp2IL 的作用就是把 Unity IL2CPP 构建尽可能恢复成可供 ILSpy 阅读的托管程序集。其官方说明也明确指出：恢复出的代码可能较乱，但通常仍能判断方法的实际行为，并建议使用 ILSpy查看。

基本调用方式是：

```powershell
Cpp2IL-Win.exe --game-path="你的游戏安装目录"
```

工具会尝试自动识别 Unity 版本和所需文件，并把结果输出到 `cpp2il_out`。

### 第六步：用 AssetRipper 提取配置数据

Cpp2IL主要用于代码逻辑；AssetRipper更适合检查：

```text
ScriptableObject
JSON
Addressables
武器配置
被动配置
角色配置
DLC内容组
隐藏与解锁字段
rarity权重
排除列表
```

AssetRipper用于分析Unity游戏文件并恢复原生Unity资源结构，当前工具声明支持到Unity 6000系列。

需要把“代码”和“数据”分开研究：

```text
代码回答：怎样抽
配置回答：抽什么、权重多少
```

### 第七步：写一个只记录、不改结果的运行时探针

最有效的方法并不是完全依赖静态反编译，而是让游戏在每次升级时输出：

```text

角色
当前等级
Luck

已持有被动与等级

每个候选的基础rarity
每个候选的最终有效权重
已有装备预填结果
普通池每次随机抽取结果
重复拒绝记录
```

### 第八步：用统计试验验证反编译结论

固定同一个游戏状态，执行大量奖励生成：

```text
最低：10,000次
较可靠：100,000次
低概率项目：1,000,000次
```

然后比较：

```text
理论概率
运行时观察频率
95%置信区间
理论值与实测值偏差
```

若理论与实测不符，通常说明遗漏了以下某一层：

- 幸运修正；
    
- 已有装备优先；
    
- 角色专属加权；
    
- 新武器保底；
    
- DLC内容组；
    
- 当前槽位限制；
    
- 封印或放逐；
    
- 重抽排除；
    
- 隐藏保底计数器；
    
- 服务于合作模式的同步随机数。

## 六、其他类似游戏该怎么选

调查顺序不应该只看游戏知名度，而要看代码可获得性。

### 第一优先：可读的开源重实现

`emoji-survival-game` 中有一份可读的 TypeScript `LevelUpFactory`，完整实现了：

- `rarity`累计权重；
    
- 武器和被动槽限制；
    
- 前3级武器优先；
    
- 已有装备升级倾向；
    
- 3或4个选项；
    
- 不重复奖励。
    

它非常适合作为算法教材和 ProjectVL 的第一版仿真参照。

但它是重实现，不是当前《吸血鬼幸存者》官方代码，因此应该标记为：

```text
旧版机制的可读复现
```

而不是：

```text
当前官方版本的绝对事实
```

### 第二优先：旧 Phaser 版《吸血鬼幸存者》

优点是逻辑和配置都曾集中在 JavaScript bundle 中，最容易做完整还原。

适合研究：

- 升级池；
    
- 幸运；  
    -武器与被动权重；
    
- 宝箱；
    
- 进化；
    
- 光源掉落物；
    
- 重抽、跳过和放逐。
    

### 第三优先：Unity Mono类幸存者

若某游戏仍使用Unity Mono，通常可以直接查看：

```text
GameName_Data/Managed/Assembly-CSharp.dll
```

这比IL2CPP容易得多，往往可以直接在ILSpy中看到接近原始C#的代码。

### 第四优先：Godot游戏

Godot游戏的玩法脚本通常比IL2CPP更容易定位，尤其是其 `.gd` 脚本和资源配置。公开的Brotato模组已经能够继承和覆盖其商店脚本入口，例如 `res://ui/menus/shop/shop.gd`，说明从商店生成函数切入具有可行性。

但Brotato的商店系统与《吸血鬼幸存者》的升级三选一并不相同，更适合研究：

- 商品品质阶级概率；
    
- 武器池与道具池；
    
- 标签和武器类型加权；
    
- 锁定商品；
    
- 刷新费用；  
    -波次与品质概率成长。

## 七、对 ProjectVL 最有价值的研究产物

你的项目文件已经确认对应 GitHub 上的 ProjectVL。 当前连接到的仓库是 `SageLys/ProjectVL`。

不建议只整理一张“竞品权重表”。更有价值的是建立一个可重复使用的奖励池仿真框架：

```text
RewardPool/
├─ RewardCandidate
├─ RewardContext
├─ EligibilityRule
├─ WeightModifier
├─ ForcedOfferRule
├─ WeightedSampler
├─ RerollPolicy
├─ RewardPoolSnapshot
└─ MonteCarloSimulator
```

每次生成奖励时，系统都应输出：

```text
1. 原始池
2. 排除过程
3. 最终有效权重
4. 强制或保底分支
5. 每一步抽取结果
6. 最终展示概率
```

这样在S4成长曲线仿真中，就能直接回答：

- 某件关键装备第几波首次出现；
    
- 多少局会因为奖励池污染而无法成型；
    
- 增加一个新卡型后，旧卡型的出现率下降多少；
    
- 三选一改四选一对构筑成功率影响多大；
    
- 保底、定向掉落和高星直掉分别需要多强；
    
- 封印槽、重抽次数对玩家控制力的真实贡献。
    

## 最终判断

目前可以确定三件事：

1. **旧版《吸血鬼幸存者》的升级池核心算法已经足以还原和复现。**
    
2. **当前版的具体实现可以通过 MelonLoader＋Cpp2IL＋ILSpy＋AssetRipper＋运行时日志查清。**
    
3. **在没有当前游戏安装文件和明确版本号之前，不能负责任地声称旧版公式就是2026年当前版公式。**
    

对 ProjectVL，最合理的下一步不是继续泛泛搜集概率数字，而是建立一个“旧版吸血鬼幸存者奖励池复现器”，随后再用当前版本运行时日志逐项校正差异。

那么请根据公开的旧版代码，帮我整理一下随机奖励池概率计算的通用原则与启示

你要提炼的不是《吸血鬼幸存者》某一版的具体数字，而是从旧版公开代码中抽象出一套可用于设计类幸存者、roguelike、三选一奖励系统的通用模型。

最核心的结论是：

> 随机奖励池不是“按固定概率随机给奖励”，而是一个随玩家状态不断变化的条件概率系统。

它通常由五层组成：

# [  
\text{最终奖励}

\text{资格过滤}  
\rightarrow  
\text{特殊规则插入}  
\rightarrow  
\text{权重抽取}  
\rightarrow  
\text{多选项去重}  
\rightarrow  
\text{重抽与后处理}  
]

下面按原理解释。

---

## 一、第一原则：先决定“能不能出现”，再计算“多容易出现”

很多人设计奖励池时，会直接给每件物品填写一个概率：

```text
火球 20%
冰箭 15%
护盾 10%
```

这通常是不正确的。

旧版《吸血鬼幸存者》首先排除：

- 尚未解锁的内容；
    
- 进化武器；
    
- `rarity = 0` 的内容；
    
- 被封印或放逐的内容；
    
- 当前状态下不允许取得的内容；
    
- 槽位已经满，且玩家尚未持有的新装备。
    

只有通过这些资格判断的内容，才进入最终抽取池。公开代码中的初始化流程会将进化、未解锁和零权重项目加入排除集合；之后重新计算权重时，还会检查武器槽和被动槽上限。

因此每件奖励应该有两类独立配置。

第一类是资格条件：

```ts
eligible(item, context): boolean
```

第二类是权重：

```ts
weight(item, context): number
```

概率公式应写成：

[  
P(i\mid s)=  
\begin{cases}  
\dfrac{w_i(s)}{\sum_{j\in E(s)}w_j(s)}, & i\in E(s)\  
0, & i\notin E(s)  
\end{cases}  
]

其中：

- (s) 是当前游戏状态；
    
- (E(s)) 是当前合格候选集合；
    
- (w_i(s)) 是候选的有效权重。
    

### 启示

资格和权重必须分开。

不要使用“把不合格物品的权重临时改成0”作为唯一实现。因为策划和测试人员需要明确知道：

```text
这个物品为什么没出现？
```

可能的原因包括：

- 未解锁；
    
- 槽位已满；
    
- 已达到最大等级；
    
- 被玩家放逐；
    
- 当前阶段未开放；
    
- 不符合角色或构筑标签；
    
- 被同类互斥规则排除。
    

这些原因在数值调试中比最终概率本身更重要。

---

## 二、第二原则：`rarity`通常是相对权重，不是百分比

旧版武器配置中存在类似数值：

- Whip：100
    
- Magic Wand：100
    
- Cross：80
    
- Garlic：70
    
- Pentagram：60
    
- Peachone：50
    
- Bone：1
    

这些数值是相对权重，不是100%、80%或1%的出现概率。

假设当前合格池只有四个奖励：

|奖励|权重|
|---|--:|
|A|100|
|B|80|
|C|50|
|D|20|

总权重为：

[  
W=100+80+50+20=250  
]

单次抽取概率为：

[  
P(A)=100/250=40%  
]

[  
P(B)=80/250=32%  
]

[  
P(C)=50/250=20%  
]

[  
P(D)=20/250=8%  
]

旧代码采用的是累计权重法：

1. 计算累计权重；
    
2. 生成 ([0,W)) 内的随机数；
    
3. 选择第一个累计权重大于随机数的候选。
    

公开实现中，`calculateWeights` 建立累计权重列表，`GetRandomWeightedWeaponOrPowerup` 再从中抽取。

### 启示

奖励权重具有三个重要性质。

第一，整体乘以相同倍数不会改变概率。

```text
100 / 80 / 50
```

和：

```text
10 / 8 / 5
```

概率完全相同。

第二，一个奖励的概率取决于其他所有合格奖励。

同样是权重100：

```text
池中总权重200 → 50%
池中总权重500 → 20%
池中总权重1000 → 10%
```

第三，新增内容会稀释旧内容。

即使旧奖励权重一个数字都没改，只要往池子中加入更多候选，它们的实际出现率就会下降。

这就是典型的“奖励池膨胀”或“内容稀释”。

---

## 三、第三原则：玩家看到的是一组奖励，不是一次独立抽取

在三选一系统中，玩家真正关心的是：

> 某件奖励出现在这一整页中的概率是多少？

而不是：

> 单次抽卡时抽到它的概率是多少？

旧版代码会不断抽取，直到组成若干个不重复选项。普通情况下为3个，幸运值可能让选项数量增加到4个。

这相当于加权无放回抽样。

假设候选权重仍是：

```text
A = 100
B = 80
C = 50
D = 20
```

单抽时：

[  
P(A)=40%  
]

但是三选一页面中A至少出现一次的概率，不是：

[  
40%\times3=120%  
]

正确算法需要考虑每次抽取后分母发生变化。

A不出现的情况，只可能是B、C、D三个全部被抽中。计算所有可能顺序后：

[  
P(A\text{ 出现在三选一中})\approx93.25%  
]

因此：

- 单抽概率：40%
    
- 三选一页面出现概率：约93.25%
    

这是两个完全不同的指标。

### 启示

策划表中至少要区分以下概率：

```text
单槽抽中概率
整页至少出现一次的概率
整页出现且处于第一个位置的概率
连续N次升级均未出现的概率
在指定时间前首次出现的概率
```

其中最有设计价值的通常是：

[  
P(\text{在前N次选择中至少出现一次})  
]

而不是静态单抽概率。

---

## 四、第四原则：多选项生成并不一定是纯粹的统一抽池

旧版《吸血鬼幸存者》的升级页面不是简单地从同一个池里连续抽三次。

它会先尝试加入已有装备的升级，然后再从普通池中补足剩余选项。公开代码中，系统会两次调用“已有装备”选择逻辑，若结果有效且不重复，就预先放入奖励页面。

更接近以下流程：

```text
1. 尝试选一个已有装备升级
2. 再尝试选一个已有装备升级
3. 从普通加权池补足剩余选项
4. 拒绝重复候选
5. 返回最终选项
```

因此最终三选一可以由不同来源组成：

```text
槽位1：已有装备升级分支
槽位2：已有装备升级分支
槽位3：普通权重池
```

它不是：

```text
槽位1～3：全部来自同一个池
```

### 启示

奖励页面最好设计成多个“槽位角色”，而不是一个统一随机函数。

例如：

```text
槽位A：成长连续性槽位
优先提供已有装备升级

槽位B：构筑扩展槽位
优先提供新武器或新被动

槽位C：自由随机槽位
从所有合格内容中加权抽取
```

这种结构比单纯提高某些权重更容易控制体验。

因为玩家通常同时需要两种东西：

- 继续强化已经形成的构筑；
    
- 获得新的构筑方向。
    

如果全部选项都来自同一权重池，很容易出现两种极端：

```text
全是已有装备升级，缺乏新鲜感
全是新装备，原有构筑迟迟无法成型
```

---

## 五、第五原则：奖励池需要承担隐性的进度保护

旧代码在玩家等级不高于3级且武器槽未满时，会优先只从真正的武器中抽取，而不是把武器和被动混在一起。

这是典型的新手阶段保护：

```text
前期最重要的不是完全公平的随机，
而是确保玩家尽快获得基础战斗能力。
```

如果初期把攻击、经济、防御、辅助全部放进统一池，玩家可能连续获得：

- 拾取范围；
    
- 移速；
    
- 幸运；
    
- 金币增益；
    

却没有足够的攻击武器。

数学上随机没有错误，但体验上可能直接导致开局失败。

### 启示

随机系统的目标不是“保持统计中立”，而是“维持可玩的状态空间”。

常见保护规则包括：

- 前几次至少出现一个攻击型奖励；
    
- 首个被动之前保证一定数量武器；
    
- 低血量时增加生存奖励候选；
    
- 某构筑核心长期不出现时逐步增加权重；
    
- 玩家缺少某种必要功能时，提高对应类别权重；
    
- Boss前确保玩家至少获得一次关键成长机会。
    

这种机制不一定要表现为硬保底，也可以表现为软修正：

[  
w_i'=w_i\times m_i(s)  
]

例如：

```text
当前没有远程攻击：
远程武器权重 × 1.5

当前武器数量不足：
新武器权重 × 2.0

当前防御明显不足：
防御类权重 × 1.3
```

---

## 六、第六原则：已有装备升级需要独立控制

旧版存在一个“已有装备优先”的概率分支，其概率随等级奇偶和幸运值变化。公开代码中基础值为0.3，偶数等级会乘以2，同时还叠加幸运修正。

这表明系统没有把“已有装备升级”和“获得新装备”完全交给同一个权重池。

原因很清楚：

- 新奖励提供构筑扩展；
    
- 已有奖励升级提供成长确定性；
    
- 两者在体验上承担不同职责。
    

### 启示

应该显式定义一个“构筑收敛率”。

例如：

# [  
P(\text{已有装备升级})

f(\text{当前等级},\text{已有装备数},\text{未满级数},\text{幸运})  
]

一个实用的通用模型可以是：

# [  
p_{\text{existing}}

\operatorname{clamp}  
\left(  
p_0  
+  
a\cdot\frac{\text{已占槽位}}{\text{槽位上限}}  
+  
b\cdot\frac{\text{未满级装备数}}{\text{已持有装备数}}  
,  
p_{\min},  
p_{\max}  
\right)  
]

直观含义是：

- 构筑越接近成型，越容易继续升级现有装备；
    
- 早期更愿意给新装备；
    
- 中后期逐渐推动构筑收敛；
    
- 仍保留一定新内容出现机会。
    

这比简单设置“所有已有装备权重翻倍”更可控。

---

## 七、第七原则：幸运值不一定只是乘权重

旧版幸运值至少会影响：

- 是否增加第4个奖励选项；
    
- 已有装备优先分支的触发概率；
    
- 部分受幸运影响的内容权重。
    

因此幸运并不是一个单一的：

[  
w_i'=w_i\times Luck  
]

它更像是同时影响多个随机子系统。

例如选项数量判断为：

[  
P(\text{第四选项})=1-\frac{1}{Luck}  
]

当Luck为1时，没有额外选项；Luck提高后，第4个选项出现率逐渐增加。

### 启示

“幸运”应该被拆解为明确效果，而不是模糊地影响“一切随机”。

可以分成：

```text
稀有奖励幸运
选项数量幸运
掉落数量幸运
已有装备升级倾向
宝箱品质幸运
暴击幸运
特殊事件幸运
```

否则会出现两个问题。

第一，玩家无法理解幸运有什么用。

第二，策划无法预测幸运的真实价值。

尤其是“增加一个选项”非常强，因为它不仅增加奖励数量，还提升玩家选择权。其价值通常远高于把某个稀有奖励的权重提高10%。

---

## 八、第八原则：放逐、封印、重抽本质上都是操纵条件概率

这三个机制表面不同，但数学本质一致。

### 放逐

永久或长期移除一个候选：

[  
E'(s)=E(s)\setminus{i}  
]

### 封印

在进入一局之前，从基础池中移除候选。

### 重抽

重新执行奖励生成过程，可能同时排除上一轮结果。

旧版重抽代码会重新计算排除后的权重池，并避免重新出现上一轮的部分选项。

### 启示

玩家控制随机性的核心，不只是“再抽一次”，而是改变后续分母。

假设池中总权重为1000，玩家封印了三个权重100的低需求奖励，那么某权重50的核心奖励概率会从：

[  
50/1000=5%  
]

提高到：

[  
50/700\approx7.14%  
]

提升幅度不是2.14个百分点而已，而是相对提升：

[  
\frac{7.14%-5%}{5%}\approx42.8%  
]

这说明移除候选的价值会随池子结构显著变化。

设计重抽、封印和放逐时，不能只按次数估值，还要考虑：

- 被移除候选的总权重；
    
- 奖励池大小；
    
- 页面选项数量；
    
- 是否允许重抽重复；
    
- 是否保留已有装备优先槽位；
    
- 重抽后是否启动新的保底。
    

---

## 九、第九原则：随机奖励系统需要“拒绝重复”，但拒绝方式会改变分布

旧代码生成多个奖励时，会检查新抽到的内容是否已经存在于当前选项列表中；重复则拒绝，继续抽取。

这种做法看似只是UI去重，实际上会改变整页概率。

高权重物品：

- 很容易在第一次被抽中；
    
- 之后再抽到时会被拒绝；
    
- 其被拒绝的权重等价于重新分配给其他候选。
    

因此低权重候选在第二、第三槽位的有效机会，会比单抽公式更高。

### 启示

需要明确多选项系统使用哪种抽样模型。

常见方案有三种。

#### 方案A：加权无放回

抽中后从池中移除。

优点：

- 数学清晰；
    
- 不会重复；
    
- 性能稳定。
    

#### 方案B：有放回抽取，重复则拒绝

旧版代码更接近此类实现。

优点：

- 实现简单；
    
- 结果近似加权无放回。
    

缺点：

- 候选极少时可能大量循环；
    
- 需要设置最大尝试次数。
    

#### 方案C：允许重复，但重复转化为升级或数量

适合卡牌、资源包等系统，但不适合普通三选一装备界面。

对于ProjectVL，建议直接使用显式的加权无放回抽样，不要依赖反复拒绝重复来实现。

---

## 十、第十原则：奖励概率必须随“当前局面”计算，不能预先写死

同一件奖励在不同状态下，概率可能完全不同。

例如某武器基础权重100：

|当前状态|出现概率|
|---|--:|
|未解锁|0|
|被封印|0|
|新武器槽已满且未持有|0|
|已持有且未满级|大于0|
|已满级|0|
|前3级武器保底池|可能显著提高|
|触发已有装备优先分支|进一步提高|

所以正确问题不是：

```text
这把武器的出现概率是多少？
```

而是：

```text
在角色等级L、已有装备集合H、槽位状态C、
幸运值K、放逐集合B、当前奖励阶段T下，
这把武器出现在这一页中的概率是多少？
```

### 启示

策划工具必须支持“状态快照”。

推荐的计算输入至少包括：

```ts
interface RewardContext {
  playerLevel: number;
  luck: number;

  ownedWeapons: OwnedItem[];
  ownedPassives: OwnedItem[];

  maxWeaponSlots: number;
  maxPassiveSlots: number;

  unlockedIds: Set<string>;
  sealedIds: Set<string>;
  banishedIds: Set<string>;

  previousOffers: string[];
  rerollCount: number;

  stage: number;
  wave: number;
  timeSeconds: number;
}
```

没有状态输入的“奖励概率表”只能用于非常粗略的初始检查。

# 对设计最重要的六条启示

## 1. 不要设计一个巨大的统一池

将所有内容放在同一个池中，会导致：

- 新内容稀释旧内容；
    
- 构筑难以成型；
    
- 功能类别失衡；
    
- 新玩家可能拿不到必要攻击能力；
    
- 后期大量满级或不可用项目反复被过滤。
    

更好的结构是分类池：

```text
武器池
被动池
已有装备升级池
稀有奖励池
进化池
资源补偿池
特殊事件池
```

奖励页面再按规则从多个池中组合。

## 2. 区分“探索”与“收敛”

随机奖励系统的两个核心目标是：

```text
探索：提供新方向
收敛：让已有构筑成型
```

早期应偏向探索，中后期应逐渐偏向收敛。

可以设计一个随进度变化的比例：

|阶段|新奖励|已有奖励升级|
|---|--:|--:|
|前期|70%|30%|
|中期|45%|55%|
|后期|20%|80%|

这比所有阶段使用同一概率更符合构筑节奏。

## 3. 页面概率比单抽概率更重要

真正应该验收的是：

```text
某件奖励在一次三选一中出现的概率
在前5次升级中至少出现一次的概率
构筑核心在第几波前出现的概率
连续N次不出现的概率
```

而不是只看 `weight / totalWeight`。

## 4. 新增内容必须重新评估池稀释

每次加入新奖励，都应该重新计算：

```text
旧核心奖励页面出现率下降多少
平均首次出现时间延后多少
构筑完整率下降多少
重抽价值提高多少
玩家需要多少封印槽才能抵消膨胀
```

否则内容越更新，构筑体验越不稳定。

## 5. 保底最好作用于规则层，而不是粗暴修改基础权重

与其永久提高某件物品的权重，不如建立状态修正规则：

```text
连续5次未见攻击武器：
攻击池权重 × 2

连续8次未见当前构筑核心：
核心权重逐步增加

玩家尚无输出装备：
至少保留一个输出槽位
```

这样不会长期扭曲整个池子的基础分布。

## 6. 必须通过仿真验收，而不能只靠公式

多选项、已有装备优先、拒绝重复、幸运、重抽和保底叠加后，手算会迅速变得复杂。

应该用Monte Carlo仿真统计：

```text
10万～100万局
```

输出：

- 各奖励首次出现波次；
    
- 各奖励整页出现率；
    
- 各构筑完成率；
    
- 各星级期望数量；
    
- 连续未出现分布；
    
- 重抽和封印的边际价值；
    
- 池子膨胀前后差异。

# 可直接用于ProjectVL的通用流程

- 玩家开始合成、装备后，逐步向已经形成的构筑收敛；
    
- 中后期仍按固定节奏提供少量偏离当前构筑的调整机会；

## 一、当前代码实际在做什么

目前普通掉落分成两层：

1. `rollDropOnKill` 判断是否产生掉落；
    
2. `spawnGroundDrop` 从 11 张技能卡中完全等概率选一种。
    

当前代码相当于：

```ts
if (dropRollSuccess) {
  type = allCards[randomIndex];
}
```

`CARD_KEYS` 是一份手工维护的 11 卡硬编码数组；只要没有传入 `forcedType`，就直接均匀抽取。因此每种卡在一次成功掉落中的条件概率都是：

[  
P(i\mid 已产生掉落)=1/11\approx9.09%  
]

玩家拥有多少张某类型卡、合成过多少次、有没有装备、处于第几波，目前全部不影响卡型。

普通敌人的基础掉落率为 27%，封顶95%；普通掉落当前固定为1★。游戏采用二合、最高6★、7个手牌格、3个装备格，3★才能装备。

当前 `GameState` 只有全局 `merges`，没有“各卡型合成次数”“各卡型最高达到星级”“各卡型出现次数”等数据；每次合成也只是给全局 `state.merges` 加一。因而代码目前无法判断“玩家本局主要在合成哪种卡”。

### 当前均匀随机并不能可靠完成初期教学

第1波预算配额为：

[  
51+1\times52=103只  
]

若假设全部被击杀、不计赏金敌人与技能掉率加成，则预计产生：

[  
103\times27%\approx27.8次普通掉落  
]

但均匀独立抽取下，即使恰好出现28次掉落，全部11种技能都至少出现一次的概率也只有约41.6%；把掉落次数本身的波动计入后，约为40.2%。第1波的规模来自当前预算配置。

更直观地说：

- 前10次成功掉落，平均只见到约6.76种卡；
    
- 前20次全部11种都见过的概率只有约11.3%；
    
- 前30次全部见过的概率也只有约49.2%。
    

因此，“前期掉落很多”不等于“玩家一定能接触完整卡池”。

## 二、《吸血鬼幸存者》原则需要怎样迁移

参考资料的核心原则是：随机奖励不是固定概率表，而是随局面变化的条件概率系统；同时应区分探索与构筑收敛。

但本项目不能直接照搬三选一页面。

### 三选一系统

一次升级同时展示多个槽位，可以明确安排：

- 一个已有装备升级；
    
- 一个新方向；
    
- 一个自由随机项。
    

玩家在同一时刻横向比较。

### ProjectVL 的持续即时掉落

每次击杀最多出现一个卡牌掉落，选项被分散在时间轴上。玩家通过以下动作进行选择：

- 是否点击拾取；
    
- 是否让它过期；
    
- 是否腾出手牌空间；
    
- 是否继续合成；
    
- 是否消耗或装备。
    

因此，三选一中的“页面槽位”应迁移成：

> **连续若干次成功掉落构成一个滚动奖励页面。**

例如，每10次普通掉落中安排：

- 若干次探索型掉落；
    
- 若干次当前构筑强化掉落；
    
- 固定少量调整型掉落；
    

然后打乱这些掉落角色的顺序。

这比每次独立做一次“70%主流、20%冷门、10%随机”的骰子更适合本项目。独立骰子即使调整概率为20%，仍可能连续十几次没有调整牌；角色袋则能保证玩家持续得到调整机会。

## 三、推荐机制：时间序列角色袋

建议新增一个 `NormalDropDirector`，它只负责普通、快速和坦克敌人成功掉落后的卡型选择。

一次普通掉落的完整概率应写成：

# [  
P(i\mid 击杀状态)

P(产生掉落\mid 状态)  
\times  
P(i\mid 已产生普通掉落,状态)  
]

前一项继续由现有 `totalDropChance` 控制。

后一项改由掉落导演控制。

### 1. 每10次成功普通掉落生成一个角色袋

建议首版参数：

|构筑成熟度|探索型|主线强化型|调整型|
|---|--:|--:|--:|
|初期|6|3|1|
|中期|3|5|2|
|后期|1|7|2|

不是按波次硬切三个阶段，而是计算一个连续的构筑成熟度 (M)。

建议初版公式：

[  
M=\operatorname{clamp}\left(  
0.25\cdot\frac{总合成次数}{10}  
+  
0.35\cdot\frac{本局最高到达星级-1}{3}  
+  
0.40\cdot\frac{已装备类型数}{2},  
0,1  
\right)  
]

各项分别封顶为1。

然后：

```text
主线强化数量 = round(3 + 4M)
调整数量     = round(1 + M)
探索数量     = 10 - 主线强化数量 - 调整数量
```

结果自然从 `6/3/1` 过渡到 `1/7/2`。

这样偏向性不是单纯由时间决定，而是由玩家是否真的进行了高星合成和装备选择决定。玩家在第3波仍没有形成构筑，系统就不会强行替他收敛；玩家很早做出3★并装备，偏向性就会提前增强。

### 2. 探索型掉落

探索型不做普通均匀随机，而是优先选择“本局普通掉落中出现次数最少”的类型。

流程：

```text
找到普通出现次数最少的卡型
→ 从并列最少的卡型中随机选择
→ 避免立即重复上一张
```

这实际上是一种动态洗牌袋，但不会像“前11张全部不重复”那样阻止玩家早期获得重复牌。

还需要一个启动保护：

> 在11种卡全部至少出现一次之前，每10次普通掉落至少保留5个探索角色。

这样前20次成功普通掉落中一定存在至少11个探索位置，能够硬性保证全部11种技能得到一次展示；剩余位置仍可提供重复牌，避免玩家迟迟无法开始合成。

### 3. 主线强化型掉落

主线强化不能只看“当前拥有几张”，否则最初随机拿到的一张1★就会触发正反馈，把偶然开局误认为玩家选择。

建议为每种卡计算构筑投入分：

[  
S_i=  
当前持有折算量  
+  
0.5\times\min(该类型合成次数,8)  
+  
装备加成  
]

其中：

# [  
当前持有折算量

\sum 2^{星级-1}  
]

例如：

- 1★折算1；
    
- 2★折算2；
    
- 3★折算4；
    
- 4★折算8。
    

装备加成建议：

```text
已装备3★：+6
每高于3★一级：再+2
```

于是：

```text
3★装备卡：当前量4 + 装备加成6 + 历史合成分
普通1★手牌：当前量1
```

玩家的明确装备选择会显著高于偶然拿到的零散卡，但历史合成次数只作为次要信号，不会永久锁死早期构筑。

主线强化角色从投入最高的前3种卡中加权抽取：

[  
w_i=(S_i+0.5)^{1.25}  
]

同时建议：

- 最高权重与最低权重之比封顶为6:1；
    
- 手牌中已经存在同型1★时，权重乘1.5，帮助当前普通1★掉落立即促成合成；
    
- 没有任何构筑投入时，主线强化角色退化为“优先匹配当前手牌中的1★”，仍没有候选时退化为探索型。
    

这样初期的“主线”主要帮助玩家完成第一批2★和3★；中后期才真正转化为构筑偏向。

### 4. 调整型掉落

调整型负责提供玩家本局投入较少的卡牌。

建议规则：

1. 按构筑投入分排序；
    
2. 排除投入最高的前2种；
    
3. 从其余类型中选取投入最低的一半；
    
4. 使用与投入分成反比的权重；
    
5. 优先选择最近较久没有出现的类型。
    

近似公式：

[  
w_i^{pivot}=\frac{1}{1+S_i}  
]

后期每10次普通掉落固定安排2次调整型，而且两个调整位置应分别放在角色袋的前半段和后半段，避免它们恰好挤在一起。

这会形成一个可感知的体验：

```text
主流类型持续出现
→ 玩家能够推进高星合成
→ 每隔几次又会出现一张明显不同的牌
→ 玩家可以忽略，也可以借此启动转型
```

### 5. 反连抽保护

建议普通掉落同类型最多连续出现2次。

第三次若仍选中同型：

- 从当前角色的其他候选中重新选择；
    
- 没有其他合法候选时才允许继续重复。
    

这不是为了让分布平均，而是为了避免即时地面掉落连续刷出完全相同的视觉结果。

## 四、不同掉落来源必须分开

当前 `spawnGroundDrop(..., forcedType = null)` 同时承担了多种来源：

- 普通敌人掉落；
    
- Boss必掉；
    
- 技能生成的额外掉落；
    
- 赏金奖励；
    
- 调试生成。
    

这会导致只要直接修改 `spawnGroundDrop` 的默认随机逻辑，Boss和“丰收”的额外空投也会无意间继承构筑偏向。

赏金系统已经有独立的奖励洗牌袋，并在奖励结算时强制指定卡型。

“丰收”的 `extraDrop` 原子目前同样通过 `forcedType=null` 触发均匀随机掉落；3★丰收还会提高总掉率与掉落时限。

因此建议明确区分掉落来源：

```ts
type CardDropSource =
  | 'normalKill'
  | 'bossKill'
  | 'bounty'
  | 'skillExtra'
  | 'debug';
```

首版规则：

|来源|卡型规则|
|---|---|
|normal / fast / tank 击杀|新动态掉落导演|
|Boss击杀|保持均匀随机|
|赏金奖励|保持赏金承诺的指定卡型|
|丰收等技能额外掉落|保持均匀随机|
|调试掉落|保持强制指定|

这样普通敌人负责构筑收敛；Boss、赏金和技能额外掉落继续作为相对独立的惊喜或调整渠道。

## 五、代码实施方案

### 第1步：把卡池来源改为配置驱动

当前 `CARD_KEYS` 在 `dropSystem.ts` 中手工硬编码了11张卡。技能本身已经由 `skills.json` 配置，README也规定技能数据应来自配置而非 core 中逐卡硬编码。

## 六、不建议采用的方案

### 1. 直接按最高星级乘权重

例如：

```text
拥有3★ → 对应掉率×3
拥有5★ → 对应掉率×5
```

问题是第一批随机重复会迅速形成正反馈，玩家还没做选择，系统就替玩家锁定了流派。

### 2. 只按波次切换概率

例如：

```text
第1波均匀
第2波已有卡×2
第4波已有卡×5
```

这没有响应玩家实际构筑进度。慢构筑玩家会被过早收敛，快构筑玩家又得不到足够支持。

### 3. 第一轮11张完全不重复

这能保证展示完整卡池，但7格手牌无法容纳11种，而且前11次没有重复意味着玩家几乎无法开始合成。探索保护必须和重复成长机会并存。

### 4. 每次独立投掷“20%调整牌”

### 5. 把所有掉落来源都改成构筑偏向

这会让赏金、Boss和丰收额外掉落都失去独立价值，也会显著放大丰收卡的正反馈。

- 调整型不得选择当前投入最高的前2种卡；
    
- 玩家将一个新类型升至3★并装备后，最迟在下一个角色袋内进入主线候选。

以下数值必须完全不变：

- 普通敌人总掉落率；
    
- 掉落率技能乘数；
    
- 掉落星级；
    
- 掉落持续时间；
    
- Boss必掉规则；
    
- 赏金奖励类型；
    
- 自动合成规则；
    
- 满手牌时的立即合成拾取规则。

实施时采用：

> **配置驱动卡池 + 按来源分流 + 10次掉落角色袋 + 玩家状态成熟度 + 各类型构筑投入分。**

# 一、当前代码的真实情况

## 1. 经验升级目前确实只是通用属性

现在升级三选一只有六类效果：

- 基础伤害
    
- 射速
    
- 治疗
    
- 最大生命
    
- 射程
    
- 经验获取
    

`applyPerk()` 通过一个固定 `switch` 直接修改 `damageBonus`、`fireRateBonus` 等全局字段，没有流派标签、构筑倾向或技能类型的概念。

配置中的升级选项也全部是这类通用强化。

因此当前玩家升级时并不是在“构筑”，而是在选择几种几乎对所有打法都同样有用的基础增益。你的判断是正确的。

## 2. 普通掉落已经有一套很好的“掉落导演”

最新代码已经实现了三种普通掉落角色：

- `discovery`：探索新卡
    
- `build`：支持当前构筑
    
- `pivot`：提供转型机会
    

系统还会依据玩家持有卡牌、装备卡牌、合成次数和最高星级计算每种具体卡的“投入分”。

成熟后，一袋十次掉落大致是：

- 1 次探索
    
- 7 次主构筑
    
- 2 次转型
    

并且已有防止连续同型掉落、保留全卡池曝光等保护机制。

所以不需要重写掉落系统。正确做法是：**给现有投入分增加一层“玩家主动选择的流派倾向”。**

## 3. Bounty 并不是每只精英单独掉落

这是需要修正理解的一点。

当前 Bounty 敌群成员被击杀时不会走普通掉落判定；只有整个 Bounty 敌群完成后，才会生成报价时承诺的指定卡和万能卡。

Bounty 的奖励卡型目前来自一个均匀洗牌的全卡池，只做了连续重复保护，没有读取玩家构筑。

因此这里要改变的不是“精英怪单体掉率”，而是：

> **Bounty 报价所承诺的奖励卡型分布。**

## 4. 当前 Boss 并不是真正的“波末 Boss 阶段”

目前只在第 3、5、8 波生成 Boss。

实现方式是：如果当前波属于 `bossWaves`，并且只剩最后一个出怪名额，就把该名额替换成 Boss。

这意味着 Boss 只是“该波最后加入出怪队列的敌人”，并不保证：

- 普通敌人已经全部死亡；
    
- Bounty 已经结束；
    
- Boss 不会与大批敌人同时在场；
    
- Boss 死亡后才进入波间休息。
    

所以不能只把 `bossWaves` 改成 `[1,2,3,4,5,6,7,8]`。那只是“每波最后一个出怪名额是 Boss”，不是“每波末尾的 Boss 战”。

## 5. 万能卡系统已经完整存在

当前万能卡按星级储存在独立背包中：

- 1★万能卡只能把一张1★卡升到2★；
    
- 2★万能卡只能把一张2★卡升到3★；
    
- 以此类推。
    

相关发放、拖拽使用、升级和自动合成逻辑已经实现，可以直接复用。

# 二、总体设计结论

建议把构筑系统拆成三个层级：

1. **流派标签层**：定义哪些卡属于哪些宽协同流派。
    
2. **流派倾向层**：记录玩家通过升级主动表达的方向。
    
3. **流派效果层**：让升级同时影响技能效果、普通掉落和 Bounty 奖励。
    

不要让升级直接指定某一张卡，也不要设计“选择穿透以后只给穿透卡”。

正确的关系应当是：

> 玩家选择“弹道强化”后，所有具有弹道标签的卡都获得收益，并且穿透、连锁闪电、分裂爆破等卡的出现概率一起提高。

这才是宽协同。

# 三、流派标签应该怎么设计

当前每张卡只有一个 `category`，值为：

- projectile
    
- control
    
- domain
    
- economy
    
- defense
    

但实际技能早已跨类别。例如连锁闪电同时具备弹道和减速，冲击同时具备控制和防御，荆棘同时具备防御、领域、持续伤害和处决。

因此建议：

- 保留现有 `category`，继续用于卡牌颜色、UI分类和主身份。
    
- 新增多值字段 `synergyTags`，专门用于构筑协同。
    

建议第一版只开放四条主流派：

|主流派|可以覆盖的现有卡|
|---|---|
|弹道|穿透、连锁闪电、分裂爆破|
|控制|冰霜、诱饵、冲击、连锁闪电、圣域|

`harvest` 目前是唯一经济卡，不适合作为独立主流派。建议暂时标为 `utility/economy`，作为通用辅助选项；等经济卡达到至少三张后，再开放经济流派。

## 1. 新增流派倾向状态

```ts
type BuildTag =

interface BuildState {
```

## 3. 第一批升级建议

第一版不需要做二三十个选项。先做八个主升级加两三个通用选项即可。

|流派|升级方向|宽协同对象|
|---|---|---|
|弹道|弹道和衍生弹伤害提高|穿透、连锁、分裂、榴弹等|
|弹道|弹跳、穿透、分裂等数量效果增强|所有多段弹道|
|控制|减速、冻结、眩晕、击退持续或强度提高|所有控制卡|

治疗、最大生命、经验收益可以保留，但应当归入 `utility`，不能继续占据升级系统主体。

## 4. 升级三选一不能继续纯随机

当前逻辑只是从所有未满层的升级中按权重抽三项。

建议改成有角色的三选一：

- 第一个选项：强化当前最高倾向流派。
    
- 第二个选项：桥接当前流派或支持当前持有卡牌。
    
- 第三个选项：转型或通用生存选项。
    

开局玩家尚未表达方向时，前三项应来自三个不同主流派，避免出现“伤害、射速、射程”这种没有真正路线区别的选择。

## 5. 玩家选择后必须快速看到反馈

仅仅改变后台概率不够。选择流派后，应保证：

- 清空现有普通掉落的角色袋，使新倾向立即生效；
    
- 接下来两次成功普通掉落中，至少有一次来自所选流派；
    
- 升级界面明确显示“此选择会提高哪些卡的出现倾向”；
    
- 后续 Bounty 报价较高概率展示该流派卡牌。
    

这能让玩家感知到：

> 我刚刚做出的选择，确实改变了这局游戏。

# 五、技能属性如何按流派强化

当前效果解释器本身是数据驱动的，这是非常适合扩展的基础。

不建议在每个技能执行时写：

```ts
if (cardType === 'pierce') ...
if (cardType === 'frost') ...
```

更合适的实现位置是效果解析阶段。

当前 `equippedBindings()` 已经同时拿到了：

- `card`
    
- `def`
    
- `binding`
    

然后再执行该绑定。

建议新增：

```ts
function applyBuildScaling(
  state: GameState,
  def: CardDef,
  bindings: BindingDef[]
): BindingDef[]
```

执行流程变为：

```ts
const baseBindings = resolveEquipBindings(def, card.star);
const scaledBindings = applyBuildScaling(state, def, baseBindings);
```

消耗态技能同理：

```ts
const baseTier = resolveConsumableTier(def, star);
const scaledTier = applyBuildScaling(state, def, baseTier);
```

这样有三个优点：

1. 不需要给每张卡写特殊判断。
    
2. 区域、子弹附加效果、召唤物等延迟效果在生成时就已经得到正确参数。
    
3. 双标签桥接卡可以分别接受不同属性强化。
    

必须按“效果原子”识别参数，不能看到所有名为 `ratio` 的字段就统一放大。因为当前代码中的 `ratio` 可能分别代表减速、易伤、伤害减免、持续伤害等完全不同的东西。

# 六、普通掉落如何读取升级选择

现有投入分继续保留，只需加入“主动流派倾向分”。

建议公式：

```ts
organicScore(type)
  = 当前已有的持有、合成、装备投入分

affinityScore(type)
  = 该卡所有 synergyTags 对应 affinity 的加权和

finalScore(type)
  = organicScore(type)
  + min(affinityScoreCap, affinityScore(type) * affinityScorePerStack)
```

第一版参数建议：

```json
{
  "affinityScorePerStack": 2.5,
  "affinityScoreCap": 6
}
```

关键限制：

- 只有 `build` 主构筑位读取流派倾向。
    
- `discovery` 探索位不读取。
    
- `pivot` 转型位不读取。
    
- 继续保留现有最大权重比和同型连续掉落限制。
    

这样玩家会明显更容易获得目标流派，但系统仍然不会把卡池锁死。

现有“前20次普通掉落覆盖全部11种卡”的测试也应继续通过。

# 七、Bounty 奖励怎么改

当前 Bounty 使用均匀奖励袋，因此玩家选了控制流，下一次 Bounty 仍可能等概率承诺任意卡。

建议将 `drawRewardType()` 改为：

```ts
selectBountyRewardType(state, rng)
```

推荐分布：

- 65%～75%：符合当前主要流派。
    
- 15%～20%：符合次要流派或桥接两条路线。
    
- 10%～20%：探索卡和转型卡。
    

在符合流派的卡中，再根据以下因素加权：

- 玩家是否差一张就能合成；
    
- 该卡是否已有投入；
    
- 该卡本局是否长期没有出现；
    
- 是否与上一次 Bounty 奖励重复。
    

报价生成后仍然冻结奖励卡型，不应因为玩家之后又选了升级而偷偷改变已经展示的奖励。当前代码已经具备“报价生成时冻结奖励”的结构。

## Bounty 不应继续稳定产出万能卡

当前每次完成 Bounty 默认同时产出：

- 一张指定卡；
    
- 一张万能卡。
    

如果每波 Boss 都稳定提供万能卡，Bounty 继续稳定提供万能卡会削弱 Boss 奖励的稀缺性和辨识度。

建议第一版直接设置：

```json

```

重新分工：

- 普通掉落：广泛、持续的构筑材料。
    
- Bounty：高风险、定向的流派卡。
    
- 波末 Boss：稳定、珍贵的万能卡。
    

三种奖励来源就会有明确区别。

# 九、Boss 数值必须同步重做

## 一、你原方案中的隐藏冲突

你希望同时满足：

- 敌人前期更弱；
    
- 出怪节奏不变；
    
- 掉落与升级概率不变；
    
- 操作手感不变。
    

这里需要区分“概率不变”和“实际发生时间不变”。

假设第一波普通怪原本需要 1 秒击杀，简单难度改成 0.5 秒：

- 每只怪的掉落率仍然是原来的概率；
    
- 每只怪提供的 XP 也没有变化；
    
- 每波总敌人数没有变化；
    
- 所以每波期望掉落总数、XP 总数不变；
    
- 但玩家会更早击杀敌人，因此掉落和升级会更早出现。
    

换句话说：

> 显著降低敌人 HP，必然会改变现实时间中的掉落密度和升级时间。

这不是 D 参数发生了变化，而是击杀速度发生了变化。

因此建议把“保持不变”定义为：

- 掉落概率不变；
    
- 掉落星级规则不变；
    
- 掉落存在时间不变；
    
- 拾取半径不变；
    
- 每只怪 XP 不变；
    
- 升级选项及概率不变；
    
- 每波敌人总量和类型构成不变；
    
- 允许简单难度下掉落和升级在时间轴上适度提前。
    

若连掉落时间轴也必须严格保持，那么就不能明显降低敌人 HP，只能降低敌人伤害。这样游戏会更不容易失败，但怪物不会显得“特别弱”。

## 二、推荐的难度结构

建议提供四档：

|难度|定位|
|---|---|

|困难|接近当前版本，但前两波略微缓和|

最重要的设计原则是：

不要复制成：

这种方案后续修改敌人时会产生四套配置漂移。

正确结构应是：

```text
基础敌人数值
× 当前波次原有成长
× 难度曲线倍率
× Bounty / Boss / 临时状态倍率
```

“地狱”难度的所有难度倍率均为 `1`，这样才能确保当前版本真正原样保留。

## 三、用曲线而不是直接改 `hpPerWave`

你的初步想法是降低 `hpBase`，再提高 `hpPerWave`。从结果上可行，但不适合实现多难度。

直接改 `hpBase/hpPerWave` 会产生几个问题：

- 每种怪物、每个难度都需要单独计算；
    
- Boss、Tank、Fast 的成长关系容易失控；
    
- 当前地狱基准容易被覆盖；
    
- 改总波数后曲线终点会变化；
    
- 策划很难理解某一波最终到底乘了多少。
    

建议使用归一化难度曲线：

```ts
const progress =
  totalWaves <= 1
    ? 1
    : (wave - 1) / (totalWaves - 1);

const multiplier =
  start + (end - start) * Math.pow(progress, power);
```

其中：

- `start`：第一波倍率；
    
- `end`：最终波倍率；
    
- `power`：曲线形状；
    
- `power = 1`：线性增长；
    
- `power > 1`：前期增长慢，后期增长快；
    
- `power < 1`：前期快速增长。
    

你想要的是“初期特别弱，后期更陡”，所以应使用约 `1.4–1.8` 的 `power`。

最终敌人 HP 计算应保持当前公式语义不变：

```ts
const rawHp = def.hpBase + wave * def.hpPerWave;
const finalHp = rawHp * difficultyHpMultiplier;
```

注意，当前代码快照中使用的是：

```ts
hpBase + state.wave * hpPerWave
```

而不是：

```ts
hpBase + (state.wave - 1) * hpPerWave
```

难度系统不应趁机修改这一语义，否则“地狱”也会发生数值变化。当前开发入口的即时调参逻辑同样直接使用这套公式。

```ts
const resolved = resolveEnemyStats(...);

```

这是本次实现中最容易遗漏的地方。

## 七、Bounty 和其他倍率的结算顺序

当前项目已经存在 Bounty 强化敌人的机制，因此难度倍率必须有固定顺序。

建议顺序：

```text
敌人基础值
→ 原有波次成长
→ 难度倍率
→ Boss / Bounty / 精英倍率
→ 局内减速、易伤、狂暴等临时状态
```

例如：

```ts
const baseHp =
  def.hpBase + wave * def.hpPerWave;

const difficultyHp =
  baseHp * difficultyHpMultiplier;

const bountyHp =
  isAcceptedBounty
    ? difficultyHp * bountyHpMultiplier
    : difficultyHp;
```

不要先应用 Bounty，再由简单难度整体压低，否则 Bounty 的危险性可能被过度削弱。

## 十、试玩验收标准

不要只检查通关与否。每档难度应比较：

|指标|用途|
|---|---|
|第一波受伤比例|判断初期是否过难|
|第一波首次突破时间|判断是否给玩家学习窗口|
|第一波进入危险区敌人数|判断压力是否仍然可见|
|普通怪 TTK|判断是否真的“弱”|
|Tank TTK|防止肉盾仍旧卡死前期|
|首个 Boss 受伤比例与击杀时间|判断第一次难度峰值|
|最终波受伤比例|判断后期曲线是否真正变陡|
|每分钟掉落数|检查 HP 降低带来的掉落提前|
|首次升级时间|检查升级节奏是否明显提前|
|总掉落数与总升级数|验证每波经济总量没有改变|

建议使用相对验收：

- 轻松第一波受伤量约为地狱的 20%–40%；
    
- 标准约为地狱的 40%–65%；
    
- 困难约为地狱的 65%–85%；
    
- 地狱必须与原版一致；
    
- 最终波的难度差距应明显小于第一波差距；
    
- 轻松和标准依旧必须出现危险区敌人，不能变成全程在屏幕边缘秒杀。
    

最后一点很重要。你的项目需要的是“更容易但仍能感受到压迫”，而不是简单地把所有怪物变成一碰就死。
