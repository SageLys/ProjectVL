# 二、当前代码实际存在的问题

## 1. 普通掉落总量仍是固定概率模型

当前普通敌人死亡时，只执行：

```ts
rng() < totalDropChance(...)
```

成功后才调用卡型导演决定掉哪张卡。也就是说，现有动态导演只解决“掉什么”，完全没有解决“每分钟掉多少”。

`totalDropChance` 的计算仍然是：

```ts
基础 dropChance × 装备掉率倍率
```

然后受统一概率上限限制。

当前基础值是 27%。

因此：

- 敌人杀得慢时，资源不足。
    
- 敌人杀得快时，资源爆炸。
    
- 玩家构筑越强，击杀效率越高，单位时间掉落反而越多。
    
- 固定概率无法稳定控制视觉负担和点击负担。
    

这正是必须改掉的核心。

## 2. 当前敌人数量增长极其陡峭

Budget 模式的每波配额目前是：

```text
51 + 波数 × 52
```

所以第 1–8 波的普通敌人配额分别是：

```text
103、155、207、259、311、363、415、467
```

同屏目标则是：

```text
5 + 波数 × 10
```

即：

```text
15、25、35、45、55、65、75、85
```

配置还允许最后阶段把目标乘以 3，最大同屏 100。

代码确实直接使用这些线性公式，并没有阶段概念。

因此当前曲线的基本逻辑是：

> 波数越后 → 敌人越多 → 击杀越多 → 27% 固定掉率产生越来越多掉落

这与你现在希望的“后两波怪物更少、个体更强、基本挂机”完全相反。

## 3. 当前全局平均掉率掩盖了后期过载

我按照项目 `simulateBudgetWave` 使用的同一简化口径复算了当前 Standard 难度：

- 使用基础炮台伤害、射速和射程。
    
- 使用普通敌人的预计存活时间。
    
- 不计算技能、玩家操作和复杂敌人构成。
    

该模型本身也明确说明它不考虑技能、掉落和玩家输入。

结果如下：

|波次|预计普通掉落|常规阶段预计掉落/min|
|---|--:|--:|
|1|27.8|约 30|
|2|41.9|约 51|
|3|55.9|约 64|
|4|69.9|约 75|
|5|84.0|约 75|
|6|98.0|约 76|
|7|112.1|约 78|
|8|126.1|约 79|

把 Boss 时间和波间休息也算进去后，全局数字大约是 47/min，看起来似乎只比 40 高一点。但这个平均值隐藏了真正的问题：

- 第一波资源偏少。
    
- 从第二波开始迅速超过目标。
    
- 中后期实际视觉和操作压力接近目标的两倍。
    

当前 `derivedMetrics` 也确实用“全局总敌人数 × 固定 dropChance”计算总掉落，再除以包括 Boss 和波间休息的总时间。它没有按波、阶段或掉落来源拆分。

所以现有面板中的“掉落/min”不能继续作为新方案的主要验收指标。

## 4. 现有卡型导演应该保留

现有 `normalDropTypePolicy` 已经具备较好的内层结构：

- 前期：探索位 6、主线位 3、调整位 1。
    
- 后期：探索位 1、主线位 7、调整位 2。
    
- 根据合成次数、最高星级和装备数量计算构筑成熟度。
    
- 成熟度由 0 到 1 平滑变化，不是突然切换。
    

具体实现也确实根据玩家的合成、星级和装备情况平滑插值。

因此不应该推翻它。

正确做法是：

- 三阶段导演决定：现在是否产生普通掉落，以及每分钟产生多少。
    
- 现有卡型导演决定：这次普通掉落应该是哪种卡。
    

这是两套不同职责的系统。

# 三、8 波还是 10 波

## 建议：正式基线继续使用 8 波

建议划分为：

|阶段|波次|主要任务|
|---|---|---|
|选择期|1–2|看见卡池、开始合成、确定初步方向|
|构筑期|3–6|集中发育、形成主构筑、完成关键升星|
|验证期|7–8|少量强敌检验战斗构筑，发放终局资源|

主要原因有四个。

### 原因一：当前目标本来就是 8–12 分钟

当前理论模型在基础炮台下已经能算出较长的总局长。实际技能会缩短战斗，但直接增加两个完整波次仍很容易把整局推向 12 分钟以上。

若添加 2 波后再整体压缩每一波：

- 选择期会被压缩。
    
- 每波 Boss 的存在感会下降。
    
- Bounty 出现窗口会缩短。
    
- 每波合成与升级节奏都要重调。
    
- 原本“保留 8 波发育”的优势会被缩波抵消。
    

### 原因二：增加总波数会改变现有难度曲线

现有难度倍率使用：

```text
(当前波 - 1) / (总波数 - 1)
```

把 8 波改成 10 波后，即使所有难度配置完全不变，原有第 2–8 波的敌人倍率也会变化。

这意味着增加两波并不只是“末尾多两波”，而会重新解释整条难度曲线。

### 原因三：Boss 奖励和终局奖励也会整体后移

当前每波都有 Boss，Boss 奖励星级和数量根据波数计算，最终波还有额外数量奖励。

改为 10 波后：

- 最终奖励从第 8 波移动到第 10 波。
    
- 第 7–8 波不再是最终强度位置。
    
- 原有奖励测试和参数都要重做。
    

### 原因四：前 6 波原则上可以提供足够的资源

按照建议值粗估：

- 选择期约 2 分钟 × 35/min ≈ 70 次普通掉落展示。
    
- 构筑期约 4.5–5 分钟 × 40/min ≈ 180–200 次。
    
- 验证期前共约 250–270 次普通掉落展示。
    
- 若拾取率为 70–80%，则实际拾取约 175–215 次。
    

考虑二合规则、现有构筑倾向导演、每波 Boss 万能卡和 Bounty 奖励，前 6 波并非天然发育不足。

真正要验收的是：

> 玩家进入第 7 波时，是否已经拥有足以接受验证的构筑，而不是是否经历了 8 个发育波次。

## 保留一个 10 波实验 variant

项目已经有 URL variant 和深覆盖基础设施，可以创建 10 波对照版本，而不污染正式基线。

建议：

- 正式基线：8 波，7–8 验证。
    
- 对照 variant：10 波，9–10 验证。
    
- 只有当 8 波版本无法达到“第 7 波构筑完成度”指标时，才考虑切换正式结构。
    

# 四、三阶段的第一版体验参数

以下是实施起点，不是最终定案。

## 1. 选择期：第 1–2 波

目标：

- 普通掉落基准：35/min。
    
- 同屏目标：约 6–10。
    
- P95 同屏建议不超过 14–16。
    
- 每波常规阶段：约 55–65 秒。
    
- 敌人配额起点：约 55–75。
    
- 每波 Bounty 最多 1 次。
    
- Boss 保留，但应是短收尾，不应成为主要失败来源。
    
- 卡型导演继续偏探索。
    

关键点是：

> 减少敌人，不等于减少资源到无法发育。

普通敌人击杀速度必须至少高于掉落目标。建议选择期保持约 50–60 次有效击杀/min，使 35 次掉落能够分布在这些击杀中。

若只有 30 次击杀/min，就算每只怪必掉，也无法达到 35/min。

## 2. 构筑期：第 3–6 波

目标：

- 进入构筑期后的前 15–20 秒，从 35 平滑升到 40/min。
    
- 此后保持约 40/min。
    
- 同屏目标逐步提高到约 14–28。
    
- 每波常规阶段约 65–80 秒。
    
- 敌人配额起点约 90–170，按波递增。
    
- Bounty 恢复当前主动决策功能。
    
- 卡型导演按现有成熟度逐步从探索转向主线。
    

这应当是全局唯一明显偏忙的阶段。

但这里的“忙”应主要来自：

- 掉落选择。
    
- 合成。
    
- 装备决策。
    
- Bounty 决策。
    

不应该来自 50–100 个敌人同时挤在屏幕上。

普通资源逻辑：

- 普通敌人掉落：关闭。
    
- 普通卡牌掉落率目标：不计算。
    
- Bounty 出价：关闭。
    
- 常规升级三选一：最好不再弹出。

- 1 个最终 Boss。
    
- 共 3 次强奖励掉落。


正好位于你提出的 4–6 次范围中间。

# 五、普通掉落不应再使用“动态概率”，而应使用“掉落节拍预算”

这是整个方案最重要的技术选择。

## 不推荐的方案

每波配置：

```text
第1波概率 35%
第2波概率 32%
第3波概率 25%
……
```

这种方案仍然取决于击杀速度。玩家战力变化后，每分钟掉落仍会漂移。

## 推荐方案：时间令牌桶

新增普通掉落控制器。

状态示例：

```ts
interface OrdinaryDropRateState {
  credit: number;
  activeRegularSeconds: number;
  shownThisWave: number;
  eligibleKillsThisWave: number;
}
```

在选择期和构筑期的常规战斗时间内，每帧积累掉落额度：

```ts
credit += targetDropsPerMinute / 60 * dt;
credit = Math.min(credit, carryCap);
```

普通敌人被击杀时：

```ts
if (credit >= 1) {
  credit -= 1;
  生成一次普通掉落;
}
```

然后继续调用现有的：

```ts
selectNormalEnemyDropType(...)
```

决定卡型。

## 为什么要限制额度积压

若一段时间没有敌人死亡，额度不能无限积累，否则下一批敌人死亡时会连续爆出大量掉落。

建议：

```text
carryCap = 1.25–1.75 次掉落
```

这样：

- 短暂击杀空窗不会永久损失产出。
    
- Boss、波间休息、暂停期间不会储存十几次掉落。
    
- 下一次击杀最多只产生短暂补偿，不会形成掉落瀑布。
    

## 只在有效常规战斗时间计时

以下时间不积累普通掉落额度：

- 波间休息。
    
- 暂停。
    
- Boss 单独阶段。
    
- 验证期。
    
- 游戏结束。
    
- 没有常规出怪资格的演出时间。
    

因此新的指标应叫：

```text
ordinary drops / active regular minute
```

而不是用整局时间作分母。

# 六、掉率加成技能的处理

当前 Harvest 3★和 5★会提供：

```text
掉率 ×1.25
掉落存在时间 ×1.25
```

6★则会在每波开始额外生成掉落。

建议明确口径：

- 35/min 和 40/min 是没有 Harvest 时的普通击杀掉落基线。
    
- `dropRateMul` 改为乘在“每分钟目标”上，而不是乘在单次击杀概率上。
    

例如：

```text
构筑期基础：40/min
Harvest 3★：40 × 1.25 = 50/min
```

这使 Harvest 仍然有明确价值。

同时必须把统计拆开：

- 普通击杀掉落。
    
- 技能额外掉落。
    
- Bounty 奖励。
    
- Boss 奖励。
    
- 验证奖励。
    

否则 Harvest、Boss 和 Bounty 会把普通掉率指标污染。

验证期中建议：

- `dropRateMul` 不再产生普通击杀掉落，因为普通掉落渠道已关闭。
    
- Harvest 的 `onWaveStart extraDrop` 可以保留，但建议自动收取或生成在炮台附近，避免重新制造点击疲劳。
    
- 它应作为技能效果单独统计，不计入验证期 5 次强奖励。
    

# 七、敌人曲线的实现方式

## 不再使用一条全局线性公式

当前接口只有：

```ts
waveQuota: { base, perWave }
targetOnScreen: { base, perWave }
```

类型定义也只允许这套线性结构。

建议改为：

```ts
type RunStage = 'selection' | 'build' | 'validation';

interface StagePlanConfig {
  selectionWaves: number;
  validationWaves: number;

  selection: RegularStageConfig;
  build: RegularStageConfig;
  validation: ValidationStageConfig;
}
```

阶段解析：

```ts
function stageForWave(wave: number, totalWaves: number): RunStage {
  if (wave <= selectionWaves) return 'selection';
  if (wave > totalWaves - validationWaves) return 'validation';
  return 'build';
}
```

这样即使测试 variant 改为 10 波，也会自动得到：

```text
1–2 选择
3–8 构筑
9–10 验证
```

## 选择期和构筑期使用独立曲线

建议每个阶段分别配置：

```ts

  waveQuota: CurveConfig;
  targetOnScreen: CurveConfig;
  checkInterval: number;
  batchMax: number;
  maxAlive: number;
  enemyHpMul: CurveConfig;
```

不要再让同一个 `perWave` 同时覆盖整局。

```ts

  enemies: ValidationEnemySpec[];

```

这样可以明确表达：

```text

```

而不是把：

```text

targetOnScreen = 2
```

硬塞进普通出怪系统。

# 十、验收标准

## 自动化验收

### 选择期

- 无 Harvest 时普通掉落：33–37/min。
    
- 有效击杀速度必须高于普通掉落目标。
    
- 普通掉落额度不会跨 Boss 或波间大量积压。
    
- 同屏和配额明显低于构筑期。
    
- 不因降低敌人数导致第 1–2 波基础资源断档。
    

### 构筑期

- 进入阶段后 20 秒内由 35 平滑到 40/min。
    
- 稳定区间：38–42/min。
    
- 强构筑提高击杀速度时，普通掉落/min 不随之翻倍。
    
- Harvest 3★基线约为 47.5–52.5/min。
    
- 普通卡型仍按成熟度向主构筑收敛。
    

### 验证期

- 普通击杀掉落为 0。
    
- Bounty offer 为 0。
    
- 第 7 波奖励拾取物为 2。
    
- 第 8 波奖励拾取物为 3。
    
- 两波总计 5。
    
- 强奖励不会过期。
    
- 峰值敌人数保持在少数个体范围。
    
- 不出现强制升级弹窗打断挂机观察。
    

## 实际游玩验收

“放弃 20–30%”不能靠代码单元测试证明，必须用真实玩家操作数据验证。

计算口径应为：

```text
普通掉落放弃率
= 普通过期数量
÷（普通拾取数量 + 普通过期数量）
```

不要把以下内容混进去：

- Boss 奖励。
    
- Bounty 奖励。
    
- 技能额外掉落。
    
- 验证奖励。
    
- 调试生成物。
    

还需要检查：

- 放弃是否来自“我不想要”。
    
- 是否来自“来不及点”。
    
- 是否来自“卡槽满了”。
    
- 是否来自“掉落图标难以辨认”。
    

只有第一种和部分第二种符合你的目标；大量卡槽满拒绝不应被误判为合理放弃。

## 二、6★万能卡目前实际上不可用

这是本次最重要的规则问题。

当前万能卡的定义不是“能够变成任意同星卡”，而是：

> 将万能卡拖到同星卡或装备上，使目标提升一星。

例如：

- 1★万能：1★ → 2★
    
- 4★万能：4★ → 5★
    
- 5★万能：5★ → 6★
    

卡牌最高为 6★，所以合法万能卡库存只有 1—5★。代码会直接拒绝 `star >= maxStar` 的万能卡；6★万能卡即使配置出来，拾取时也不会进入库存。

因此你的“Boss 万能卡递增到 6★”在当前规则下不能直接实施。

正确对应关系是：

- **Boss 万能卡最高应为 5★。**
    
- **5★万能卡就是制造 6★卡的奖励。**
    

若一定要出现真正的“6★万能卡”，必须先为其设计新功能，例如“转化为任意一张6★卡”。这已经不是数值调整，而是新增核心规则，不建议在当前验证阶段混入。

此外还有一个时机问题：最终 Boss 的奖励是在最终 Boss 被击杀后才生成，拾取后本局就结束。最终 Boss 掉落的6★或5★奖励没有后续战斗可以验证，只能影响结算展示。

所以高星能力必须主要在最终 Boss **之前**发给玩家。

### 对“精英万能卡 1—4★”的处理

代码里实际上存在两类容易被统称为“精英”的系统：

- 前中期的 Bounty 敌群。
    
- 最后两波的固定 `validationElite`。
    

我的建议是：

- Bounty 万能卡采用 1→4★曲线。
    
- 验证精英不再继续主要掉万能卡，而改为3—5★具体卡。
    
- Boss 万能卡采用1→5★曲线。
    

这样不同奖励源才有明确职责。若验证精英仍然同时掉4★万能和4—5★具体卡，奖励价值会再次成倍增加，而且会削弱卡型选择和一次性释放决策。

## 四、高星具体卡如何选择

验证期不能完全随机，否则一张5★冷门卡可能成为纯垃圾；但也不能永远发主流派，否则验证期没有即时选择。

建议使用现有掉落导演已经具备的两种选择逻辑：

### 构筑卡

用于第 7 波4★卡和第 8波5★卡。

选择规则：

- 优先玩家当前装备类型。
    
- 其次选择投入度最高、合成次数最多或与升级流派匹配的卡。
    
- 从最高权重的前 2—3 种中随机，避免每局完全相同。
    

项目已有 `calculateCommitmentScore`、`selectBuildType` 和流派亲和度系统，可以直接复用，不需要另写一套卡型评分。

### 转向卡

用于第 8 波高速精英的3★卡。

选择规则：

- 排除玩家投入最高的前两种卡。
    
- 从投入较少的卡型中选择。
    
- 主要鼓励玩家直接拖入战场进行一次性释放，而不是强迫继续构筑。
    

现有 `selectPivotType` 已经实现了“排除主要构筑、偏向低投入卡型”的逻辑，可以直接使用。

这样验证期会同时出现：

- 一张明显支持现有构筑的高星卡。
    
- 一张不属于当前构筑、但可以当作高强度消耗技能使用的卡。
    

这与你描述的预期一致。

# 一、诱饵为什么感觉不生效

## 1. 装备后不会立刻生成

诱饵装备态绑定的是 `onWaveStart`。只有下一波正式开始时才会创建诱饵；本波中途装备，不会产生任何实体。

装备系统只是把卡放进装备栏并发送 `equipped/swapped` 事件，没有执行“装备时初始化被动”的流程。

因此典型情况是：

> 玩家装备诱饵 → 继续观察当前战斗 → 什么也没发生 → 判断诱饵无效。

## 2. 装备态诱饵默认生成在炮台中心

`onWaveStart` 没有传入空间点时，效果原点默认就是炮台坐标；召唤物又直接使用该原点生成。

3★和5★诱饵的嘲讽半径只有 140。敌人必须已经非常接近炮台，才会改变目标。

这使它在功能上变成：

> 敌人先照常走向炮台，接近炮台后才改为撞击与炮台重叠的诱饵。

路径变化极小，所以无论敌人最初处于炮台射程内还是射程外，玩家都很难看到明显的“被引走”。

## 3. 诱饵还会被炮台画面覆盖

渲染顺序是先画召唤物，后画炮台；而诱饵恰好与炮台同坐标。

诱饵本身只是一个半径 14 的圆和一条小血条，也没有显示嘲讽范围、敌人转向线或被吸引标识。

所以即使它已经生成，也很容易被炮台主体遮住。

## 4. 还存在跨波累积风险

诱饵持续时间配置为 999 秒，每波都会再次执行一次召唤。开始下一波时没有清理上一波召唤物。

从当前代码推断，只要旧诱饵没有被摧毁，就可能与下一波新诱饵重叠累积。镜像炮台也存在相同风险。

现有测试只验证了“手动在远离炮台的位置生成一个诱饵后，附近敌人会转向”，并没有验证实际卡牌装备、下一波生成、中心重叠或多波生命周期。

### 诱饵修复方案

不建议只把嘲讽半径调大。应当修复完整生命周期：

1. 给召唤物记录来源：
    
    - `sourceCardId`
        
    - `sourceBindingIndex`
        
    - `spawnPolicy`
        
    - `refreshPolicy`
        
2. 增加通用的装备被动同步函数，例如：
    

```ts
reconcileEquipmentPassives(state, config, rng)
```

装备、卸下、替换、升星以及开波后都调用一次。

3. 诱饵采用“每张装备卡最多一个实例”：
    
    - 刚装备时立即生成。
        
    - 下一波开始时刷新血量并重新定位，而不是无限新增。
        
    - 卸下装备后移除对应诱饵，或者进入短暂消退状态。
        
4. 不要生成在炮台正中心。推荐生成在炮台外围：
    
    - 距炮台约 `120–160px`；
        
    - 优先放在当前敌人密度最高的方向；
        
    - 没有敌人时使用装备槽决定的固定方向，保证结果可预测。
        
5. 增加明确表现：
    
    - 诱饵脚下显示嘲讽范围；
        
    - 被吸引敌人头顶显示短暂图标；
        
    - 敌人切换目标时画一条短暂指向线；
        
    - 诱饵受击、爆炸、重生必须有独立事件和视觉反馈。

# 二、持续光束与范围榴弹是否实际生效

## 单独装备时：逻辑上能够生效

持续光束对应 `beamMorph`，范围榴弹对应 `mortarMorph`。配置和单独测试均已存在。

现有测试分别验证了：

- 榴弹会生成 `mortar` 子弹并在落点造成伤害；
    
- 光束会按照间隔造成伤害，并且不再生成普通子弹。
    

所以这两个效果并非完全没有实装。

## 但“持续光束”实际上不是持续光束

配置是每 0.9 秒触发一次。每次触发时瞬间计算一条直线上的伤害，然后生成十个粒子。没有持续存在的光束实体、持续时间或连续伤害 tick。

但文案写的是“主炮化为持续光束”“自动横扫”。

因此目前更准确的名称应当是：

> 周期性贯穿光束 / 脉冲光束

要保留“持续光束”名称，就应该真正实现短时间持续照射，例如：

- 每 0.9 秒启动一次；
    
- 持续 0.5–0.7 秒；
    
- 每 0.1 秒结算一次伤害；
    
- 屏幕上始终存在清晰的炮口到射程末端的光束线。
    

## 范围榴弹的表现也不足

榴弹目前仍然使用普通子弹的统一画法，只是半径略大。所有子弹都是同一种青色圆点。

爆炸时也只有通用橙色粒子，没有：

- 目标落点预警圈；
    
- 抛物线或空中高度；
    
- 爆炸范围扩张圈；
    
- 范围受击反馈。
    

因此“逻辑生效但玩家看不出来”对榴弹确实成立。

# 三、两种主炮形态同时装备时发生了什么

这是当前最明确的构筑缺陷。

## 当前采用静默覆盖

`getModifiers()` 中只有一个字段：

```ts
morph: 'none' | 'beam' | 'mortar'
```

遍历装备时，遇到光束就赋值为 `beam`，遇到榴弹就赋值为 `mortar`。后处理的装备覆盖前一个。

装备遍历顺序就是装备槽顺序。因此：

- 光束卡在前、榴弹卡在后：榴弹生效；
    
- 榴弹卡在前、光束卡在后：光束生效；
    
- 被覆盖的6★卡完全不产生作用；
    
- UI没有任何冲突、停用或覆盖提示。
    

所以你当时同时装备二者时，**不是两者合理组合，而是其中一个被另一个静默覆盖。**

---

# 四、更严重的问题：换形会让其他弹道被动失效

普通攻击的触发链大致是：

```text
生成普通子弹
→ onFire
→ 子弹命中
→ onHit
→ onKill
```

但是：

- 榴弹分支生成榴弹后没有调用 `onFire`；
    
- 榴弹爆炸只直接调用伤害函数，没有调用 `onHit`；
    
- 光束分支完全绕过普通 `shoot()`，直接结算直线伤害；
    
- 光束也没有调用 `onFire` 或 `onHit`。
    

这意味着只要启用光束或榴弹，以下效果可能全部失效：

|卡牌|被影响的装备效果|
|---|---|
|心跳连锁|命中连锁、减速|
|冷淡处理|子弹减速、冻结叠层|
|热情退烧|命中生成灼烧区|
|群发拒绝|命中分裂、范围爆炸|
|保持距离|每发子弹击退|
|直球拒绝的低阶形态|穿透、折返等普通子弹效果|

这正是“装备被动没有合理共存”的核心原因。

# 五、审查中发现的其他卡牌缺陷

## 1. 致命命中不会触发 `onHit`

当前流程先扣除普通子弹伤害。只有敌人扣血后仍然存活，才会执行子弹附着效果和 `onHit`。

如果普通子弹直接击杀目标：

- 连锁不会从死亡目标跳出；
    
- 分裂爆炸不会发生；
    
- 灼烧区不会生成；
    
- 其他命中效果也不会触发。
    

这会导致这些卡在敌人较弱时反而显得“不生效”。

应将“命中”和“死亡”拆成两个阶段，保证致命命中仍然产生一次 `onHit`，再统一执行死亡结算。

## 2. 热情退烧的“烧死蔓延”可能永远无法触发

卡牌要求：敌人在带有 `dot` 状态时死亡，才生成新的灼烧区。

但区域中的 `dot` 在运行时是直接扣血，不会写入敌人的 `status.dots`。

而 `requiresStatus: "dot"` 检查的恰好是 `enemy.status.dots.length > 0`。

因此由灼烧区烧死的敌人，大概率不满足“身上有 dot 状态”的判断，“烧死蔓延”成为死效果。

推荐改为伤害来源判定：

```json
{
  "trigger": "onKill",
  "triggerParams": {
    "requiresSource": "scorchDot"
  }
}
```

区域伤害调用 `dealDamage` 时传入 `scorchDot` 来源，而不是伪造一个状态。

# 六、建议确立的装备共存规则

不要继续通过代码执行顺序隐式决定。应把共存规则写成正式系统契约。

|效果类别|推荐规则|
|---|---|
|数值乘数|明确乘法叠加|
|固定数值增益|明确加法与上限|
|减速、易伤|保持当前“取最强、刷新时长”|
|光环、领域|按来源独立存在|
|触发型被动|所有装备独立触发|
|召唤物|每个来源独立，但同一绑定保持单实例|
|主炮形态|**互斥，只能激活一种**|
|处决阈值|取最高|
|护盾|明确刷新、覆盖或追加规则|

对于“持续光束”和“范围榴弹”，我建议在当前验证期采用：

> **主炮形态互斥，禁止静默覆盖。**

```text
“持续光束”与“范围榴弹”只能启用一个。

```

这样比临时制作“光束榴弹融合形态”更稳定，也更容易控制平衡。未来若确实要做形态融合，可以作为专门的高阶构筑，而不是让通用被动系统自动猜测。

## 三、代码中的经验规则

### 3.1 敌人基础经验

当前敌人经验完全由敌人类型决定：

|敌人类型|击杀经验|
|---|--:|
|普通敌人 normal|1 XP|
|高速敌人 fast|1 XP|
|重装敌人 tank|2 XP|
|Boss|5 XP|

这些经验值不会随着波数、血量、伤害或难度自动增长。

击杀时的实际经验公式是：

```text
实际经验
= 敌人基础经验
× killXpMul
×（1 + 本局经验加成）
× 装备经验倍率
```

当前 `killXpMul = 1`。

具体结算代码为：

```text
enemy.xp
× cfg.progression.killXpMul
× (1 + state.xpGainBonus)
× getModifiers(state).xpMul
```

### 3.2 只有“击杀”才给经验

常规敌人突破炮台时会从敌人数组中移除，但不会进入击杀结算，因此不会获得经验。召唤物吸引敌人后，敌人撞死在召唤物上，同样明确标注为“不给击杀奖励”。

因此，本报告中的 911 XP 是：

> **所有应出现敌人全部被玩家击杀时的数学期望，不是普通玩家必然获得的固定经验。**

实际经验会因为漏怪而下降。

### 3.3 难度不会提高经验

难度配置会调整敌人的血量、伤害和速度，但 `createEnemy` 最终仍直接使用 `def.xp` 作为经验，没有乘以难度倍率。

这意味着：

- 轻松难度击杀同一敌人：经验不变；
    
- 标准难度：经验不变；
    
- 困难难度：经验不变；
    
- 地狱难度：经验不变。
    

当前难度的设计是“纯战斗压力选择”，不是“高风险高经验收益”。

## 四、当前升级需求曲线

经验配置为：

```json
"xpNeedBase": 10,
"xpGrowth": 2
```

即每次升级后，下一级所需经验翻倍。

升级需求如下：

|从当前等级升到|本级所需经验|从开局累计需要|
|---|--:|--:|
|2 级|10|10|
|3 级|20|30|
|4 级|40|70|
|5 级|80|150|
|6 级|160|310|
|7 级|320|630|
|8 级|640|1270|
|9 级|1280|2550|

升级时，系统会：

1. 扣除当前等级所需经验；
    
2. 等级加一；
    
3. 下一级需求乘以 2；
    
4. 加入一次待选择升级；
    
5. 暂停游戏；
    
6. 展示三个升级选项。
    

游戏只要处于暂停状态，敌人移动、射击、掉落计时和游戏时间都会停止，因此升级弹窗不会让玩家在战斗中受到额外伤害。

需要注意的是，虽然战斗安全，但每次弹窗仍然会打断玩家的拾取、观察和即时反应节奏。

即：

> 第 3 波结束时会停在 **153.375 / 160**，只差约 6.625 XP，却没有升级。

这会产生明显的“差一点升级但被波间切断”的体验。

### 第 4 波

进入第 4 波后，只需再获得约 6.625 XP，因此大约击杀 5～6 个敌人，就会立刻升到 6 级。

因此第 3、4 波形成一种不够自然的节奏：

> 第 3 波整波没有升级，但第 4 波刚开场就弹出升级。

### 第 5 波

升到 7 级需要累计 630 XP。

第 5 波开始时约有 464.375 XP，还需要 165.625 XP。第 5 波平均每个敌人约 1.325 XP，因此大约在第 125 个常规敌人时升级。

### 第 6～8 波

升到 8 级需要累计 1270 XP。

最终只有约 911 XP，因此第 6、7、8 波不会再发生任何升级。

最终经验条停在：

```text
281 / 640 ≈ 43.9%
```

这不是“差一点升级”，而是明显无法在当前默认局长内完成下一等级。

---

## 七、当前升级选择的构筑体验

默认一局共发生 6 次升级，因此玩家会完成 6 次三选一。

第一次升级有特殊规则：

- 三个选项必须来自三个不同的战斗流派；
    
- 不会出现通用强化；
    
- 不会出现经验提升。
    

测试明确验证了第一次选择不包含 `utility`。

这意味着第一波的三次升级大致承担：

1. 第一次：确定第一条战斗路线；
    
2. 第二次：开始强化或补充路线；
    
3. 第三次：进一步形成构筑方向。
    

宏观上，这与“选择阶段”是吻合的。

但问题在于，三个选择几乎全部塞在第一波。玩家此时通常尚未获得足够多的卡牌，也未必理解不同技能与流派的对应关系，因此选择依据可能不足。

---

## 八、赏金挑战对经验的影响

赏金挑战只会在第 1～6 波出现，验证阶段明确禁止生成赏金报价。

每个赏金遭遇的敌人数为：

|波次|单次赏金敌人数|
|---|--:|
|1|3|
|2|3|
|3|4|
|4|4|
|5|5|
|6|5|

计算规则为：

```text
3 + floor((波数 - 1) × 0.5)
```

赏金敌人构成为：

- 普通：50%；
    
- 高速：30%；
    
- 重装：20%。
    

所以单个赏金敌人平均经验为：

```text
50% × 1 + 30% × 1 + 20% × 2 = 1.2 XP
```

### 赏金经验场景

|赏金参与方式|额外预期 XP|最终结果|
|---|--:|---|
|完全不接受|0|911 XP，7 级，281 / 640|
|第 1～6 波各完成 1 次|28.8|939.8 XP，7 级，309.8 / 640|
|每波完成最大 2 次|57.6|968.6 XP，7 级，338.6 / 640|

结论是：

> 即使玩家每波完成最多两次赏金挑战，在没有经验强化的情况下，默认 8 波仍然只能达到 7 级。

赏金挑战可以让经验条更快增长，但不足以改变最终等级。

---

## 九、“击破经验 +12%”升级的影响

当前通用升级“洞悉弱点”效果为：

```text
击破经验 +12%
最大叠加 6 次
```

每次选择会把 `xpGainBonus` 增加 0.12。代码测试也验证了这一行为。

但是：

1. 第一次升级不会出现通用选项；
    
2. 后续每次升级也不保证出现经验强化；
    
3. 经验强化只影响选择之后的击杀；
    
4. 默认版本需要从 911 XP 提高到 1270 XP，差额为 359 XP。
    

即使假设一层经验强化非常早获得，它也只能为剩余约 880 XP 增加约 106 XP，仍然远不足以达到 8 级。

粗略估算，通常需要大约四层经验强化都在较早阶段取得，才可能把默认一局推到 8 级。考虑到它只是多个通用选项之一，这不应被视为常规结果。

因此：

> 7 级是默认稳定终点；8 级属于非常偏向经验构筑的特殊结果。

## 十、随机敌人组成会不会改变最终等级

前 6 波共生成 665 个常规敌人。

如果把所有普通与高速敌人先按 1 XP 计算，再为每个重装敌人额外增加 1 XP，则：

```text
总经验
= 665
+ 重装敌人总数
+ 8 个 Boss × 5
+ 验证精英基础经验 5
```

重装敌人数的数学期望约为 201，因此：

```text
665 + 201 + 40 + 5 = 911 XP
```

随机波动的标准差约为 11.8 XP。按近似 95% 区间，单局击杀全部敌人时通常会落在：

```text
约 887～935 XP
```

整个区间都满足：

```text
高于 7 级阈值 630
低于 8 级阈值 1270
```

所以敌人随机类型不会实质改变最终等级。

> 在完整击杀的前提下，最终 7 级几乎是确定结果，而不是仅仅取平均后得到的偶然结果。

## 十一、漏怪对经验的影响

前 6 波常规敌人合计贡献约 866 XP。

如果按经验权重计算：

|常规经验损失比例|预计最终经验|最终等级|
|---|--:|---|
|0%|911|7|
|10%|约 824|7|
|20%|约 738|7|
|30%|约 651|7，刚刚超过阈值|
|超过约 32.5%|低于 630|可能只有 6 级|

因此，只要玩家没有漏掉约三分之一以上的常规敌人，最终通常仍能达到 7 级。

不过，不同难度、不同防御构筑和召唤物构筑的实际漏怪比例可能明显不同。当前代码和现有遥测不足以确认真实玩家的平均漏怪率。

---

## 十二、最终验证阶段的经验设计

第 7、8 波总共只提供：

```text
7 + 8 = 15 XP
```

占整局 911 XP 的约：

```text
1.65%
```

而这两波敌人的血量极高。例如：

- 第 7 波重装精英基础血量为 `90 + 45 × 7 = 405`，再乘 14，约为 5670 HP；
    
- 第 8 波重装精英基础血量为 `90 + 45 × 8 = 450`，再乘 20，约为 9000 HP；
    
- 但两者都只提供 2 XP。
    

这说明当前设计把最终两波明确视为：

> **构筑验收阶段，而不是继续成长阶段。**

这个方向本身并非错误。最终验证阶段不再继续升级，可以避免玩家在测试完成构筑时又获得一个临时新强化，导致验证结果失真。

问题在于，目前界面仍然保留经验条，而且玩家在击杀高血量精英和最终 Boss 后，只看到经验条极小幅度增长。这容易产生“强敌经验奖励反而非常低”的反馈落差。

建议在设计上明确二选一：

### 方案 A：保持验证阶段不升级

这是更符合当前三阶段导演结构的方案。

处理方式应是：

- 第 7 波开始时明确提示“构筑锁定，进入验证阶段”；
    
- 验证敌人的主要奖励由高星卡、万能卡和结算分数承担；
    
- 弱化或隐藏验证阶段经验条；
    
- 不需要强行提高精英经验。
    

### 方案 B：希望最终战仍有成长反馈

则需要：

- 提高验证精英和 Boss 经验；
    
- 或在第 7 波前降低 8 级阈值；
    
- 确保最终战至少有一次升级。
    

但这样会改变“用完成构筑接受验证”的原始含义。

从当前代码结构和项目阶段目标看，建议优先采用方案 A。

---

## 十三、Boss 经验反馈问题

当前所有 Boss 均固定为 5 XP，但 Boss 血量随波数高速增长：

```text
Boss HP = 300 + 波数 × 320
```

所以：

|波次|Boss 基础 HP|XP|
|---|--:|--:|
|1|620|5|
|4|1580|5|
|8|2860|5|

最终 Boss 的基础血量约为第一波 Boss 的 4.6 倍，但经验完全相同。

不过，Boss 另有逐波递增的万能卡奖励，因此经验并不是 Boss 的唯一奖励。

因此，这更接近“反馈表达问题”而非必然的数值错误：

- 如果万能卡奖励足够醒目，Boss 固定 5 XP 可以接受；
    
- 如果玩家主要注意经验条，则会觉得 Boss 经验过低。
    

不建议仅为了“经验与血量匹配”直接大幅增加 Boss XP，因为这可能破坏当前六次升级的构筑数量。应先确定每局目标升级次数，再反推 Boss 经验。

## 十四、当前体验的主要问题

### 14.1 第一波三次升级，打断过于密集

当前第一波预计获得约 78.5 XP，而前三个累计阈值只有 10、30、70。

这会导致第一波出现三次暂停弹窗。

优点是玩家很快获得构筑能力；缺点是：

- 尚未理解卡牌和流派就被要求决策；
    
- 刚建立战斗节奏就反复暂停；
    
- 第一次波次体验被升级界面切碎；
    
- 即时拾取和反应操作的教学空间被挤占。
    

这是当前最值得优先验证的问题。

### 14.2 第三波“差一点”，第四波开场立刻升级

第 3 波结束时约为 303.375 XP，而 6 级阈值是 310。

这种安排没有明显设计收益：

- 第 3 波整波没有升级；
    
- 波末看见经验条几乎满；
    
- 第 4 波只击杀几只敌人便弹窗；
    
- 升级节点与波次高潮、Boss 击杀都没有对齐。
    

建议调整阈值，使升级发生在第 3 波末或第 4 波中段，而不是第 4 波刚开场。

### 14.3 第 6～8 波成长完全停止

玩家在第 5 波后段达到 7 级，之后经历：

- 第 5 波剩余敌人；
    
- 整个第 6 波；
    
- 第 7 波验证；
    
- 第 8 波最终验证；
    

但不会再升级。

如果第 6 波战斗时间较长，就会出现明显的后程成长真空。

### 14.4 经验收益与敌人强度完全脱钩

困难和地狱难度不提高经验，高倍率验证精英也不提高经验。

这使经验系统无法表达：

- 高风险挑战；
    
- 强敌价值；
    
- Boss 强度；
    
- 验证阶段压力。
    

是否调整取决于经验系统究竟承担“固定构筑节拍器”还是“击杀奖励”：

- 若是固定节拍器，当前方向合理；
    
- 若是击杀奖励，当前数值不合理。
    

目前代码更接近前者，但 UI 表现仍像传统击杀经验系统，定位存在模糊。

### 14.5 经验显示可能出现浮点小数

HUD 直接使用：

```ts
String(state.xp)
```

没有取整或格式化。

获得 12% 经验强化后，单次经验可能变成：

- 1.12；
    
- 2.24；
    
- 多次累计后甚至可能出现 JavaScript 浮点误差形式。
    

例如理论上可能显示：

```text
13.440000000000001 / 160
```

这属于明确的 UI 风险。

建议至少改为：

```ts
state.xp.toFixed(1)
```

或者从根本上将经验存储为整数，例如把所有经验扩大 100 倍结算。

### 14.6 README 已经过时

README 仍然写着“守住 5 波即胜利”，但当前配置已经是 8 波。

当前实际配置明确为：

```json
"totalWaves": 8
```

这会直接误导后续调试、Agent 分析和人工验收，建议尽快更新。

## 十五、当前遥测无法验证真实经验体验

仓库已有一个名为 `computeExperienceMetrics.ts` 的脚本，但这里的 “Experience Metrics” 实际指 E1～E7 的玩法体验指标，例如：

- 掉落可见性；
    
- 拾取率；
    
- 输入次数；
    
- 场上敌人；
    
- 危险状态；
    
- 构筑成熟度。
    

它没有统计玩家的 XP 或等级。

当前遥测事件类型包含击杀、掉落、Boss、升级弹窗和赏金，但事件结构没有：

- `xpBefore`；
    
- `xpGain`；
    
- `xpAfter`；
    
- `levelBefore`；
    
- `levelAfter`；
    
- `xpNeed`。
    

采样数据也只有时间、波次和场上敌人数。

因此，现在只能静态推算，无法从导出的会话中准确回答：

- 玩家平均每波获得多少经验；
    
- 各难度平均漏掉多少经验；
    
- 实际升级发生在第几秒；
    
- 一次升级弹窗停留多久；
    
- 有多少玩家最终只有 6 级；
    
- 经验强化实际被选择几次；
    
- 赏金为一局贡献了多少经验；
    
- 最后一次升级距离最终 Boss 有多远。
    

这是本次调查中最重要的工程缺口。

## 十六、建议增加的经验遥测

建议在 `kill` 或独立 `xpGain` 事件中记录：

```ts
{
  type: 'xpGain',
  at: state.time,
  wave: state.wave,
  enemyType: enemy.type,
  spawnKind: enemy.spawnKind,
  baseXp: enemy.xp,
  multiplier: ...,
  gainedXp: xpGain,
  xpBefore: ...,
  xpAfter: ...,
  levelBefore: ...,
  levelAfter: ...
}
```

在 `levelUp` 事件中记录：

```ts
{
  type: 'levelUp',
  at: state.time,
  wave: state.wave,
  level: state.level,
  remainingXp: state.xp,
  nextXpNeed: state.xpNeed
}
```

同时补充：

- `enemyBreached`：记录漏掉的敌人类型和对应损失经验；
    
- `perkSelected`：保留完整 perk ID，而不仅是输入字符串；
    
- `runEnd`：记录最终等级、经验、经验需求和总经验获得量。
    

建议新增的每局汇总指标：

|指标|用途|
|---|---|
|总经验获得|确认实际值与理论值差异|
|每波经验|检查升级节奏|
|每波漏失经验|判断难度和防御构筑影响|
|升级时间点|检查是否集中在第一波|
|升级波次分布|验证预期节奏|
|最终等级分布|判断 6、7、8 级比例|
|赏金经验占比|判断赏金是否影响成长|
|经验强化选择次数|判断其实际价值|
|最后升级至结局的间隔|测量后程成长真空|

## 十七、建议的调整目标

在调整数值前，应先明确目标升级次数。

结合当前 8 波结构，建议基准目标为：

> **默认完整通关仍然获得 6 次升级，但不再把 3 次全部塞进第一波。**

推荐节奏：

|波次|推荐升级次数|
|---|--:|
|第 1 波|2|
|第 2 波|1|
|第 3 波|1|
|第 4 波|1|
|第 5 波|0|
|第 6 波|1|
|第 7～8 波|0，进入构筑验证|

这种节奏仍然保持：

- 选择阶段快速确立路线；
    
- 构筑阶段持续获得强化；
    
- 验证阶段冻结构筑；
    
- 一局合计 6 次升级。
    

同时解决：

- 第一波三连弹窗；
    
- 第三波无升级、第四波开场立刻升级；
    
- 第六波完全没有成长节点。

## 十八、推荐的 A/B 参数方案

当前参数：

```json
"xpNeedBase": 10,
"xpGrowth": 2
```

建议先创建一个不覆盖其他配置的实验 variant：

```json
{
  "$comment": "平滑默认 8 波升级节奏，仍以 6 次升级为目标",
  "progression": {
    "xpNeedBase": 20,
    "xpGrowth": 1.7
  }
}
```

该方案的每级需求约为：

|升级|本级需求|累计阈值|
|---|--:|--:|
|1 → 2|20|20|
|2 → 3|34|54|
|3 → 4|58|112|
|4 → 5|99|211|
|5 → 6|168|379|
|6 → 7|286|665|
|7 → 8|486|1151|

在当前 911 XP 基准下，预期升级分布变成：

- 第 1 波：升 2 次；
    
- 第 2 波：升 1 次；
    
- 第 3 波：升 1 次；
    
- 第 4 波：升 1 次；
    
- 第 5 波：不升级；
    
- 第 6 波前段：升 1 次；
    
- 最终仍然是 7 级，共 6 次升级；
    
- 第 7、8 波仍然作为纯验证阶段。
    

这个方案的优点是：

- 不改变一局总升级次数；
    
- 不需要修改敌人经验；
    
- 不影响不同难度之间的等级公平性；
    
- 不会让最终验证阶段临时获得新构筑；
    
- 只通过两个参数即可进行 A/B 测试。
    

它不是最终定案，但比直接提高 Boss 或精英经验更适合作为第一轮验证。

## 十九、10 波 variant 的经验结果

仓库中已有 `validation-10` variant，它只把总波数改为 10，并没有单独调整经验曲线。

在 10 波版本中：

- 第 1～2 波仍为选择阶段；
    
- 第 3～8 波为构筑阶段；
    
- 第 9～10 波为验证阶段；
    
- 构筑阶段配额重新在 95～170 之间分布。
    

在无赏金、无经验强化、完整击杀的情况下，预期总经验约为：

```text
1292.125 XP
```

最终结果：

```text
8 级，22.125 / 1280
```

也就是说：

|版本|预期总 XP|最终等级|升级次数|
|---|--:|--:|--:|
|默认 8 波|911|7|6|
|validation-10|1292.125|8|7|

这是一个重要的实验混杂因素：

> `validation-10` 不只是把游戏延长两波，也会让玩家额外获得一次升级。

如果该 variant 用来比较“8 波是否足够完成构筑”，那么实验实际同时比较了：

- 更长的战斗时间；
    
- 更多常规掉落；
    
- 更多赏金机会；
    
- 更多敌人；
    
- **多一次 perk 升级。**
    

这可能是合理的整体处理，也可能干扰对“卡牌成长是否足够”的单独判断。实验报告中必须明确记录。

## 二十、最终判断

### 当前一局的预期体验

当前默认版本的经验设计，实际产生的是：

> **6 次升级、最终 7 级、前期密集选择、后期构筑冻结。**

更具体地说：

1. 第一波三次升级，构筑建立很快，但打断过于密集；
    
2. 第二波再升级一次，前两波已经完成四次选择；
    
3. 第三波经验条几乎满但不升级；
    
4. 第四波刚开始便升级，节点不自然；
    
5. 第五波后段完成最后一次升级；
    
6. 第六波虽然敌人最多，却完全没有升级；
    
7. 最终两波只有 15 XP，明确承担构筑验证功能；
    
8. 默认通关稳定停在 7 级，不会自然达到 8 级；
    
9. 赏金通常不能改变最终等级；
    
10. 10 波版本会自然多获得一次升级。
    

### 是否合理

判断为：

> **宏观结构合理，微观节奏尚未完成。**

合理之处是：

- 升级数量受控；
    
- 初期快速确定流派；
    
- 最终验证阶段不继续改变构筑；
    
- 8 波和 10 波能够形成不同的构筑完成度。
    

主要问题是：

- 第一波升级过度集中；
    
- 第 3、4 波节点错位；
    
- 第 6 波成长反馈不足；
    
- 强敌经验表现与战斗强度脱节；
    
- 经验数值可能显示浮点误差；
    
- 当前遥测无法验证实际玩家结果；
    
- README 与当前波次数量不一致。
    

### 优先级建议

第一优先级不是立即改敌人经验，而是：

1. 接入 XP、等级和漏怪经验遥测；
    
2. 实测不同难度下的每波经验与升级时间；
    
3. 建立 `xp-smooth-6` A/B variant；
    
4. 比较当前 `10 / 2.0` 与建议 `20 / 1.7`；
    
5. 确认玩家是否更偏好“第一波三次升级”还是“前六波持续成长”；
    
6. 最后再决定 Boss 和验证精英是否需要额外经验。
    

当前代码足以确定理论结果，但还不足以宣称真实玩家的一局平均经验就是 911 XP。911 XP 是“完整击杀、无额外成长来源”的静态预期；真实均值必须补充遥测后才能确认。

进入修改阶段时，最合理的第一步是同时加入 `xp-smooth-6` variant 和经验遥测，避免只凭主观手感调整翻倍曲线。

# ProjectVL 升级三选一系统调查报告

## 一、核心结论

当前“升级三选一”不是从全部选项中完全随机抽取三个，而是一套有明确构筑导演逻辑的系统：

1. 第一个位置负责强化当前主流派；
    
2. 第二个位置负责支持玩家已经持有的卡牌，或提供另一条战斗路线；
    
3. 第三个位置负责提供新流派转型或通用数值强化；
    
4. 三个选项不会重复；
    
5. 达到最大叠加层数的选项会被移出候选池；
    
6. 选择战斗流派升级后，还会影响后续普通掉落和赏金奖励的卡型倾向。
    

因此，系统本质上是：

> **带构筑识别、流派导向和兜底机制的受控随机三选一。**

但当前存在几个重要问题：

- 所谓“开局三条不同路线”并不一定在第一次升级触发；
    
- 第三个位置按“选项数量”而不是按“流派”均衡随机；
    
- 回血、经验加成等通用选项没有根据当前局势动态过滤；
    
- 玩家界面没有解释三个位置各自承担什么职责，因此玩家可能仍然感觉它们只是随机出现。

# 四、三个选项位置的设计逻辑

代码把三选一的三个位置分别赋予了不同职责。

## 4.1 第一个位置：主流派强化

系统首先检查四个战斗流派的倾向值：

- 弹道；
    
- 控制；
    
- 领域；
    
- 防御。
    

拥有最高倾向值的流派被视为当前主流派。

第一个选项优先从主流派中抽取：

- 路线强化；
    
- 或桥接强化。
    

例如当前弹道倾向最高，第一个选项会在：

- 超压弹道；
    
- 增殖弹药；
    

之间随机。

如果最高倾向有多个并列流派，则先在并列流派之间等概率随机一个。

如果所有流派倾向都为零，则从四个拥有合法路线升级的流派中随机选一个。

设计目的很明确：

> 至少有一个选项继续支持玩家已经选择的主要构筑，降低升级完全不相关的概率。

---

## 4.2 第二个位置：支持当前持有卡牌

系统读取玩家手牌和装备中的所有卡牌，并收集它们的 `synergyTags`。

例如玩家持有：

- 直球拒绝：覆盖弹道；
    
- 冷淡处理：覆盖控制、领域；
    
- 私人领域：覆盖防御。
    

第二个选项会优先从这些已经被卡牌覆盖的流派中选择，但不会与第一个选项属于同一流派。

如果存在多个符合条件的已覆盖流派，系统在这些流派之间等概率随机。

需要注意：

- 不看持有几张同流派卡；
    
- 不看卡牌星级；
    
- 不看是否已经装备；
    
- 手牌和装备均算作“持有”；
    
- 只要某个流派被覆盖一次，就具有同等候选资格。
    

如果没有任何可用的已覆盖流派，第二个位置会从其他战斗流派中随机。

设计目的为：

> 确保至少一个升级与玩家当前真正拿到的卡牌产生关系，而不是只看抽象流派积分。

---

## 4.3 第三个位置：转型或通用强化

在非开局状态下，第三个位置执行一次 50% 随机：

### 50%：转型路线

从前两个选项尚未占用的战斗流派中，抽取一个 `route` 类型升级。

这相当于告诉玩家：

> 除了继续当前构筑，也可以开启一条新路线。

需要注意，转型池只包含 `route`，不包含 `bridge`。

### 50%：通用强化

从以下五个通用选项中抽取：

- 高能弹芯；
    
- 过载供能；
    
- 重整心防；
    
- 扩容心防；
    
- 洞悉弱点。
    

如果本次随机选择的池已经没有合法选项，系统会自动改用另一个池。

设计目的为：

> 第三个位置不与前两个位置争夺“主构筑职责”，而是承担转型、保命或基础能力补强。

---

# 五、什么是“开局状态”

代码中的“开局”不是简单指第一次升级，而是必须同时满足：

1. 四个战斗流派倾向全部为零；
    
2. 手牌和装备栏全部为空。
    

在这个状态下：

- 第一个选项只能是路线强化；
    
- 第二个选项只能是另一条路线强化；
    
- 第三个选项也只能是第三条不同的路线强化；
    
- 不会出现桥接强化；
    
- 不会出现回血、伤害、射速或经验等通用强化；
    
- 三个选项必定属于三个不同的战斗流派。
    

测试也只验证了“空状态的新局”会出现三个不同战斗流派，且不含辅助选项。

## 这里存在一个重要问题

这段逻辑并不保证在“第一次升级”触发。

假设玩家第一次升级前已经拾取了一张卡：

```text
流派倾向仍然全部为 0
但卡槽不再为空
```

此时 `opening` 会变成 false。

结果是第一次升级就可能：

- 出现桥接升级；
    
- 第三个位置出现通用升级；
    
- 不再保证三个不同流派的路线选项。
    

所以当前系统真正实现的是：

> **空背包开局保护。**

而不是：

> **第一次升级保护。**

如果原设计意图是“第一次升级必须让玩家在三条战斗路线中选择”，判断条件应该更接近：

```text
perkHistory.length === 0
```

或者：

```text
level === 2
```

而不应该依赖卡槽是否为空。

# 六、具体随机算法

## 6.1 第一步：排除达到上限的选项

系统首先过滤：

```text
当前已选层数 < maxStacks
```

达到最大层数的升级不会再出现。

例如：

- 增殖弹药达到 3 层后永久退出候选池；
    
- 洞悉弱点达到 6 层后永久退出；
    
- 高能弹芯理论上需要达到 99 层才退出。
    

测试验证了达到上限的增殖弹药不会再次出现。

---

## 6.2 第二步：每个位置先确定候选池

随机顺序不是：

```text
全部 13 个选项 → 随机抽 3 个
```

而是：

```text
位置 1 → 确定主流派池 → 在池中抽取
位置 2 → 确定持有卡流派池 → 在池中抽取
位置 3 → 确定转型池或通用池 → 在池中抽取
```

这意味着 `weight` 只影响最后一步“在已经确定的池中选谁”，不会影响位置职责，也不会直接决定抽中哪个流派。

---

## 6.3 第三步：加权随机

加权算法为标准权重抽取：

```text
选项概率 = 该选项权重 ÷ 候选池总权重
```

如果候选池所有权重都为 0，则退化为等概率随机。

所有战斗流派升级当前权重均为 1，所以同一候选池内基本等概率。

例如非开局状态下，控制流派候选池包含：

- 凝滞力场：权重 1；
    
- 乘虚而入：权重 1。
    

因此二者各有 50% 概率。

同理：

|流派|候选池内部概率|
|---|---|
|弹道|超压弹道 50%，增殖弹药 50%|
|控制|凝滞力场 50%，乘虚而入 50%|
|领域|领域扩张 50%，余烬灼心 50%|
|防御|加固壁垒 50%，荆棘反击 50%|

前提是这些选项都没有达到最大层数，并且该位置允许桥接选项。

---

# 七、通用辅助选项的概率

五个通用升级的权重总和为：

```text
0.7 + 0.7 + 0.8 + 0.6 + 0.5 = 3.3
```

在五个选项全部合法时，进入通用池后的条件概率为：

|通用选项|权重|进入通用池后的概率|
|---|--:|--:|
|重整心防|0.8|24.24%|
|高能弹芯|0.7|21.21%|
|过载供能|0.7|21.21%|
|扩容心防|0.6|18.18%|
|洞悉弱点|0.5|15.15%|

由于第三个位置正常情况下只有 50% 概率进入通用池，所以在“转型池和通用池都可用”的普通状态下，第三个位置的无条件概率约为：

|选项|出现在第三位置的概率|
|---|--:|
|重整心防|12.12%|
|高能弹芯|10.61%|
|过载供能|10.61%|
|扩容心防|9.09%|
|洞悉弱点|7.58%|
|任意通用升级|50%|
|任意转型路线|50%|

这些概率会随着某些选项达到最大层数而重新归一化。

---

# 八、第三位置存在“按选项数量偏流派”的现象

第三位置选择转型路线时，代码不是：

```text
先等概率选择一个未占用流派
再从该流派中选择一个升级
```

而是：

```text
把所有未占用流派的 route 选项放进同一个池
再按选项权重抽取
```

当前各流派的 `route` 数量为：

|流派|Route 数量|
|---|--:|
|弹道|2|
|控制|1|
|领域|2|
|防御|1|

因此，在其他条件相同时：

- 弹道有两个抽签单位；
    
- 领域有两个抽签单位；
    
- 控制只有一个；
    
- 防御只有一个。
    

这会让弹道和领域在第三个“转型位置”中比控制和防御更容易被选为流派。

如果设计目标是让四个流派获得同等转型机会，应改成：

1. 先从未占用流派中等概率选一个；
    
2. 再从该流派内部抽具体升级。
    

---

# 九、同一弹窗不会出现重复选项

每次某个升级被选进三选一后，会从后续位置的候选池中排除。

因此同一弹窗不会出现：

- 两个超压弹道；
    
- 两个重整心防；
    
- 或任何相同 ID 的重复项。
    

但非开局状态下，可能出现两个不同升级属于同一个流派吗？

正常的前三个角色槽逻辑会尽量避免：

- 第二位置明确排除第一位置流派；
    
- 第三位置的转型池排除前两个已占用流派。
    

只有候选池不足、进入最终兜底逻辑时，才可能破坏这种结构。

---

# 十、兜底逻辑

如果某个职责位置没有合法候选，系统会从所有尚未选择的合法升级中按权重补齐，直到达到三个选项或候选耗尽。

例如后期大量升级达到上限时，可能出现：

- 三个选项不足；
    
- 原本应该是转型的位置出现通用；
    
- 原本应该支持其他流派的位置回到当前主流派；
    
- 选项结构不再严格遵守三个职责。
    

这是合理的防崩溃兜底，但意味着“槽位职责”只是在正常候选充足时成立。

---

# 十一、连续升级时的随机方式

如果一次经验奖励跨过多个等级，系统不会一次性展示多组升级。

它会：

1. 记录多个 `pendingLevelUps`；
    
2. 先生成第一组三选一；
    
3. 玩家选择后；
    
4. 根据选择后的最新流派、卡牌和层数状态，重新生成下一组三选一；
    
5. 所有待选升级完成后恢复战斗。
    

这意味着连续升级并不是预先抽好六个选项，而是每次选择都会影响下一次抽取。

例如：

- 第一组选择超压弹道；
    
- 弹道倾向 +1；
    
- 下一组第一个位置就会优先提供弹道强化；
    
- 后续卡牌掉落也开始向弹道牌倾斜。
    

---

# 十二、选择升级还会改变后续掉落

战斗流派升级的 `affinityGain` 为 1，通用升级为 0。

选择战斗流派升级后，系统会：

1. 对应流派倾向 +1；
    
2. 清空普通掉落的角色袋；
    
3. 清空赏金奖励袋；
    
4. 安装一次该流派的掉落保底；
    
5. 让后续普通掉落和赏金奖励重新根据新流派倾向计算。
    

普通掉落会根据卡牌的流派标签计算倾向分，辅助标签不参与流派导流。

如果连续若干次普通掉落没有出现刚选择流派的卡牌，保底会强制选择该流派卡型。

所以当前系统形成了一个完整闭环：

```text
升级选择流派
→ 流派倾向增加
→ 后续掉落更容易出现该流派卡
→ 玩家更容易形成对应装备
→ 下一次升级继续支持该流派
```

这是当前升级系统最重要的设计价值。

---

# 十三、玩家界面实际展示了什么

升级界面会显示：

- 升级名称；
    
- 升级说明；
    
- 非辅助升级的流派标签；
    
- 当前持有的、能受该流派影响的卡牌名称。
    

例如玩家持有冷淡处理，控制升级或领域升级下方可能显示：

```text
生效中：冷淡处理
```

但是界面不会显示：

- 这是第一位置的主推选项；
    
- 这是第二位置的现有卡牌支持；
    
- 这是第三位置的转型或通用选项；
    
- `route` 与 `bridge` 的区别；
    
- 当前该升级已经选择了几层；
    
- 最大可叠加层数；
    
- 精确随机权重。
    

因此底层随机逻辑虽然很有设计感，但玩家只能看到结果，无法理解系统为什么给出这些选项。

# 十四、当前设计的优点

## 14.1 不容易出现三张完全无关的升级

至少第一个位置支持主流派，第二个位置尽量支持现有卡牌。

## 14.2 能形成稳定流派

选择升级不仅增强流派，还会导向对应卡牌掉落。

## 14.3 保留转型空间

第三个位置不会永远要求玩家继续堆主流派，而是持续提供新路线或通用能力。

## 14.4 随机可复现

所有抽取都通过注入的 RNG 完成。同一个状态和同一个随机种子，会生成同一组三选一。测试对此进行了验证。

这对数值测试、问题复现和自动化验收很有价值。

## 14.5 多标签卡能自然连接多条流派

例如心跳连锁同时拥有弹道和控制标签：

- 超压弹道可以强化其连锁伤害；
    
- 增殖弹药可以增加弹跳数；
    
- 凝滞力场可以强化其减速；
    
- 乘虚而入可以让受控目标承受更多伤害。
    

不同强化轴可以同时作用于同一张双标签卡。

同一个强化轴如果同时匹配多个标签，只取最强值，不会重复相加。

# 十五、当前设计的主要问题

## 15.1 “第一次升级保护”可能失效

开局判定依赖卡槽为空，而不是第一次升级。

这是最明确的逻辑风险。

建议改为：

```text
第一次进行 perk 选择
```

作为开局判断，而不是：

```text
没有拾取任何卡牌
```

---

## 15.2 回血选项可能成为无效选项

重整心防在满血时仍可能出现，权重还高于其他通用选项。

建议至少采用以下一种处理：

- 满血时不进入候选池；
    
- 满血时降低权重；
    
- 满血选择后把溢出治疗转成临时护盾；
    
- 根据失血比例动态提高权重。
    

---

## 15.3 经验强化可能在终盘成为低价值选项

洞悉弱点没有波次或阶段限制。

即使已经进入第 7、8 波验证阶段，后续只剩很少经验，它仍然可能进入通用池。

建议在以下情况下动态降低或禁用：

- 已进入验证阶段；
    
- 剩余敌人经验不足以推动下一次升级；
    
- 已接近最终 Boss；
    
- 预计回本经验低于一个明确阈值。
    

---

## 15.4 通用与转型固定五五开，过于机械

第三位置始终 50% 转型、50% 通用，没有考虑：

- 当前生命；
    
- 已经建立了几条流派；
    
- 当前持有多少匹配卡；
    
- 是否已经完成装备；
    
- 是否处于前期或后期。
    

例如：

- 前期更需要路线建立；
    
- 中期可以增加桥接和转型；
    
- 低血时可以提高生存选项；
    
- 后期应减少经验加成。
    

固定五五开便于理解和测试，但还不够适应局势。

---

## 15.5 第三位置不是流派均衡随机

因为它直接按 route 选项抽取，拥有两个 route 的弹道和领域在转型池中更占优势。

如果目标是四流派公平，应改为“先抽流派，再抽选项”。

---

## 15.6 防御桥接可能在没有对应机制时出现

荆棘反击只强化：

- 破盾新星；
    
- 反噬；
    
- 突破爆发。
    

如果玩家没有私人领域、带刺玫瑰或相关突破反击机制，它可能暂时没有直接收益。

系统会通过流派掉落导向补发相关卡牌，但玩家在选择当下仍可能感觉这是一个空选项。

---

## 15.7 伤害和射速升级可能读取临时增益

高能弹芯和过载供能使用的是选择时的“当前总伤害”和“当前总射速”。

当前总数值包含临时 Buff 倍率。

因此，如果玩家升级时身上存在临时伤害或射速 Buff，有可能把临时增强后的数值作为永久加值计算基础。

这可能产生非预期的永久收益，应确认设计意图。

更稳定的写法通常是：

```text
永久伤害倍率 += 15%
```

而不是：

```text
永久加值 += 此刻总伤害 × 15%
```

---

# 十六、整体设计评价

当前升级三选一的底层结构是合理的，而且明显优于纯随机抽取。

它试图同时解决三个问题：

1. 玩家需要稳定强化已经选择的构筑；
    
2. 玩家需要看到与当前持有卡牌有关的选项；
    
3. 玩家又不能完全失去转型和保命空间。
    

因此三个位置分别承担：

```text
位置 1：继续主流派
位置 2：支持当前卡牌或第二路线
位置 3：转型或通用补强
```

这是清晰且可扩展的系统框架。

当前主要问题不是框架错误，而是若干条件与权重还比较原型化：

- 开局保护条件不准确；
    
- 通用选项没有局势判断；
    
- 第三位置存在流派数量偏置；
    
- 后期仍可能给出经验类低价值选项；
    
- UI 没有把受控随机的理由告诉玩家。
    

最终判断为：

> **系统不是“随机三选一”，而是“主流派延续 + 当前卡牌支持 + 转型/通用”的半导演式升级系统。框架正确，但需要进一步补足开局判定、动态权重、无效选项过滤和玩家解释。**

优先修正顺序建议：

1. 把 `opening` 改为真正的首次升级判定；
    
2. 为回血和经验强化增加动态有效性判断；
    
3. 把第三位置改为先抽流派、再抽具体升级；
    
4. 在界面展示“主推”“适配当前卡牌”“新路线/通用”；
    
5. 检查伤害和射速升级是否会永久捕获临时 Buff；
    
6. 最后再调整各选项的具体权重。
    

这份调查已经覆盖当前三选一的选项池、实际效果、槽位职责、权重算法、构筑导流和现有风险。下一步应据此形成一份可直接交给代码 Agent 执行的“三选一系统改进方案”。

# 《Hades 1》技能池与局内随机控制机制报告

## 一、执行摘要

《Hades》的祝福系统不是一个简单的“所有技能按权重随机三选一”，而是一套分层、带状态依赖的条件随机系统：

```text
房间奖励池
→ 奖励来源池
→ 本局神祇池
→ 对应神祇的祝福池
→ 槽位、前置与互斥过滤
→ 优先祝福与替换祝福插入
→ 品质分桶
→ 生成三个不重复选项
→ 玩家选择或重抽
```

它与《吸血鬼幸存者》的核心区别是：

- 《吸血鬼幸存者》更接近“候选物品拥有相对权重”；
    
- 《Hades》更接近“先决定奖励来源和品质，再从当前合法候选中抽取”；
    
- 玩家控制随机的主要手段，不是直接提高某个技能的权重，而是改变**神祇来源、技能资格、核心槽位、前置条件、品质概率和重抽次数**。
    

因此，《Hades》的随机控制本质上是：

> 玩家通过每一次选择，持续编辑未来的候选空间。

最重要的设计结论有四个：

1. **进入哪些神祇，比单次祝福三选一更重要。**
    
2. **让目标祝福获得出现资格，比攒重抽次数更重要。**
    
3. **核心槽位既是能力槽，也是奖励池裁剪工具。**
    
4. **品质、技能身份和奖励来源是三个相互独立的随机层。**

# 三、Hades中的“技能池”究竟包括什么

在《Hades》的内部结构中，祝福通常以 `Trait` 表示。玩家看到的“神祇祝福三选一”，实际上包含多种性质完全不同的候选。

## 3.1 五类核心槽位祝福

扎格列欧斯的五种基础行动各自只能持有一个对应祝福：

- Attack：普通攻击；
    
- Special：特殊攻击；
    
- Cast：投弹；
    
- Dash：冲刺；
    
- Call：神援。
    

公开脚本内部使用的槽位名称分别包括：

```text
Melee
Secondary
Ranged
Rush
Shout
```

祝福界面还会按照这些核心槽位排序，而不是将所有结果无序显示。

核心槽位具有强互斥性。例如，玩家不能同时拥有阿佛洛狄忒和宙斯的普通攻击祝福。新神可以提供同槽位替换，但替换会移除旧祝福。

社区机制资料也将其概括为Attack、Special、Cast、Dash、Call五个独占槽位。([hades.fandom.com](https://hades.fandom.com/wiki/Boons "https://hades.fandom.com/wiki/Boons"))

## 3.2 无槽位的普通辅助祝福

大量祝福不直接占据五个核心槽位，例如：

- 状态效果强化；
    
- 闪电弹射次数；
    
- 暴击强化；
    
- 击退强化；
    
- 复仇效果；
    
- 资源收益；
    
- 生存能力；
    
- 神援充能；
    
- 特定攻击方式的附加效果。
    

这些祝福通常可以相互叠加，但仍可能有：

- 前置条件；
    
- 互斥条件；
    
- 最大获取数量；
    
- 必须持有某个核心祝福；
    
- 必须持有同神的某个下级祝福。
    

## 3.3 关联祝福与高阶祝福

公开代码中的 `LinkedUpgrades` 用来描述需要前置能力才能进入候选池的祝福。

它至少支持两种主要前置结构：

```text
OneOf
持有列表中的任意一个祝福

OneFromEachSet
从多个集合中，各持有至少一个祝福
```

游戏还会将特定的三组前置识别为类似“满足其中两组”的条件结构。

这套关联结构承担了：

- 二阶普通祝福；
    
- 传奇祝福；
    
- 双重祝福；
    
- 某些特殊联动能力。
    

公开脚本会先检查玩家是否拥有要求的祝福，再决定关联祝福是否进入候选；部分高阶能力还有独立的 `PriorityChance`，在满足条件后获得优先插入机会。

## 3.4 传奇祝福与双重祝福

传奇祝福不是普通祝福简单升到“传奇品质”，而是独立技能。

双重祝福也不是某个普通祝福的高品质版本，而是两个神祇之间的独立联动技能。

社区资料显示：

- 传奇祝福通常需要该神的一个或多个前置祝福；
    
- 双重祝福需要同时满足两个神祇的特定前置；
    
- 赫尔墨斯和卡俄斯不提供普通双重祝福；
    
- 双重和传奇祝福满足资格后，仍需要通过对应特殊品质概率检查。([hades.fandom.com](https://hades.fandom.com/wiki/Legendary_Boons "https://hades.fandom.com/wiki/Legendary_Boons"))
    

代码中，传奇和双重祝福都可能使用 `Legendary` 这一品质键；界面再通过 `IsDuoBoon` 判断使用传奇动画还是双重祝福动画。

## 3.5 赫尔墨斯、卡俄斯和代达罗斯锤

这三类奖励应与普通奥林匹斯祝福区分。

赫尔墨斯提供速度、闪避、冲刺和攻击频率等能力，其奖励来源和普通神祇池存在特殊处理。

卡俄斯使用“诅咒—祝福”组合：

1. 玩家先获得一项临时负面效果；
    
2. 经历指定房间数；
    
3. 负面效果解除；
    
4. 永久正面效果生效。
    

公开代码会分别从永久祝福列表和临时诅咒列表中选取结果，并组合成 `TransformingTrait`。

代达罗斯锤属于武器改造奖励，不是某位普通神祇内部的祝福。公开模组可以分别保留或排除：

```text
HermesUpgrade
WeaponUpgrade
```

说明它们在奖励来源层面具有独立身份。

## 3.6 石榴与已有祝福升级

Pom of Power并不向玩家提供新技能池，而是从玩家已有的可升级祝福中选择对象并提高等级。

所以《Hades》的局内成长包含两个不同系统：

```text
获得新祝福
改变构筑结构

升级已有祝福
提高现有构筑强度
```

# 四、第一层随机：房间奖励池

《Hades》的祝福随机并不是从打开祝福界面才开始。更早的一层随机发生在房门奖励生成阶段。

## 4.1 房间奖励不是每次完全独立抽取

公开脚本中存在 `RewardStores`。游戏会从当前奖励仓中选出一个合法结果，随后将该结果从仓中移除。

当仓内没有合法结果时，系统会补充一组新奖励；多次无法生成时，还存在治疗奖励一类的最终保底。

这意味着房间奖励更接近：

```text
有限奖励袋
→ 抽出一个
→ 暂时移除
→ 奖励袋用完后重新装填
```

而不是：

```text
每个房间都从永远不变的概率表独立抽一次
```

这种“袋式随机”可以减少短期内同类奖励过度重复，也能控制一局中祝福、货币、生命、石榴和永久资源的整体密度。

新一局开始时，代码会初始化奖励仓，同时根据夜之圣镜配置初始化局内重抽次数。

## 4.2 金桂冠和蓝桂冠奖励池

社区资料将普通房门奖励分成两个主要类别。

金桂冠奖励主要包括：

- 神祇祝福；
    
- 代达罗斯锤；
    
- 石榴；
    
- 金币；
    
- 半人马之心。
    

蓝桂冠奖励主要包括：

- 黑暗；
    
- 冥府钥匙；
    
- 宝石；
    
- 仙酒。
    

Fated Authority只能把一个房间奖励重抽为同一大类中的其他奖励，不会稳定地把蓝桂冠永久资源变成金桂冠局内成长。([hades.fandom.com](https://hades.fandom.com/wiki/Mirror_of_Night "https://hades.fandom.com/wiki/Mirror_of_Night"))

这是一项非常重要的边界：

> 房门重抽改变的是同级奖励身份，而不是任意改写整个奖励生态。

# 五、第二层随机：本局神祇池

## 5.1 普通神祇池存在四类来源上限

公开函数 `GetEligibleLootNames` 会先检查本局是否已经达到神祇来源上限。

未达到上限时，候选来自所有当前合法的 `GodLoot`。

达到上限后，候选会收缩为已经记录在：

```text
CurrentRun.LootTypeHistory
```

中的神祇来源。

`ReachedMaxGods` 中明确写有：

```text
maxLootTypes = 4
```

并根据本局已经接触的神祇来源判断是否达到上限。

因此，普通流程可以理解为：

```text
本局接触不足4个主要神祇来源
→ 新神和旧神都有机会进入

本局已经形成4个神祇来源
→ 后续普通神祇奖励主要在这4个来源中循环
```

特殊来源如赫尔墨斯和卡俄斯具有独立入口和数据规则，不应简单等同于普通八位奥林匹斯神池。

## 5.2 “接受一个神”也是修改未来随机池

当某个神祇进入本局来源历史后，它不只是给玩家一项当前奖励，还会影响后续可出现的神祇集合。

这使每个神祇选择同时具有两层价值：

```text
当前价值
这一次三选一给了什么

未来价值
这个神会不会持续占用本局神祇池
```

因此，随意接受一个与目标构筑无关的神，可能造成长期池污染。

反过来，尽早确定两个或三个主要神祇，可以提高后续祝福的构筑一致性。

# 六、第三层随机：神祇内部技能池

当系统已经确定奖励来自某个神后，才会进入祝福候选生成。

## 6.1 基础数据池

每个奖励来源的数据会分别记录：

- `WeaponUpgrades`：核心能力祝福；
    
- `Traits`：普通辅助祝福；
    
- `LinkedUpgrades`：需要前置的关联祝福；
    
- `Consumables`：部分可作为选项出现的消耗品；
    
- 特殊来源还可能记录永久祝福、临时诅咒等。
    

初始化时，系统会把这些内容整理为该奖励来源的 `TraitIndex`，并同时保存关联祝福的前置条件。

## 6.2 核心槽位过滤

对于核心技能，系统会扫描玩家已经占用的槽位。

如果当前已有某个核心槽位祝福，则普通候选生成会排除其他占据同一槽位的技能。

例如玩家已经拥有普通攻击祝福，则其他神的普通攻击祝福不会作为普通新技能直接加入；但可能通过替换分支重新出现。

## 6.3 已拥有技能过滤

普通祝福生成时，系统会移除玩家已经拥有的同名技能，避免将其作为一个“新祝福”重复发放。

已有祝福的等级提高主要交给石榴等升级系统，而不是让普通祝福三选一无限重复同名技能。

## 6.4 游戏状态条件过滤

每个技能还会经过 `IsGameStateEligible`。

公开代码支持大量资格条件，包括：

- 必须拥有某个祝福；
    
- 必须拥有列表中的任意一个祝福；
    
- 必须拥有指定数量的前置祝福；
    
- 必须占用某种核心槽位；
    
- 不得拥有某个祝福；
    
- 不得拥有一组互斥祝福；
    
- 必须装备指定信物；
    
- 当前区域、房间深度或流程状态必须满足要求。
    

因此，某个祝福不能出现，往往不是因为“概率太低”，而是因为它当前根本没有进入候选池。

## 6.5 关联祝福进入池

普通技能和满足条件的 `LinkedUpgrades` 会合并为最终合法候选。

之后系统再次移除：

- 已经拥有的非叠加技能；
    
- 当前不满足游戏状态条件的技能。
    

所以神祇内部的技能池是动态的：

# [  
E_g(s)

## 基础技能  
+  
已解锁的关联技能

## 已拥有技能

## 槽位冲突技能

不满足条件技能  
]

其中：

- (g) 是当前神祇；
    
- (s) 是当前局状态；
    
- (E_g(s)) 是该状态下的合法技能集合。
    

---

# 七、优先候选与替换机制

《Hades》不是把所有合法祝福直接混在一起抽取。系统会先处理若干优先分支。

## 7.1 核心祝福优先

`PriorityUpgrades`通常包含攻击、特殊攻击、投弹、冲刺和神援等核心祝福。

系统会检查：

- 玩家是否已经拥有该技能；
    
- 对应槽位是否空闲；
    
- 技能是否满足资格条件。
    

如果槽位空闲，这些核心祝福可能被优先放入三选一。系统会控制优先祝福数量，最多补到三个选项。

设计目的很明确：

> 玩家在接触一个神时，系统优先帮助其建立核心战斗能力，而不是只提供边缘辅助技能。

## 7.2 关联技能优先插入

已经满足前置条件的关联祝福，可能拥有 `PriorityChance`。

系统逐个检查这些关联祝福；若随机检查成功，便在普通候选生成之前插入选项。

这意味着传奇或高级联动技能的出现，并不总是等价于：

```text
与所有普通祝福完全等概率
```

它们可能有独立的资格检查和优先出现分支。

## 7.3 核心技能替换

如果玩家已经占用了核心槽位，新神可以提供替换祝福。

替换后的品质会提高一级：

```text
Common → Rare
Rare → Epic
Epic → Heroic
```

替换选项会保存：

- 被替换技能；
    
- 旧品质；
    
- 新技能；
    
- 新品质。
    

因此，填满核心槽位有两个相反效果：

1. 普通同槽位候选会被排除，帮助缩小普通池；
    
2. 替换分支可能重新提供同槽位技能，并以更高品质诱导玩家改变构筑。
    

这是一个很精巧的机制：

> 槽位占用不是彻底封死选择，而是把“新技能”转换成“付出替换代价的高品质技能”。

# 八、第四层随机：品质分桶

## 8.1 先建立合法品质表

系统会为所有当前候选建立五个品质表：

```text
Common
Rare
Epic
Heroic
Legendary
```

一个技能只有在自己的数据中支持某个品质，才会进入对应品质表。

同一个普通祝福通常可能同时进入：

```text
Common
Rare
Epic
Heroic
```

传奇或双重祝福则可能进入 `Legendary` 表。

## 8.2 品质按顺序检查，而不是一次归一化抽取

普通候选填充时，系统按照以下顺序检查：

```text
Legendary
→ Heroic
→ Epic
→ Rare
→ Common
```

如果传奇检查成功，就不再检查后续品质；传奇失败后才检查英雄，依次类推。

假设对应品质表均非空，各检查概率分别为：

- (p_L)：传奇；
    
- (p_H)：英雄；
    
- (p_E)：史诗；
    
- (p_R)：稀有。
    

则实际结果为：

[  
P(L)=p_L  
]

[  
P(H)=(1-p_L)p_H  
]

[  
P(E)=(1-p_L)(1-p_H)p_E  
]

[  
P(R)=(1-p_L)(1-p_H)(1-p_E)p_R  
]

[  
P(C)=(1-p_L)(1-p_H)(1-p_E)(1-p_R)  
]

如果某个品质桶为空，则跳过对应检查。

因此，界面中显示的品质概率不能简单理解为相互独立、相加等于100%的静态表。它们是有顺序的条件检查。

## 8.3 决定品质后，再从该品质候选中选技能

公开脚本普通填充分支使用：

```text
GetRandomValue(rarityTable[品质])
```

选择具体候选，没有看到类似《吸血鬼幸存者》那种每个普通祝福拥有独立 `rarity weight` 的处理。

因此，在这个脚本层面可以判断：

> 同一品质桶中的技能身份差异，主要来自资格、优先分支和前置条件，而不是每个技能另有一套公开权重。

谨慎地写成条件概率：

[  
P(i\mid R=r,s)  
\approx  
\frac{1}{|B_r(s)|}  
]

其中 (B_r(s)) 是当前状态下支持品质 (r) 的合法候选集合。

优先候选、替换候选以及特殊脚本会打破这一简化公式，所以它只适用于普通填充分支。

## 8.4 三个选项不重复

一个技能被选中后，会立刻从所有品质表中移除。

因此，同一祝福不会因为同时存在于Common、Rare、Epic等多个桶中，而在同一次三选一里重复出现。

这相当于一次带品质条件的无放回抽样。

---

# 九、祝福品质如何影响实际数值

获得品质后，系统会读取技能的 `RarityLevels`。

某个品质可能对应：

- 固定倍率；
    
- 最小倍率到最大倍率之间的随机值。
    

如果配置的是范围，系统会在该范围中再次调用随机数生成倍率。

因此，《Hades》的品质随机可能有两层：

```text
第一层：获得Common、Rare、Epic或Heroic

第二层：在该品质允许的数值范围内生成具体倍率
```

例如两个同为Epic的祝福，具体数值未必完全相同。

代码还特别对技能数据的处理顺序进行了排序，因为属性计算会消耗随机数，顺序不稳定会破坏同一种子下的确定性。

---

# 十、局内随机控制手段

《Hades》给玩家的随机控制可以分成五层。

## 10.1 控制房间奖励类型

### Dark Foresight

夜之圣镜中的Dark Foresight提高金桂冠奖励出现概率。

满级效果为：

```text
每级 +2%
最高 +20%
```

它提高祝福、锤子、金币、石榴和生命上限等局内成长奖励相对于永久资源奖励的比例。([hades.fandom.com](https://hades.fandom.com/wiki/Mirror_of_Night "https://hades.fandom.com/wiki/Mirror_of_Night"))

它控制的不是：

```text
某个具体祝福的概率
```

而是：

```text
整局获得构筑机会的次数
```

这是奖励密度控制。

### Fated Authority

Fated Authority最多提供8次房门奖励重抽。

它改变的是下一房间奖励身份，且通常保持在原本的金桂冠或蓝桂冠大类内。([hades.fandom.com](https://hades.fandom.com/wiki/Mirror_of_Night "https://hades.fandom.com/wiki/Mirror_of_Night"))

适合用来：

- 寻找更多神祇祝福；
    
- 寻找特定神；
    
- 将不需要的金币或生命改为其他金桂冠奖励；
    
- 调整本局奖励来源分布。
    

缺点是它不能直接控制某位神内部的祝福选项。

## 10.2 控制下一位神祇

八位普通奥林匹斯神的信物具有两项能力：

1. 下一次普通神祇祝福来自指定神；
    
2. 该神祝福获得Rare或更高品质的概率增加10%/15%/20%。
    

强制神祇效果每件信物一局触发一次；只要继续佩戴，品质加成仍然生效。([hades.fandom.com](https://hades.fandom.com/wiki/Keepsakes "https://hades.fandom.com/wiki/Keepsakes"))

它的真正价值不仅是“保证见到某个神”，还包括：

- 在四神池形成前主动占据一个神祇位置；
    
- 提前获得目标构筑的基础前置；
    
- 为双重祝福引入第二位指定神；
    
- 避免神池被无关神祇占满。
    

典型策略是：

```text
塔耳塔罗斯：神A信物
获得第一组核心或前置

水仙花平原：神B信物
引入双重祝福的第二位神

至福乐土以后：换生存或输出信物
```

## 10.3 控制祝福品质

夜之圣镜提供两组互斥路线。

### Olympian Favor与Dark Foresight

Olympian Favor：

```text
每级 +1% Rare概率
最高 +40%
```

Dark Foresight：

```text
每级 +2% 金桂冠奖励概率
最高 +20%
```

玩家必须在：

```text
单次祝福品质更高
```

和：

```text
整局获得更多局内成长奖励
```

之间选择。([hades.fandom.com](https://hades.fandom.com/wiki/Mirror_of_Night "https://hades.fandom.com/wiki/Mirror_of_Night"))

### Gods' Pride与Gods' Legacy

Gods' Pride：

```text
每级 +1% Epic概率
最高 +20%
```

Gods' Legacy：

```text
每级 +1% Legendary或Duo概率
最高 +10%
```

玩家必须在：

```text
普通祝福稳定高品质
```

和：

```text
高阶联动祝福成型率
```

之间选择。([hades.fandom.com](https://hades.fandom.com/wiki/Mirror_of_Night "https://hades.fandom.com/wiki/Mirror_of_Night"))

这不是简单的强弱关系，而是构筑目标不同：

- 普通高伤害构筑偏向Gods' Pride；
    
- 依赖传奇或双重祝福的构筑偏向Gods' Legacy。
    

此外，迷你Boss、厄瑞玻斯房间、斯堤克斯神庙中的高价祝福，以及Yarn of Ariadne、Refreshing Nectar等资源，也会提高祝福品质或高阶祝福机会。([hades.fandom.com](https://hades.fandom.com/wiki/Boons "https://hades.fandom.com/wiki/Boons"))

## 10.4 控制神祇内部三选一

### Fated Persuasion

Fated Persuasion最多提供4枚用于祝福和卡戎之井选项的重抽骰子。([hades.fandom.com](https://hades.fandom.com/wiki/Mirror_of_Night "https://hades.fandom.com/wiki/Mirror_of_Night"))

它比房门重抽更直接，因为它作用于：

```text
已经确定神祇之后的具体技能三选一
```

但公开代码揭示了一个容易误解的细节。

重抽时，系统会：

1. 收集旧三选一中的所有技能名；
    
2. 从中随机选择一个；
    
3. 仅将这一个技能加入排除列表；
    
4. 重新生成三选一。
    

因此，重抽不是：

```text
保证三个结果全部更换
```

而是：

```text
至少排除一个旧结果
另外两个旧结果仍可能再次出现
```

这是一种“部分刷新”设计。

它既保证了重抽有一定新鲜度，又避免重抽成为过强的精确搜索工具。

### 重抽的最佳时机

重抽只有在目标技能已经满足资格时才有价值。

错误使用：

```text
尚未获得双重祝福前置
→ 对某位神连续重抽
→ 目标双重祝福概率仍然是0
```

正确使用：

```text
先拿齐前置
→ 确认目标已经进入LinkedUpgrades合法池
→ 再用Fated Persuasion刷新
```

因此，重抽资源的价值取决于当前候选池状态，而不是固定的。

## 10.5 通过选择本身裁剪奖励池

这是《Hades》最隐蔽、也最强的随机控制。

### 占据核心槽位

当玩家填满普通攻击、特殊攻击、投弹、冲刺等核心槽位后，其他占用这些槽位的普通候选会被排除。

因此，填入非目标槽位可以减少目标神祝福池中的无关核心选项。

但这也可能触发高品质替换选项，所以并非纯粹的永久封印。

### 获取前置技能

获得一个前置祝福会让若干二阶、传奇或双重祝福从0概率变为可出现。

所以一次当前强度普通的前置技能，可能显著提高未来构筑上限。

### 避免无关前置

有些构筑并不希望过早解锁大量关联祝福，因为每个新解锁祝福都会扩大候选池。

这会形成典型的池污染：

```text
获取过多无关低阶祝福
→ 解锁大量二阶技能
→ 目标技能在合法池中的占比下降
```

### 控制神祇数量

避免接触无关神祇，可以防止四神池被过早填满。

所以玩家在房门处跳过某个神，本质上是在保护未来神池。

# 十二、典型构筑的随机控制流程

假设玩家想要神A与神B的双重祝福。

## 阶段一：提前查明资格

需要明确：

- 神A要求哪些核心或辅助祝福；
    
- 神B要求哪些核心或辅助祝福；
    
- 两组前置是否存在槽位冲突；
    
- 当前武器形态是否改变投弹或攻击技能名称。
    

目标双重祝福在前置未满足时，概率严格为0。

## 阶段二：锁定第一位神

塔耳塔罗斯佩戴神A信物。

目标不是立刻追求双重祝福，而是优先获得：

- 神A核心前置；
    
- 神A必要的二阶前置；
    
- 与武器形态相符的核心技能。
    

## 阶段三：引入第二位神

进入下一地区后换神B信物。

此时要避免：

- 神祇池被其他无关神填满；
    
- 选择与目标前置冲突的核心技能；
    
- 解锁大量与目标无关的关联祝福。
    

## 阶段四：完成资格后再投入重抽

当神A和神B的前置都满足后：

- 目标双重祝福才进入合法池；
    
- Gods' Legacy开始产生实际价值；
    
- Fated Persuasion才应集中投入。
    

## 阶段五：后期切换稳定性资源

目标核心成型后，继续强行佩戴神祇信物的收益下降。

此时可换成：

- 生存信物；
    
- Boss战信物；
    
- 经济信物；
    
- 伤害增益信物。
    

这体现出《Hades》的随机控制节奏：

```text
前期控制来源
→ 中期控制资格
→ 成型节点控制具体候选
→ 后期转向战斗稳定性
```

# 十三、与《吸血鬼幸存者》的结构差异

## 《吸血鬼幸存者》

主要逻辑是：

```text
统一武器/被动池
→ 资格过滤
→ 单物品相对权重
→ 多选项无放回抽取
→ 已有装备升级倾向
```

关键控制问题是：

```text
某件装备的权重占总权重多少
```

## 《Hades》

主要逻辑是：

```text
房间奖励来源
→ 神祇来源池
→ 四神来源限制
→ 神内技能资格
→ 优先与替换分支
→ 品质分桶
→ 桶内随机
```

关键控制问题是：

```text
目标技能是否已经进入合法品质桶
```

所以《Hades》中最常见的概率误判是：

> “我已经见到这个神很多次，为什么还没有目标技能？”

可能原因不是运气差，而是：

- 前置未满足；
    
- 核心槽位冲突；
    
- 技能已被其他条件排除；
    
- 目标属于Legendary/Duo，但特殊品质检查未通过；
    
- 神池或关联技能池被其他内容扩大；
    
- 重抽发生在目标获得资格之前。

# 十四、对ProjectVL的设计启示

这套机制对ProjectVL的价值，不在于复制“神祇祝福”，而在于吸收其分层控制思想。项目文件说明当前工作对应ProjectVL仓库。

## 14.1 不要把所有卡牌放进一个统一大池

可以建立：

```text
奖励来源池
→ 卡牌家族池
→ 具体技能池
→ 星级池
```

例如先决定：

- 输出；
    
- 控制；
    
- 防御；
    
- 资源；
    
- 特殊构筑。
    

再从对应家族中抽具体卡牌。

这样新内容不会直接稀释所有旧内容。

## 14.2 限制一局中的活跃构筑家族

Hades通过四神池形成一局的构筑边界。

ProjectVL可以考虑：

- 一局最多激活3～4个技能家族；
    
- 新家族进入后，占用本局来源名额；
    
- 达到上限后，普通掉落优先从已有家族中生成；
    
- Boss或特殊奖励可以突破上限。
    

这能让随机局面逐渐收敛，而不是随游戏进行持续膨胀。

## 14.3 把技能身份和星级分开生成

Hades将：

```text
出现什么祝福
```

和：

```text
该祝福是什么品质
```

分成不同层。

ProjectVL同样可以将：

```text
卡牌类型
```

和：

```text
卡牌星级
```

分别计算。

这比把“1星火球、2星火球、3星火球”全部当作独立候选更容易控制。

## 14.4 让玩家的选择改变未来池

玩家拿到某张卡后，可以：

- 解锁关联技能；
    
- 排除互斥技能；
    
- 提高同家族出现率；
    
- 激活进化候选；
    
- 触发融合路径；
    
- 收缩无关家族。
    

如此一来，玩家选择的不只是即时战斗力，也是在设计自己的后续奖励池。

## 14.5 重抽不必保证全部更新

Hades只排除一个旧结果的做法，提供了一种中间方案：

```text
完全独立重抽
可能三个都重复，体验差

排除全部旧结果
控制力过强，池子消耗过快

排除至少一个旧结果
保证部分变化，同时保留随机性
```

ProjectVL可以采用：

- 首次重抽排除一个旧选项；
    
- 连续重抽逐步增加排除数量；
    
- 高级重抽才保证全部更换。
    

## 14.6 将元成长设计为互斥的随机控制方向

Hades的夜之圣镜让玩家在以下方向中做互斥选择：

- 更多局内成长奖励；
    
- 更高普通品质；
    
- 更高传奇/联动概率；
    
- 房门奖励重抽；
    
- 具体技能重抽。
    

ProjectVL也可以把随机控制拆成不同流派：

```text
广度型
每次出现更多选项

品质型
高星卡概率提高

定向型
目标家族权重提高

纠错型
更多重抽或排除

收敛型
更容易出现已有构筑升级
```

不能让玩家同时把所有控制手段拉满，否则随机系统会退化为固定配装。

# 十六、最终结论

《Hades》的技能池可以概括为：

# [  
\text{最终祝福}

\text{房间奖励控制}  
\times  
\text{神祇来源控制}  
\times  
\text{资格过滤}  
\times  
\text{优先与替换规则}  
\times  
\text{品质检查}  
\times  
\text{桶内随机}  
]

它最成功的地方，不是给玩家无限重抽，而是把随机控制分散在整个局内决策链中：

- 选择哪扇门；
    
- 是否引入某位神；
    
- 是否让神池达到四类上限；
    
- 是否占据某个核心槽位；
    
- 是否拿取某个前置；
    
- 是否扩大关联祝福池；
    
- 是否选择普通高品质或传奇联动路线；
    
- 在什么时点消耗重抽。
    

最终形成的体验是：

> 玩家无法直接命令系统给出目标技能，但可以通过一连串可理解的决策，把目标技能从“不可能出现”逐步变成“高概率出现”。

这正是《Hades》比简单加权随机池更具有构筑策略性的根本原因。

这份报告是别人扒 Hades 1（哈迪斯）旧版脚本和模组代码，反推出它的"神力"（boon）掉落系统到底是怎么随机的。核心结论一句话：**Hades 的随机不是抽一次就完事，而是连续好几层筛选叠加起来的**。翻成人话，分五层：

**第一层：这个房间给不给技能**  
进房间先决定这次奖励是"局内成长类"（金币/血瓶/神力/铁匠锤等）还是"局外成长类"。这个比例会跟着"你这局已经拿了多少局外奖励"动态调整，越往后局外奖励概率越走向一个目标值——不是纯拍脑袋随机，而是有个反馈闭环在压着比例。

**第二层：这个房间如果给技能，是哪个神**  
先圈定一个"候选神/来源"的名单（比如你已经点了哪个神、装备的挂件锁定了哪个神、目前神池里有几个神），再从这个名单里选一个。关键点：备用商店（卡戎商店）里那种"随机神力"是特例，抽到了也不会把这个神正式算进你本局的"神池"——也就是说"看到某神一次"和"这个神正式进入你本局可抽范围"不是一回事，需要分开算。

**第三层：这个神下面，哪些具体技能有资格出现**  
不是这个神所有技能都能抽，要过滤：前置条件（比如某些组合技/传奇技需要你先点过另外两个神的技能）、互斥（比如某些技能天生打架，出了一个另一个就不能出）、你当前武器/形态的专属限制、以及"替换型技能"（不是新加一条效果，而是替换掉你已有的某条效果，界面上会画个小图标提示"这个会替换掉你原来那个"）。报告里专门强调：这类前置/互斥不是一个简单标签，而是"组合前置+额外条件+互斥列表"这种复合结构，最好整理成一张数据表，而不是写死在代码逻辑里。

**第四层：候选技能里最终显示几个、你能看到谁**  
系统内部可能算出了一大堆合格候选，但界面只显示其中3个（可以被镜子升级/加成道具改成更多）。这里有个很实际的数字案例：假设某神下有12个合格技能，正常显示3选1，你抽中某个特定技能的概率是 3/12=25%；如果把候选数扩到5个，概率就变成 5/12≈42%；如果直接"锁定1个必出+另外2个随机"，那个被锁定的技能概率直接变100%，其余普通技能反而被挤到 2/11≈18%。**换句话说，"扩大候选数"和"塞入必出项"对最终概率的影响完全不是一个量级，设计时要分清楚在动哪根杠杆。**

**第五层：品质（稀有度）**  
每次生成候选时，系统会实时算一个"稀有/史诗/传奇"的概率表，这个概率表由基础值+房间加成+镜子升级+临时幸运buff动态叠加得出——也就是说稀有度不是写死在技能本身上的固定属性，而是"当时的情境"临时算出来的。传奇/组合技这类特殊稀有度还必须先满足前置资格，才轮到用专门的概率去判定要不要给。

对你们的技能池重设计，这份报告里最值得抄的思路是：

1. **五层严格分离，互不干扰**。房间给不给奖励、给哪个来源、来源下哪些技能合格、最终展示几个、最终品质多高——Hades 的模组生态证明这五层在代码里是真的分开的（有人只改第一层，有人只改第三层，互不影响）。这样设计师改一个参数不会意外牵动别的层，也是这份报告反复强调的"健康随机系统"的标志。
2. **"幸运"要拆开做，不要做成一个万能加成**。Hades 里"提高幸运"这件事被拆成了三种独立旋钮：影响来源的幸运（比如让某个方向的奖励更容易出现）、影响候选池的幸运（保底出某类来源）、影响品质的幸运（提高稀有度）。不要把"运气"做成一个笼统的+X%全局修正，拆开后玩家更容易理解"我这个道具具体在帮我什么"。
3. **前置/互斥数据化，别写死在if里**。技能之间的前置和互斥关系建议整理成一张类似"每个技能自带：前置类型、前置数据、额外要求、互斥列表"的数据表，这样仿真脚本和游戏本体能共用一套规则，你们现在的12卡+星级体系如果以后要加"组合技/进阶技"，这套数据结构可以直接借。
4. **"必出项"分两种做法，效果天差地别**：一种是整页推倒重来+锁死不能重抽（适合教程或者强引导第一次拿技能）；另一种是保留原本的三选一，只是塞进去一个必出的候选、不锁重抽（适合正常养成体验，因为玩家还能赌一把剩下两个格子）。你们要做定向掉落保底的话，这两种手感完全不同，值得先想清楚要哪种。

### 神池机制的本质

先厘清一个容易搞混的点：报告里说的"神池"不是一个概率表，而是一个**离散状态集合**——本局当前"可以给你发 boon 的神"名单，加上一个硬性容量上限（报告里提到的"4 神池上限"）。这个集合本身是有状态、会被写入/变更的东西，跟"某一次抽奖的概率分布"是两个不同层面的对象。抽奖发生在这个集合确定之后。

### 神池在调用链里的位置

按报告给出的调用顺序，神池的读取和写入发生在 `GetEligibleLootNames` 这一层，而不是更下游的 `SetTraitsOnLoot`（候选生成）或 `GetRarityChances`（品质层）。也就是说：

```
ChooseRoomReward → GetEligibleLootNames（神池在这里被读出、过滤）→ ChooseLoot（把选中的来源名实例化成具体 LootData）
```

`GetEligibleLootNames` 的职责是返回一张"来源名表"（比如 `AresUpgrade`、`AthenaUpgrade` 这种字符串标识），而不是直接对具体 boon 做抽样。这一点报告的证据链需要注意：**vanilla 版本这个函数的正文本身没有被公开网页完整暴露**,报告是通过 `OneGodOnly` 这个模组的 hook 行为反推出它的 I/O 契约的——`OneGodOnly` 把这张来源名表强行替换成 `{ DesiredOlympian .. "Upgrade" }`，再按条件把 `HermesUpgrade`、`WeaponUpgrade` 追加进去。能这样替换，说明原函数确实是"先产出一张离散候选来源表，再从表里选"，而不是端到端的一次性抽样。这是**间接证据**，不是直接读到源码，报告本身也把这一点标注为待本地校验项。

### 决定神池成员资格的状态变量

报告列出的相关状态量至少包括：

- 当前已激活/可进入的 Olympian 集合（也就是"4 神池"本体）
- 是否已达到 4 神池的容量上限（上限触发后，新神大概率不会再被纳入候选来源表）
- 是否装备了 Olympian keepsake（这会锁定期望神源，见下）
- 是否存在 `ForceBoonName` 或某种强制 reward trait（外部注入覆盖正常筛选）
- Hermes 与 Daedalus Hammer 的资格判定是独立于 Olympian 神池之外的（它们不占用 4 神池名额，是并行的独立槽位）
- 商店或特殊房间是否有专属来源规则（见 Charon 例外）

### 关键例外：Wrapped Boon 与"出现"vs"写入池"的区分

报告特别强调了一个反直觉但很关键的证据：Charon 商店里的 Wrapped Boon 会给出"随机某神的 boon"，**但 Hades Wiki 明确说明这个事件不会把该神写入本局的 4 神池**。

这意味着"你看到了一次来自某神的 boon"和"这个神被正式记入本局活跃神池、从此可以在普通房间被正常抽到"是两个语义完全不同、需要分开建模的状态转移。如果仿真器或你自己的系统把"出现过一次"直接等同于"进池"，会系统性地算错后续神池分布。报告建议这个 Wrapped Boon 路径必须单独建模，不能并入常规神池写入逻辑。

### Keepsake 的双重机制与神池的交互

Olympian boon keepsake 在报告里被拆成两个独立效果，且生命周期不同：

1. **一次性保底**：只在本局触发一次，效果是强制来源层给出该神的 boon（这大概率意味着一次强制写入/锁定神池成员资格，具体写入时机报告未完全证实，属于待本地校验项）。
2. **持续 rarity bonus**：只要装备着，就持续影响 `GetRarityChances` 的品质层加成，这个效果和神池成员资格无关，是纯粹叠加在品质层的乘子。

报告的建议是：仿真器里这两个效果必须拆成两个独立字段（"来源保底触发一次"+"品质加成持续生效"），不能合并成一个"这个神被加成了"的笼统状态，否则会把一次性事件和持续效果的时间窗口搞混。

### 均匀抽样假设及其验证方法

报告给出一个**待验证的近似假设**：在不考虑 keepsake 保底和强制 boon 的普通 boon 房里，`GetEligibleLootNames` 返回的 Olympian 来源集合内部是均匀抽样。这只是假设，报告要求用本地只读日志记录 `eligible_loot_names` 与最终 `chosen_loot_name`，然后按房型/biome/keepsake 状态分组做卡方检验，才能确认是否真的均匀，还是存在隐藏权重（比如越晚出现的神权重越高之类）。

### 数学分解

报告把神池相关的概率写成两段乘积而不是一个数：

```
P(god | state) = P(room reward is boon-like source | state) × P(god source | boon-like source, state)
```

第一段是房间层决定"这一房给不给来源类奖励"（跟神池无关，跟 RunProgress/MetaProgress 比例有关）；第二段才真正进入神池筛选。报告强调这个分解的意义在于：如果你观察到"某神迟迟不出现"，需要先排除是不是第一段（房间根本没给来源类奖励）在起作用，而不是直接归因于神池权重异常。

### 对你们系统的技术含义

如果要把这套"神池"逻辑搬到你们的技能池设计里，报告暗示的关键设计原语是：

- 神池应该是一个**显式的、有容量上限的状态集合**，而不是"每次都从全部技能源里按权重抽"；
- 需要区分**"候选来源表生成"**（离散集合层面的过滤/上限判断）和**"从候选来源表选一个"**（这一步才是真正的随机抽样），这两步不要合并成一次操作；
- "出现一次"和"写入池、获得持续资格"必须是两个可以独立发生的事件（对应 Wrapped Boon 例外），这样你可以设计出"一次性彩蛋来源"而不污染常规池状态；
- 保底类道具（keepsake 类比物）应该拆成"一次性强制写入"和"持续品质/概率加成"两个字段，分开实现、分开测试。

|基础武器|角色初始武器、升级选择、商人等|是|
|被动道具|升级选择、地图固定拾取|是|
|进化武器|满足配方后开宝箱|通常否|

|奥秘卡牌|开局、特定时间宝箱等|使用独立奥秘池|
|特殊角色武器|特定角色初始携带或极低权重|不一定正常出现|
|Candybox等特殊奖励|宝箱或特殊机制|独立选择逻辑|

普通升级界面只会提供“武器和被动道具”，每次通常给出3或4个不同选项。([吸血鬼幸存者百科](https://vampire-survivors.fandom.com/wiki/Level_up?utm_source=chatgpt.com "Level up - Vampire Survivors Wiki - Fandom"))

例如，鞭子进化为血鞭，并不是升级时从“鞭子”和“血鞭”两个选项中随机抽。玩家先把鞭子升满、持有对应被动，再通过宝箱触发进化。绝大部分进化武器因此不会污染普通升级池。([吸血鬼幸存者百科](https://vampire-survivors.fandom.com/wiki/Weapons?utm_source=chatgpt.com "Weapons | Vampire Survivors Wiki - Fandom"))

所以假设图鉴里有180项，真正属于普通升级获取池的，可能只有其中几十项。

## 二、玩家没有一次性解锁全部道具

新玩家开局时只拥有少量基础武器和被动道具。

其他内容需要通过具体条件逐渐解锁，例如：

- 使用某个角色存活一定时间；
    
- 将某件武器升级到特定等级；
    
- 击败指定敌人；
    
- 在地图中找到遗物；
    
- 完成某张地图；
    
- 使用某件武器造成一定伤害。
    

只有已经解锁、允许正常获得、没有被封印的道具，才可能进入对应候选池。社区对游戏池机制的整理也指出，道具只有在解锁且没有被排除时才会进入池中。([Steam社区](https://steamcommunity.com/app/1794680/discussions/0/3418810907932994082/?utm_source=chatgpt.com "How does the item pool work? :: Vampire Survivors ..."))

这是一种非常重要的“渐进式内容放量”：

- 新手只有很小的随机池，容易理解；
    
- 中期逐渐扩大，开始产生组合变化；
    
- 后期池子变大，但玩家也获得了更多控制工具。
    

因此，道具数量的增长与玩家驾驭随机性的能力基本同步。

## 三、六武器、六被动的槽位会迅速关闭随机池

默认情况下，一局通常只能主动装入：

- 6种武器；
    
- 6种被动道具。
    

当武器槽还有空位时，升级界面可以出现：

1. 已持有武器的升级；
    
2. 尚未持有的新武器。
    

但是一旦6个武器槽全部占满，绝大多数新武器就不再有资格出现，升级选择会集中到玩家已经拿到的武器上。

被动道具同理。

这意味着随机池会随着游戏进行经历一个反直觉的变化：

> 前期候选范围较大；  
> 中期玩家确定构筑后，候选范围反而越来越小。

例如玩家已经拿到：

- 鞭子；
    
- 魔杖；
    
- 圣水；
    
- 斧头；
    
- 圣经；
    
- 月桂。
    

六个武器槽已经满了。此后即使游戏解锁了几十种武器，普通升级也不会继续让玩家在几十种新武器中抽取，而主要提供这六件武器的后续等级。

因此，一局里的多数升级不是“再抽一件新装备”，而是：

> 从自己已经选中的装备中，选择下一次强化。

这也是为什么《吸血鬼幸存者》能够拥有庞大内容库，却仍然保持稳定的成长感。

## 四、每件道具的出现概率并不相等

它不是简单的等概率随机。

每件可选道具都有自己的“权重”或稀有度值。升级时，系统从当前所有符合条件的道具中，根据权重进行抽取。候选池总权重，是所有当前合法道具权重的总和。([吸血鬼幸存者百科](https://vampire-survivors.fandom.com/wiki/Level_up?utm_source=chatgpt.com "Level up - Vampire Survivors Wiki - Fandom"))

例如，一些基础武器具有较高权重，容易看到；一些特殊武器权重极低，正常角色很难随机获得。社区资料举例称，常规武器可能有100左右的权重，而某些角色特色武器只有1左右。([Steam社区](https://steamcommunity.com/app/1794680/discussions/0/3418810907932994082/?utm_source=chatgpt.com "How does the item pool work? :: Vampire Survivors ..."))

这样可以同时实现两个目标：

- 常规核心构筑比较稳定；
    
- 特殊武器偶尔出现，制造惊喜。
    

所以“加入更多道具”不等于“每件道具都等比例稀释”。

不过需要注意：**只靠低权重并不能彻底解决池子膨胀。**真正有效的是权重、槽位限制、分池、解锁门槛几种机制共同工作。

## 五、地图固定道具不会与升级池直接竞争

许多被动道具会预先放在地图上的固定地点。

这类道具有几个作用：

1. 给地图提供差异；
    
2. 允许玩家主动规划路线；
    
3. 给某些进化配方提供确定性；
    
4. 允许玩家在占满普通被动槽后，额外拾取地图道具。
    

例如，玩家可以先通过升级拿满6个被动槽，再去地图上拾取额外被动，从而突破常规槽位限制。这不是随机池直接提供的，而是地图探索奖励。

因此，《吸血鬼幸存者》把一部分构筑决定从“随机升级”转移到了“空间探索”：

> 没抽到不一定代表得不到；玩家也可以通过地图路线保证获得。

## 六、不同来源使用不同随机池

游戏并没有一个统一的“所有道具随机池”。

实际上至少可以理解为几个互相隔离的系统：

### 升级池

主要提供基础武器、被动道具及其等级。

### 光源掉落池

提供金币、回血鸡、磁铁、念珠、冻结时间等即时消耗品。幸运属性会影响光源掉落中部分物品的权重。([吸血鬼幸存者百科](https://vampire-survivors.fandom.com/wiki/Luck?utm_source=chatgpt.com "Luck - Vampire Survivors Wiki - Fandom"))

### 宝箱池

主要升级已经持有的武器和被动，并在满足条件时触发武器进化。

### 奥秘池

只提供奥秘卡牌，不会和普通武器混抽。

### 地图固定池

由关卡配置决定，位置通常固定。

### 商人或特殊奖励池

玩家可以购买或直接指定某些物品。例如部分特殊武器可以从商人处获得。([吸血鬼幸存者百科](https://vampire-survivors.fandom.com/wiki/Carr%C3%A9llo?utm_source=chatgpt.com "Carréllo - Vampire Survivors Wiki - Fandom"))

这叫做**按来源分池**。它是控制大型内容库最关键的设计手段之一。

## 七、游戏还允许玩家主动“修剪”随机池

随着玩家推进，会解锁一整套随机控制工具：

- **重选 Reroll**：重新生成本次选项；
    
- **放逐 Banish**：本局内不再出现某件道具；
    
- **跳过 Skip**：这次不选道具；
    
- **封印 Seal**：开局前直接把某件道具从池中移除。
    

封印可以在图鉴界面中预先排除升级选项或部分光源掉落物。([吸血鬼幸存者百科](https://vampire-survivors.fandom.com/wiki/Seal?utm_source=chatgpt.com "Seal - Vampire Survivors Wiki - Fandom"))

放逐则是在一局中临时移除某件道具；被放逐后，它通常不会再作为升级选项出现。([吸血鬼幸存者百科](https://vampire-survivors.fandom.com/wiki/Banish?utm_source=chatgpt.com "Banish - Vampire Survivors Wiki - Fandom"))

这形成了一个完整的成长过程：

- 新手池子小，不需要管理；
    
- 老玩家池子大，但能封印、放逐和重选；
    
- 想玩特定构筑的玩家可以主动缩池；
    
- 想体验混乱随机的玩家也可以不缩池。
    

## 八、为什么玩家仍然能够稳定凑出进化配方

因为游戏并不是要求玩家在180个条目中随机凑出两件指定物品。

实际流程更接近：

1. 从有限的基础武器池中选一件武器；
    
2. 一旦选中，它会持续进入后续升级候选；
    
3. 玩家看到对应被动时主动锁定；
    
4. 六个槽位逐渐填满，其他新道具退出候选；
    
5. 武器升满后，通过宝箱完成进化。
    

也就是说，它采用的是：

> 前期随机选择构筑方向，后期稳定兑现已经选择的方向。

随机主要负责“这局玩什么”，而不是反复阻止玩家把已经选中的东西升满。

这和完全随机掉落制有本质区别。

## 九、它仍然存在池子膨胀问题

你的担心不是多余的。随着DLC不断加入，《吸血鬼幸存者》的确会出现：

- 指定武器越来越难抽；
    
- 特定进化组合成形更慢；
    
- 新内容与旧内容相互稀释；
    
- 不熟悉图鉴的玩家难以判断配方；
    
- 多DLC同时开启时，升级界面更杂乱。
    

游戏并没有彻底消除这个问题，而是依靠以下手段压制它：

1. DLC和内容逐步解锁；
    
2. 角色初始武器保证核心起点；
    
3. 进化物不进入普通池；
    
4. 六武器、六被动快速封闭构筑；
    
5. 不同来源分池；
    
6. 权重控制；
    
7. 封印、放逐、重选；
    
8. 地图固定道具；
    
9. 特殊选择箱和商人提供定向获得。
    

所以结论不是“池子完全不会乱”，而是：

> 池子确实会膨胀，但系统通过层层隔离和玩家控制，将混乱限制在前期少数几次构筑选择中。

## 十、对“魅魔心防 / ProjectVL”最值得借鉴的原则

你当前项目对应的是ProjectVL仓库。

最值得借鉴的并不是“可以做180件道具”，而是下面这条公式：

> 总内容库 ≠ 单局掉落池 ≠ 当前时刻候选池。

可以拆成三层：

### 总内容库

游戏累计拥有的全部卡牌、装备、进化、特殊奖励。

例如未来可以有60张卡，但不会一局全部进入随机。

### 本局池

根据角色、关卡、已解锁内容、携带流派、验证期配置生成。

例如60张总卡牌中，本局只启用18张。

### 当前候选池

根据槽位、已有装备、星级、进化路线、当前波数继续缩小。

例如本局18张卡中，当前掉落真正可能出现的只有：

- 4张已拥有卡的升级材料；
    
- 3张当前流派相关卡；
    
- 2张保底或功能卡。
    

最终的有效池只有9张。

对于ProjectVL尤其需要避免这种设计：

> 解锁一张新卡，就永久向所有局的统一掉落池增加一张卡。

这样内容越多，玩家越难完成高星合成，新增内容反而会降低所有旧构筑的完成率。

更合理的结构是：

- 普通掉落池只放基础卡；
    
- 高星卡由精英、Boss、悬赏等独立池产出；
    
- 进化卡不直接进入普通池；
    
- 已选择卡牌获得后续权重提升；
    
- 槽位满后，显著减少陌生新卡；
    
- 每局按角色、关卡或流派抽取一个子池；
    
- 提供封印、锁定、刷新或定向保底；
    
- 万能卡作为纠偏资源，而不是普通卡池的一员。
    

一句话概括：

> 《吸血鬼幸存者》不是让180种道具共同随机，而是用“分池、解锁、槽位闭合、权重和定向控制”，把庞大图鉴压缩成每局可管理的构筑选择。
