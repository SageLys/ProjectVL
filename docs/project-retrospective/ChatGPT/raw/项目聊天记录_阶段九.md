# 二、当前代码实际是怎么工作的

## 1. 经验主链

当前所有击杀最终都会进入统一的 `killEnemy()`：

```text
敌人死亡
→ killEnemy()
→ 结算掉落
→ 计算 XP
→ addXp()
→ 检查累计阈值
→ levelUp()
→ 生成遗物三选一
→ 放入决策队列
→ 暂停游戏
```

经验计算目前是：

```text
敌人 XP
× progression.killXpMul
× (1 + xpGainBonus)
× 装备提供的 xpMul
```

随后调用 `addXp()`。

`addXp()` 使用的是**累计经验阈值**，一次获得大量经验时可能连续跨越多个阈值，并一次排入多个遗物决策。

现有测试甚至专门确保“一次获得40点经验时，连续产生三个遗物选择并排队”。

这正是新系统必须改掉的行为。新的自动奖励不能在一帧内连续弹出三个确认界面。

## 2. 遗物不只是一个弹窗

选择遗物后，代码会：

- 增加遗物堆叠；
    
- 写入遗物历史；
    
- 使构筑缩放缓存失效并重新计算；
    
- 增加对应神的掉落倾向；
    
- 清空普通掉落袋和 Bounty 奖励袋；
    
- 设置指定神池卡牌的掉落保底。
    

普通掉落系统随后会读取遗物提供的神池 affinity，并把它加入构筑型掉落评分；遗物保底也会强制后续掉落该神的卡。

所以如果只隐藏遗物界面，遗留的 affinity、pity 和奖励袋重建逻辑仍可能影响掉落。

## 3. 遗物直接参与技能数值计算

`buildModifierSystem.ts` 会遍历所有遗物和堆叠数，将它们聚合成：

- 技能伤害增幅；
    
- 数量增加；
    
- 控制强度；
    
- 领域面积；
    
- DOT伤害；
    
- 防御耐久；
    
- 掉率；
    
- 经验倍率等。
    

然后再把这些倍率应用到卡牌绑定、嵌套领域效果和卡牌消耗效果中。

这一模块不能整体删除，因为它同时还负责：

- 卡牌词条；
    
- 运行时临时属性修改；
    
- 装备提供的属性。
    

正确做法是只移除其中的“遗物聚合来源”，保留词条和运行时修饰器。

## 4. 当前还有独立的波末升级系统

除了经验遗物，当前每波结束还会：

1. 自动给予一组基础属性奖励；
    
2. 再弹出固定五项永久升级选择。
    

可选内容包括伤害、射速、生命上限、射程和经验获取比例。

波间流程会先处理神池选择，再处理这套波末属性选择。

如果保留它，玩家仍然会频繁遇到暂停和属性选择，不能真正实现你要求的“自动积蓄、自动抽取、只确认结果”。

因此我建议本次一并移除：

- `waveBaseReward` 五选一；
    
- 波末自动基础属性成长；
    
- `xpGainPct` 相关升级。
    

神池选择、卡牌进化选择和配方融合继续保留。

# 三、建议的新体验流程

推荐流程如下：

```text
击杀敌人
→ 获得奖励积分
→ 奖励条逐渐填充
→ 达到本轮阈值
→ 自动抽取一个奖励
→ 暂停战斗
→ 自动执行奖励
→ 显示“抽中了什么、产生了什么结果”
→ 玩家点击“确认”
→ 战斗继续
```

玩家在整个过程中不做奖励选择。

确认按钮不是“是否接受”，而是“我看到了，继续游戏”。

## 满条时的准确事务顺序

建议采用以下顺序，避免状态和表现混乱：

1. 奖励条达到阈值。
    
2. 将游戏置为 `rewardResolving` 状态并暂停时间推进。
    
3. 从奖励池自动抽取一个结果。
    
4. 立即执行奖励。
    
5. 记录本次实际结果，例如：
    
    - 造成多少伤害；
        
    - 消灭多少敌人；
        
    - 恢复多少生命；
        
    - 获得什么万能卡；
        
    - 获得哪一类临时强化。
        
6. 弹出单奖励结果卡。
    
7. 玩家点击“确认”。
    
8. 清除当前结果并恢复战斗。
    
9. 如果此前存在大量溢出积分，确认后再检查是否达到下一次阈值。
    

这样比“先确认，再释放技能”更符合你提出的自动化要求，也让确认界面能够显示实际结算结果。

# 四、奖励池应该如何设计

首版建议只有 **5种玩家能够记住的结果**。

不要把原有几十种遗物原样改造成几十种抽奖结果。那只会换一种形式恢复原来的认知负担。

## 推荐的五种奖励

|工作名|结果|主要体验|
|---|---|---|
|心防震爆|对全场敌人造成一次高额伤害|最直接的清屏爽感|
|绝对静止|全场冻结并短暂易伤|缓解压力、制造输出窗口|
|清醒回流|恢复生命并补充少量护盾|明确的生存正反馈|
|万能心意|直接获得万能卡|推进现有卡牌构筑|
|构筑共鸣|根据当前构筑自动给予短时强化|保留原遗物的构筑关联价值|

首轮占位数值可以从以下区间开始测试，不应直接视为最终定案：

- 心防震爆：普通敌人承受炮台基础总伤害的约6–10倍；Boss单独设置最大生命值伤害上限。
    
- 绝对静止：普通敌人冻结约2–3秒；Boss依据控制抗性缩短。
    
- 清醒回流：恢复最大生命的20%–30%，并提供1–2次突破吸收。
    
- 万能心意：获得1张当前阶段适用星级的万能卡。
    
- 构筑共鸣：持续10–15秒，对当前主构筑方向提供约20%–30%的强化。
    

这些数值必须通过实际每局触发次数和敌人密度再校准。

## “构筑共鸣”如何吸收旧遗物价值

原有遗物中已经有明确的方向，例如：

- 弹道伤害与弹道数量；
    
- 控制强度与受控增伤；
    
- 领域范围与持续伤害；
    
- 防御耐久与反击。
    

不要把它们分别做成十几个抽奖项。应该折叠成一个玩家可记忆的奖励：

> 抽中“构筑共鸣”后，系统自动识别当前构筑方向，再内部决定给予弹道、控制、领域、防御或功能性强化。

例如：

|当前主方向|自动强化|
|---|---|
|弹道|技能伤害提高，或临时增加投射数量|
|控制|控制持续时间提高，受控敌人承伤提高|
|领域|范围和DOT伤害提高|
|防御|护盾耐久、治疗或反击提高|
|功能|掉落效率提高，或额外给予万能卡|

玩家只需要记住“构筑共鸣会强化我当前的构筑”，不需要记住几十种遗物名和稀有度。

## 构筑方向如何判定

不建议继续使用 `relic godAffinity`，因为它本身就是本次要删除的遗物遗留机制。

建议新增一个纯函数 `calculateBuildProfile(state)`，根据实际持有内容计算：

```text
装备卡星级 × 较高权重
+ 手牌卡星级 × 较低权重
+ 本局对应卡牌合成次数 × 少量权重
```

再依据卡牌的 `synergyTags` 累积为：

```text
projectile / control / domain / defense / utility
```

得分最高的方向就是本次“构筑共鸣”的强化方向。

这样奖励判断来自玩家真正持有和投入的卡牌，而不是来自已经被删除的遗物历史。

# 五、奖励概率机制

首版应当保持简单，不要重新制造复杂的隐藏系统。

建议：

- 五种奖励都有固定基础权重；
    
- 同一奖励不能连续出现两次；
    
- 生命低于一定比例时，提高“清醒回流”的权重；
    
- “构筑共鸣”内部方向自动适配，不在外层拆成五个奖项；
    
- 首版不设置普通、稀有、史诗品质；
    
- 首版不设置叠层上限；
    
- 首版不设置永久遗物历史；
    
- 首版不通过奖励修改卡池掉落倾向。
    

这会比当前的“按第几件遗物决定品质权重、按神池安排选项、计算最大堆叠”简单得多。当前这些逻辑集中在 `progressionSystem.ts`。

## 2. 不要把奖励确认伪装成“决策”

当前 `decisionQueueSystem` 的职责是让玩家从合法候选中选择一个选项，而且入队会暂停游戏。

自动抽奖结果没有多个合法选项，它不是一个 `RunDecision`。

不建议增加：

```ts
{ kind: 'reward', options: [唯一结果] }
```

```ts

```

```ts
state.decisions.current !== null
|| state.rewardMeter.currentReceipt !== null
```

这样：

- 神池选择、进化分支仍走 `decisionQueueSystem`；
    
- 自动奖励确认走 `rewardMeterSystem`；
    
- 两种概念不会混在一起。

# 七、奖励执行不建议完全复用卡牌 EffectDef

当前项目已经有通用效果原子，包括：

- 全局或范围爆发；
    
- 冻结、眩晕、击退；
    
- 恢复；
    
- 临时属性增益；
    
- 额外掉落。
    

而且 `runEffects()` 已经能够顺序执行一组数据化效果。

但是我不建议让奖励系统直接完全等同于一张隐藏卡牌，原因有三点：

1. 全屏大招需要特殊的Boss伤害上限；
    
2. 奖励造成的击杀不能反过来无限为奖励条充能；
    
3. 奖励确认界面需要知道实际造成了多少伤害、击杀和治疗。
    

更稳妥的实现是：

> 奖励定义保持数据驱动，但执行器只包含5种明确的 `RewardAction`；每个动作调用现有战斗底层函数，而不是复制一套战斗代码。

例如：

```ts
export type RewardAction =
  | {
      kind: 'globalDamage';
      damageMul: number;
      bossHpRatioCap: number;
    }
  | {
      kind: 'globalControl';
      freezeSeconds: number;
      vulnerableRatio: number;
      vulnerableSeconds: number;
    }
  | {
      kind: 'restoreAndShield';
      healRatio: number;
      shieldHits: number;
    }
  | {
      kind: 'grantWildcards';
      count: number;
      starSchedule: number[];
    }
  | {
      kind: 'buildSurge';
      duration: number;
      value: number;
    };
```

执行器仍应复用：

- `dealDamage()`；
    
- 状态系统的冻结、易伤函数；
    
- `grantWildcards()`；
    
- 运行时属性修改器；
    
- `reconcileMaxHp()` 等既有基础能力。
    

# 八、必须防止奖励击杀无限充能

当前 `killEnemy()` 无论击杀来源是什么，都会计算并给予经验。

因此如果“心防震爆”清掉大量敌人，这些敌人又为奖励条提供积分，可能发生：

```text
奖励条满
→ 清屏
→ 清屏击杀再次充满
→ 再清屏
→ 再次充满
```

首版必须明确规定：

> 自动奖励造成的击杀不提供奖励积分。

建议给伤害/击杀结算增加一个独立参数，而不是依赖模糊的字符串判断：

```ts
export interface KillCredit {
  triggerSource?: string;
  grantsRewardPoints: boolean;
}
```

普通武器、卡牌、领域击杀：

```ts
grantsRewardPoints: true
```

自动奖励击杀：

```ts
grantsRewardPoints: false
```

由于首版奖励中的伤害效果是一次性同步结算，这个改动可以保持较小。后续如果增加“奖励召唤物”或持续DOT，再将来源信息挂到对应的攻击、区域或召唤实体上。

# 九、奖励条阈值怎么处理

当前累计阈值是：

```text
10, 22, 38, 62, 95, 140, 200, 280
```

目标是一局获得5–8件遗物。

为了在第一版尽量只验证“体验形式变化”，建议先保留原来的触发节奏，把累计阈值换算成每次重新蓄力所需积分：

```text
10, 12, 16, 24, 33, 45, 60, 80
```

也就是：

```text
第一次需要10
第二次再需要12
第三次再需要16
……
```

奖励条显示当前段进度：

```text
当前积分 / 当前阈值
```

满条后扣除阈值，保留溢出积分。

当前 HUD 直接显示累计的 `xp/xpNeed`，并用该比例决定条宽。 新系统必须改为分段进度，否则第一次满条后视觉上不会真正从零重新蓄力。

不建议立即调整触发频率。先保留原本约5–8次的目标密度，试玩后再决定：

- 是否需要更快出现第一次奖励；
    
- 后期阈值是否增长过快；
    
- 是否应该达到最后阈值后重复80点；
    
- 单局实际应该触发几次。
    

代码本身不足以得出准确的“第几秒触发”，还需要实际战斗遥测。

# 十三、Git分支迁移方案

“把当前版本转移到另一个分支”在Git中不需要复制或移动文件。

正确做法是让一个新的归档分支指向改动前的同一提交。

推荐命名：

```text
archive/pre-reward-meter-2026-07-30
```

实施分支：

```text
refactor/reward-meter
```

推荐操作：

```bash
git fetch origin

git switch main
git pull --ff-only origin main

BASE_COMMIT="$(git rev-parse origin/main)"

git branch archive/pre-reward-meter-2026-07-30 "$BASE_COMMIT"
git push origin archive/pre-reward-meter-2026-07-30

git switch -c refactor/reward-meter "$BASE_COMMIT"
git push -u origin refactor/reward-meter
```

随后所有删除和重构都在：

```text
refactor/reward-meter
```

上进行。

完成后通过PR合并到 `main`。不要直接在 `main` 上逐个删除文件。这样能够：

- 保证旧版本完整保留；
    
- 在PR中审查删除范围；
    
- 查看测试结果；
    
- 必要时随时比较旧系统；
    
- 避免误删卡牌进化或其他同名“升级”逻辑。
    

归档分支创建后不再向前移动，也不要在其上继续开发。

# 三、恢复群怪后会出现的三个隐藏问题

不能只把 `spawnLeft` 从 0 改成 200。这样会引入新的体验问题。

## 1. 后期默认敌人构成严重偏向坦克

当前普通出怪类型公式是：

```ts
roll < tankBase + wave * tankPerWave
```

配置为：

```json
"tankBase": 0.2,
"tankPerWave": 0.025,
"fastThreshold": 0.47
```

因此：

- 第 9 波坦克概率约为 42.5%；
    
- 第 10 波坦克概率约为 45%；
    
- 第 10 波高速怪只剩大约 2%。
    

直接恢复普通出怪，会得到大量高血量坦克，而不是割草敌潮。

这会把体验从：

> 大量敌人快速蒸发

变成：

> 大量肉盾缓慢挤向中心。

所以验证波必须有**独立敌人构成表**，不能继续使用全局 `typeRoll`。

## 2. 所有击杀仍然会提供经验

当前统一击杀管线无论敌人来源如何，最后都会执行：

```ts
addXp(...)
```

经验跨过阈值后会生成遗物选择，并进入决策队列。

一旦决策进入当前队列，游戏立即暂停；只要还有未解决决策，`updateGame()` 就不再推进。

因此，假如验证波增加两三百只怪，即使没有卡牌掉落，也可能出现：

> 杀群怪 → 升级 → 弹出遗物选择 → 暂停 → 选遗物 → 再杀几十只 → 再暂停。

这与“解放双手”直接冲突。

在当前经验系统仍存在的前提下，**验证波杂兵必须不提供经验**。精英和 Boss 是否提供经验也建议关闭，统一由少量显式验证奖励替代。

## 3. 当前验证奖励数量仍然偏多

当前配置会产生：

- 第 9 波：精英卡牌 + Boss 万能牌，共 2 个掉落；
    
- 第 10 波：两个精英卡牌 + Boss 万能牌，共 3 个掉落。
    

每波 2–3 个不算极多，但如果再增加敌潮、技能释放和 Boss 战，玩家仍可能需要频繁寻找散落在战场边缘的奖励。当前奖励位置是敌人的死亡位置，不是固定中心位置。

建议压缩到：

- 第 9 波：最多 1 个手动拾取奖励；
    
- 第 10 波：最多 1–2 个手动拾取奖励；
    
- 其他里程碑奖励自动发放或合并成一个奖励。

# 四、建议采用的验证波结构

## 验证波 1：构筑展示波

目的：让玩家第一次明显感受到自己的构筑已经成型。

建议结构：

1. 立即生成第一批普通敌潮；
    
2. 同屏敌人数稳定维持在 28–36；
    
3. 以普通怪和高速怪为主，少量坦克；
    
4. 敌潮进行到约 50% 时生成一个精英；
    
5. 杂兵全部清空后立即生成 Boss；
    
6. 整波只产生一个高价值手动拾取奖励。
    

建议初始参数：

```json
{
  "quota": 220,
  "targetOnScreen": 32,
  "checkInterval": 0.55,
  "batchMax": 12,
  "maxAlive": 52,
  "enemyStats": {
    "hpMul": 0.65,
    "damageMul": 0.7,
    "speedMul": 0.95
  },
  "composition": {
    "normalWeight": 0.65,
    "fastWeight": 0.25,
    "tankWeight": 0.10
  }
}
```

这里降低杂兵生命，而不是降低敌人数量。构筑失败的玩家仍可能因为清理速度不足而被高密度敌人突破；构筑成功的玩家则会持续割草。

## 验证波 2：终局狂欢波

目的：将屏幕密度、技能触发频率和击杀反馈进一步推高。

建议初始参数：

```json
{
  "quota": 300,
  "targetOnScreen": 44,
  "checkInterval": 0.45,
  "batchMax": 16,
  "maxAlive": 68,
  "enemyStats": {
    "hpMul": 0.75,
    "damageMul": 0.8,
    "speedMul": 1.0
  },
  "composition": {
    "normalWeight": 0.58,
    "fastWeight": 0.30,
    "tankWeight": 0.12
  }
}
```

在敌潮 65% 和 30% 进度附近分别加入一个精英，但两个精英不应各掉一个地面奖励。可以让第二个精英死亡后统一生成一个强奖励。

最终 Boss 出现时，可以附带一小批不掉奖励的护卫怪，使范围技能在 Boss 阶段仍然有作用。不过这一项建议放到第二轮实现，先完成纯敌潮版本。

删除验证阶段的：

改为：

- 不再开波时一次性生成所有精英；

计算：

`spawnEnemy()` 在验证阶段不能继续调用全局 `determineType()`。

应增加：


## 9. `src/core/systems/dropSystem.ts`

在 `rollDropOnKill()` 最前面加入明确门控：

```ts
if (enemy.spawnKind === 'validationMinion') return;
```

不能只依赖目前的阶段判断。因为当 `ordinaryDropRate.enabled === false` 时，旧概率掉落分支会在阶段检查之前运行，仍可能给验证杂兵掷普通掉落。

这也是为什么建议用独立 `validationMinion`，而不是简单标成 `regular`。

## 10. `src/core/systems/damageSystem.ts`

把经验结算从无条件执行：

```ts
addXp(...)
```

改成受敌人来源或当前波策略控制：

```ts
const grantsXp =
  enemy.spawnKind !== 'validationMinion'
  && validationPolicyAllowsXp(...);

if (grantsXp) {
  events.push(...addXp(...));
}
```

更理想的方式是增加一个统一的击杀收益策略：

```ts
interface KillRewardPolicy {
  grantsOrdinaryDrop: boolean;
  grantsXp: boolean;
  triggersOnKill: boolean;
}
```

其中 `onKill` 技能触发仍应保留。否则依赖击杀触发的构筑会在验证波突然失效。

因此验证杂兵应当：

- 普通掉落：否；
    
- 经验：否；
    
- `onKill` 技能：是；
    
- 击杀计数和结算分数：是。
    

## 11. 验证奖励生成位置

当前验证奖励生成在敌人死亡坐标。建议改为：

```ts
spawnValidationRewardAtTurretRing(...)
```

将奖励放在炮台附近固定半径，例如中心下方或攻击圈内缘。

这样玩家不需要在高密度战斗结束后搜索屏幕角落。

## 12. 波间时间

当前验证阶段波间自由时间是 17 秒。

建议改成 4–6 秒，或者：

- 拾取验证奖励后出现“继续”；
    
- 3 秒后自动进入下一波；
    
- 玩家也可立即点击准备。
    

否则第 9 波割草结束后等待 17 秒，会严重切断终局高潮。

# 四、问题 3：“强化炮台”的触发顺序

## 4.1 当前错误的实际原因

波次结束时，`beginIntermission()` 会立即：

- 把 `wavePhase` 设为 `between`；
    
- 激活 `intermission`；
    
- 把阶段设为 `settle`；
    
- 发出 `waveCleared`。
    

随后 `tickIntermission()` 的当前顺序是：

1. `settle`：发放自动保底奖励；
    
2. 进入 `decide`；
    
3. 先调用 `enqueueGodPoolDecisionForIntermission()`；
    
4. 等神池决策清空；
    
5. 再调用 `enqueueWaveBaseRewardDecision()`，也就是“强化炮台”；
    
6. 最后进入自由整备。
    

因此“强化炮台”出现在下一波神池选择之后，不是偶发现象，而是状态机明确规定的当前顺序。

同时，波末面板只要发现 `intermission.active` 且 `afterWave !== 0` 就会显示，并不关心强化选择是否已经完成。

所以仅仅把下面两项交换：

```ts
enqueueGodPoolDecisionForIntermission()
enqueueWaveBaseRewardDecision()
```

仍然不够。因为波末结算面板在进入 `settle` 时就已经显示了，强化选择依然不是“在结算面板显示之前”。

## 4.2 推荐的新波间状态机

把当前：

```ts
'settle' | 'decide' | 'free'
```

改成更明确的：

```ts
'rewardChoice' | 'settle' | 'godDecision' | 'free'
```

对应流程：

### `rewardChoice`

波次刚清空后立即进入。

行为：

- 隐藏波末结算面板；
    
- 立即生成 `waveBaseReward` 决策；
    
- 显示“强化炮台”；
    
- 当前决策未完成时不推进计时。
    

### `settle`

玩家完成“强化炮台”后进入。

行为：

- 发放每波自动保底奖励；
    
- 显示波末结算面板；
    
- 面板同时展示：
    
    - 自动奖励；
        
    - 玩家刚刚选择的强化；
        
- 运行结算展示计时。
    

### `godDecision`

结算展示完成后进入。

行为：

- 隐藏波末结算面板，避免两个弹窗叠加；
    
- 生成下一波的主神、副神或重点神选择；
    
- 玩家选择后继续。
    

### `free`

行为：

- 恢复波间整备面板；
    
- 玩家可以整理卡牌；
    
- 点击“准备完成”或倒计时结束后开下一波。
    

## 4.3 数据结构调整

建议给 `IntermissionState` 增加：

```ts
selectedReward: {
  id: string;
  stat: WaveChoiceStatKind;
  add: number;
} | null;
```

不要把它硬塞进现有 `rewardsGranted`，因为后者当前只表示自动保底奖励，而且其类型是 `RunBaseStatKind`。选择奖励还可能是 `xpGainPct`，语义不同。

在 `waveBaseRewardResolver` 完成选择时：

- 应用强化；
    
- 写入 `intermission.selectedReward`；
    
- 发出原有 `waveBaseRewardChosen` 事件；
    
- 下一帧切换到 `settle`。
    

## 4.4 特殊情况

开局 `afterWave === 0`

- 不显示强化炮台；
    
- 不显示波末结算；
    
- 直接进入初始主神选择。
    

最终波胜利

- 当前代码在最后一波直接执行 `endGame`，不进入波间阶段，这一点应保持不变。
    

范围已经达到上限

- 继续保留当前禁用选项机制；
    
- 只要仍有其他合法选项，就必须完成选择。
    

决策暂停

- 当前 `updateGame()` 在存在当前决策或待决队列时会直接停止推进，因此新顺序可以安全地等待玩家，不需要额外暂停系统。
