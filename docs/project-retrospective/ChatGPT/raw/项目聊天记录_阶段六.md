# ProjectVL：BOSS 移动与突破机制调查报告

## 一、结论

你的体感判断是准确的。

当前 BOSS 的行为不是偶发 BUG，而是代码明确规定的机制：

1. BOSS 以明显低于普通敌人的速度从屏幕边缘向炮台直线移动。
    
2. BOSS 进入突破距离后，立即结算一次伤害。
    
3. BOSS 不会死亡或消失，而是被随机传送回屏幕边缘。
    
4. BOSS 再次缓慢走向炮台，重复上述过程。
    

核心问题代码位于：

`src/core/systems/enemySystem.ts`

当前逻辑明确执行：

- 普通敌人突破后从敌人数组中移除。
    
- 波次 BOSS 突破后保留。
    
- 如果玩家没有死亡，则把 BOSS 坐标替换为新的随机边缘出生点。
    

也就是：

```ts
else if (
  e.spawnKind === 'waveBoss'
  && state.enemies.includes(e)
) {
  Object.assign(e, randomEdgeSpawnPosition(rng));
}
```

因此，“接触主角后瞬移到边缘”就是当前正式实现，不是渲染造成的错觉。

建议将 BOSS 重构为三个明确阶段：

> 直线接近 → 射程内曲线压迫 → 突破后贴身持续侵蚀

最重要的改动是：**删除 BOSS 突破后的边缘重置，让它停留在炮台附近，并持续造成伤害，直到 BOSS 或玩家一方死亡。**

## 二、当前实现调查

### 2.1 BOSS 的移动速度确实特别慢

当前敌人数值如下：

|敌人|基础速度|每波速度成长|
|---|--:|--:|
|普通敌人|24|+2|
|高速敌人|42|+3|
|重装敌人|15|+1.5|
|BOSS|18|0|

BOSS 不仅基础速度低，而且完全没有随波数成长。

当前 BOSS 从四个屏幕边缘随机出生，出生边距为 25 像素；炮台位于画面中央。

按照当前画布尺寸、出生位置和突破距离估算：

- BOSS 出生点到炮台的平均距离约为 380 像素。
    
- 突破距离为 48 像素。
    
- 实际需要移动约 332 像素。
    
- 以 18 像素/秒计算，平均需要约 **18.5 秒** 才能完成一次接近。
    

如果 BOSS 突破后又被送回边缘，就会重新产生接近 18 秒的无效等待。

这正是游戏进程被严重拖慢的主要原因。

### 2.2 BOSS 每一波都会出现

当前总波数为 8，`bossWaves` 配置为第 1—8 波，也就是每一波常规敌人清空后都会追加一个 BOSS。

因此，当前 BOSS 的拖延问题不是偶尔出现，而是每波都会发生。

在八波流程中，只要玩家不能在 BOSS 第一次接近时将其击杀，就可能额外增加十几秒甚至几十秒的空转时间。

### 2.3 BOSS 突破后的瞬移是专门写出的差异逻辑

当前突破结算流程是：

1. 检查反伤是否直接杀死敌人。
    
2. 结算护盾和突破减伤。
    
3. 普通敌人突破后被移除。
    
4. 扣除玩家生命值。
    
5. 触发 `breakthrough` 事件。
    
6. 触发装备的 `onBreach` 效果。
    
7. 玩家生命归零则失败。
    
8. 波次 BOSS 仍存活时，被随机送回边缘。
    

普通敌人与 BOSS 的核心区别就在这里：

```ts
if (e.spawnKind !== 'waveBoss') {
  state.enemies.splice(i, 1);
}
```

随后：

```ts
Object.assign(e, randomEdgeSpawnPosition(rng));
```

这个实现可能原本是为了避免 BOSS 停在中心、每帧重复扣血，但它实际上制造了更严重的问题：

- BOSS 战缺乏最终决战感。
    
- 玩家无法在突破后进行最后反杀。
    
- BOSS 重复跑图，形成大量无操作时间。
    
- BOSS 与普通敌人的差异只有血厚、移速慢、可以重复撞击。
    
- 防御、控制、持续伤害等构筑在最后阶段缺少有意义的表现。
    

### 2.4 当前测试把这种行为当作合法结果

现有测试验证了：

- BOSS 突破后仍留在 `state.enemies` 中。
    
- 游戏仍处于 Boss 阶段。
    
- `waveBossId` 仍然指向这只 BOSS。
    
- 玩家生命归零时仍能正常失败。
    

但测试没有验证 BOSS 突破后的实际位置，也没有验证后续伤害频率。

因此，即使 BOSS 被传送回屏幕边缘，测试仍然会通过。

这意味着修复时必须重写这一部分测试契约，而不能只改参数。

## 三、理想 BOSS 行为

推荐把波次 BOSS 设计为三个行为阶段。

### 阶段一：快速接近

BOSS 在玩家射程之外时，直接向炮台移动。

目标不是让这一阶段本身具有复杂玩法，而是尽快把 BOSS 送入玩家能够攻击的区域。

建议速度基线：

```json
{
  "speedBase": 28,
  "speedPerWave": 1.5
}
```

对应速度：

|波数|BOSS 速度|普通敌人速度|
|---|--:|--:|
|第1波|29.5|26|
|第4波|34|32|
|第8波|40|40|

这样 BOSS 不会像高速怪一样突然冲脸，但也不再是缓慢移动的靶子。

这组数值只是首轮验证基线，最终应根据实玩数据调整。

### 阶段二：射程内曲线逼近

当 BOSS 进入炮台射程后，不再完全直线接近，而是加入切向移动，形成绕着炮台逐渐收紧的螺旋路线。

不建议实现复杂寻路、样条曲线或预制轨道。当前游戏没有障碍物，简单的向量混合已经足够。

移动方向可由两个向量组成：

- `radial`：指向炮台的径向向量。
    
- `tangent`：垂直于径向的切向向量。
    

伪代码如下：

```ts
const radial = normalize(turretPosition - bossPosition);
const tangent = perpendicular(radial) * boss.orbitDirection;

const progress = clamp(
  (distance - contactDistance)
    / (orbitStartDistance - contactDistance),
  0,
  1,
);

const curveWeight =
  Math.sin(Math.PI * progress)
  * bossBehavior.curveStrength;

const movementDirection = normalize(
  radial + tangent * curveWeight,
);
```

采用 `sin(π × progress)` 的原因是：

- 刚进入曲线区域时，切向权重为 0，不会突然转弯。
    
- 路线中段弯曲最明显。
    
- 接近炮台时，切向权重重新降低，BOSS 能稳定进入接触点。
    
- BOSS 到炮台的距离始终总体下降，不会无限绕圈。
    

建议初始参数：

```json
{
  "orbitStartRangeRatio": 1.0,
  "orbitStartMaxDistance": 180,
  "curveStrength": 0.65
}
```

实际曲线起点可以取：

```ts
Math.min(
  totalRange(state, config),
  bossBehavior.orbitStartMaxDistance,
);
```

这会让射程成长对 BOSS 战产生自然收益：玩家射程越远，越早获得攻击窗口。

### 阶段三：贴身持续侵蚀

当 BOSS 到达突破距离时：

1. BOSS 进入 `contact` 状态。
    
2. 不再传送。
    
3. 停留在炮台附近。
    
4. 每隔固定时间造成一次小额伤害。
    
5. 炮台仍然能够攻击 BOSS。
    
6. 玩家需要在生命耗尽前击杀 BOSS。
    
7. 击退可以把 BOSS 从接触状态中暂时推开。
    
8. 冻结和眩晕可以暂停侵蚀伤害。
    

这才会形成用户预期的“最终对射阶段”。

## 四、推荐的运行时状态

当前 `Enemy` 没有 BOSS 行为状态，只有位置、速度、生命和状态效果等通用字段。

建议为波次 BOSS增加一个可选运行时字段：

```ts
export interface BossRuntimeState {
  phase: 'approach' | 'contact';

  /** 顺时针或逆时针，避免曲线方向每帧变化。 */
  orbitDirection: -1 | 1;

  /** 当前距离下一次接触伤害的剩余时间。 */
  contactTickRemaining: number;

  /** 进入接触时相对炮台的角度。 */
  contactAngle: number;
}

export interface Enemy {
  // 现有字段……

  bossRuntime?: BossRuntimeState;
}
```

只给 `spawnKind === 'waveBoss'` 的敌人初始化该字段。

`orbitDirection` 不建议额外消耗 RNG，可以根据敌人 ID 决定：

```ts
orbitDirection: enemy.id % 2 === 0 ? 1 : -1
```

这样不会改变现有随机种子下的掉落、敌人类型和出生位置序列。

## 五、持续伤害的具体结算方式

### 5.1 不要每帧直接调用现有突破逻辑

如果 BOSS 每帧都调用一次当前的 `absorbBreach` 和 `onBreach`：

- 护盾会在极短时间内消耗殆尽。
    
- `breakthrough` Toast 会每帧刷屏。
    
- `onBreach` 装备会反复触发。
    
- 遥测会记录大量突破事件。
    
- 不同帧率可能产生不同结果。
    

当前 `breakthrough` 事件会直接生成“受到 X 点伤害”的 Toast，因此持续伤害不能继续每帧复用该事件。

### 5.2 使用固定伤害脉冲

推荐：

```json
{
  "contactWarmup": 0.4,
  "contactTickInterval": 0.5,
  "contactDps": 14
}
```

每个脉冲的基础伤害：

```ts
pulseDamage =
  contactDps
  * contactTickInterval
  * difficultyDamageMultiplier;
```

基础为 14 DPS、每 0.5 秒一次时，每次基础伤害为 7。

当前难度配置中，标准难度 BOSS 伤害倍率从约 0.65 成长至 0.95；地狱难度为 1。

因此满血玩家的理论生存时间约为：

|情况|实际 DPS|满血生存时间|
|---|--:|--:|
|标准难度前期|9.1|约11秒|
|标准难度后期|13.3|约7.5秒|
|地狱难度|14|约7.1秒|

这个时间窗口足够形成“最后反杀”，同时不会让玩家可以无限拖延。

当前 BOSS 的 `damage` 是 28。如果直接把 28 当成持续 DPS，地狱难度满血只能存活约 3.6 秒，初版很可能过于严苛。

因此建议：

- 普通敌人继续使用 `damage` 表示一次突破伤害。
    
- BOSS 新增独立的 `contactDps`。
    
- 不要直接把当前的 28 解释为 DPS。
    

### 5.3 `onBreach` 只在进入接触状态时触发一次

现有卡牌中，冲击卡的 5★装备被动会在 `onBreach` 时释放击退和眩晕区域，并有 6 秒冷却。

正确语义应当是：

- BOSS 第一次贴近炮台：触发一次 `onBreach`。
    
- BOSS 持续贴身：不重复触发。
    
- BOSS 被击退后重新接近：可以再次触发。
    
- 装备自身的 6 秒冷却继续生效。
    

因此需要区分：

- “开始接触”
    
- “接触伤害脉冲”
    

不能把每一个伤害脉冲都视为新的突破。

### 5.4 建议增加三个语义事件

```ts
| {
    type: 'bossContactStarted';
    enemyId: number;
  }
| {
    type: 'bossContactDamage';
    enemyId: number;
    damage: number;
  }
| {
    type: 'bossContactEnded';
    enemyId: number;
  }
```

表现层规则：

- `bossContactStarted`：显示一次警告，例如“BOSS 已突破防线，正在持续侵蚀”。
    
- `bossContactDamage`：不显示 Toast，只驱动炮台受击闪烁、生命条脉冲或伤害数字。
    
- `bossContactEnded`：用于击退成功的表现反馈。
    

普通敌人的 `breakthrough` 事件保持不变。

## 六、护盾、控制和击退如何共存

### 6.1 护盾按伤害脉冲吸收

现有圣盾装备提供：

- 3★：2 次吸收，10 秒再生。
    
- 5★：2 次吸收，破盾时产生新星。
    
- 6★：3 次吸收，6 秒再生。
    

建议每个 0.5 秒伤害脉冲视为一次可吸收攻击。

这样：

- 2 层护盾约提供 1 秒无伤窗口。
    
- 护盾破裂的新星可以击退 BOSS。
    
- 如果 BOSS 被击退脱离接触距离，持续伤害停止。
    
- 防御构筑在 BOSS 最终阶段具有清晰价值。
    

### 6.2 击退可以解除贴身状态

当前 BOSS 的击退抗性为 0.85，即只承受 15% 的原始击退距离。

建议参数：

```json
{
  "contactDistance": 48,
  "contactExitDistance": 60
}
```

BOSS 需要被推出至少约 12 像素才能解除接触。

这正好能与现有技能形成合理关系：

- 80 像素原始击退 × 15% = 12 像素。
    
- 100 像素原始击退 × 15% = 15 像素。
    
- 130 像素原始击退 × 15% = 19.5 像素。
    

也就是说：

- 较强的突破反制可以勉强把 BOSS 推开。
    
- 破盾新星可以稳定争取一小段时间。
    
- 普通低强度击退无法轻易无限控制 BOSS。
    

### 6.3 硬控制应暂停持续伤害

推荐规则：

- 冻结：暂停移动，也暂停接触伤害计时。
    
- 眩晕：暂停移动，也暂停接触伤害计时。
    
- 减速：影响接近阶段速度，但不降低已经贴身后的 DPS。
    
- 击退：可能解除接触状态。
    
- 嘲讽：只在 BOSS 尚未进入贴身状态时有效。
    

理由是：如果 BOSS 已被冻结，却仍然持续攻击玩家，控制构筑会显得失效。

BOSS 本身已经拥有 0.5 的控制抗性，控制并不会过强。

### 步骤三：拆分移动逻辑

moveRegularEnemy(...)

```ts

```

### 步骤四：删除边缘瞬移

删除：

```ts
Object.assign(e, randomEdgeSpawnPosition(rng));
```

BOSS 进入接触状态后，把位置固定在当前接触方向：

```ts
boss.x =
  turret.x
  + Math.cos(contactAngle)
  * contactDistance;

boss.y =
  turret.y
  + Math.sin(contactAngle)
  * contactDistance;
```

但不能每帧无条件强制固定。

如果击退把 BOSS 推到 `contactExitDistance` 之外，应退出接触状态并恢复移动。

### 步骤五：增加持续伤害结算

建议写成独立函数：

```ts
function resolveBossContactPulse(
  state: GameState,
  config: Config,
  rng: Rng,
  boss: Enemy,
  events: GameEvent[],
): void
```

结算顺序：

1. 计算本次脉冲伤害。
    
2. 计算反伤。
    
3. 如果反伤杀死 BOSS，正常走击杀与奖励结算。
    
4. 调用现有护盾与突破减伤逻辑。
    
5. 扣除玩家生命。
    
6. 更新 `lastHpLossAt`。
    
7. 发出 `bossContactDamage`。
    
8. 玩家生命归零时结束游戏。
    

注意：当前反伤逻辑使用完整的 `e.damage`。改为持续伤害后，必须改成基于单次脉冲伤害计算，否则反伤会按完整 DPS 或旧的 28 点伤害重复结算。

建议表现：

## 调查结论

根据项目文件说明，本次分析对象是 GitHub 中的 `ProjectVL` 仓库。

**这个问题是真实存在的，而且不是激光特效导致的错觉。当前 6 星“直球拒绝”会显著降低主角的实际输出。**

在默认数值下，单目标理论 DPS 大致如下：

|状态|理论单目标 DPS|
|---|--:|
|未装备“直球拒绝”|`18 × 5 = 90`|
|装备 6 星“直球拒绝”|`18 × 1.3 ÷ 0.9 = 26`|
|相对变化|**降低约 71.1%**|

也就是说，在只攻击一个 Boss 时，装备这张 6 星卡后，主炮只剩下原本约 **28.9%** 的直接输出。

这不是普通的数值偏低，而是**攻击形态换算公式错误**。

## 一、当前代码实际上做了什么

“直球拒绝”对应内部卡牌 ID `pierce`。文案明确写着，6 星装备效果是“主炮化为持续光束”。

它的 6 星配置是：

```json
{
  "atom": "beamMorph",
  "params": {
    "interval": 0.9,
    "width": 32,
    "damageRatio": 1.3
  }
}
```

也就是每隔 0.9 秒生成一道光束，基础伤害倍率为 1.3。

由于没有单独配置持续时间和伤害间隔，代码使用默认值：

- 光束持续时间：0.6 秒
    
- 伤害 Tick 间隔：0.1 秒
    
- 每道光束共约 6 次 Tick
    

这些默认值定义在武器形态合成逻辑中。

问题出现在伤害计算：

```ts
const tickCount = Math.max(
  1,
  Math.round(duration / form.tickInterval),
);

const damagePerTick =
  totalDamage(state, config)
  * form.deliveryDamageRatio
  / tickCount;
```

这意味着，一整道持续 0.6 秒的光束，所有 Tick 加起来只造成：

```text
基础单发伤害 × 1.3
```

然后还要等到第 0.9 秒才能创建下一道光束。

---

## 二、为什么卸下装备后反而强很多

未装备激光时，普通主炮使用的是另一套计算：

```text
每发伤害 × 射速 × 弹丸数量
```

当前默认配置是：

- 单发伤害：18
    
- 射速：每秒 5 发
    
- 初始弹丸数量：1
    

因此普通主炮理论单目标 DPS 是：

```text
18 × 5 × 1 = 90
```

默认战斗配置中的确是 `damage = 18`、`fireRate = 5`。

普通射击还会根据 `totalMulti` 生成多枚子弹，并使用 `totalFireRate` 控制开火冷却。

但切换为光束以后：

- 不再使用 `totalFireRate`
    
- 不再使用 `totalMulti`
    
- 只使用 `totalDamage`
    
- 按固定的 0.9 秒间隔生成光束
    

所以当前激光理论 DPS 是：

```text
18 × 1.3 ÷ 0.9 = 26
```

相对于普通主炮：

```text
26 ÷ 90 ≈ 28.9%
```

因此测试中观察到的“远远不如卸下装备后的伤害”，与当前代码完全一致。

---

## 三、升级和构筑会进一步放大问题

当前升级系统存在“射速 +12%”选项。

普通攻击会正常获得射速成长：

```ts
return (config.fireRate + state.fireRateBonus)
  * buffMul(state, 'fireRateMul');
```

但光束攻击的 0.9 秒周期不会随射速变化。

于是玩家每拿一次射速强化：

- 卸下激光时，普通攻击继续变强
    
- 装备激光时，直接伤害基本不变
    

例如第一次射速强化后：

```text
普通主炮：
18 × 5.6 = 100.8 DPS

激光：
仍约 26 DPS
```

差距从 71% 进一步扩大到约 74%。

虽然当前初始弹丸数量为 1，代码仍明确支持 `multi`。一旦其他能力或后续版本提高弹丸数量，普通攻击会成倍增加输出，而光束仍然不会继承。初始状态中的 `multi` 为 1。

---

## 四、6 星还会彻底替换原来的贯穿与折返效果

“直球拒绝”并不是在 5 星效果上增加激光。

装备效果解析逻辑是：

- 3 星使用 3 星配置
    
- 4 星放大 3 星配置
    
- 5 星使用 5 星配置
    
- 6 星只使用 6 星配置
    

```ts
return clone(
  def.stars[
    star >= 6 ? '6'
    : star >= 5 ? '5'
    : '3'
  ].equip
);
```

因此升到 6 星后会失去：

- 3 星的贯穿
    
- 5 星的折返
    
- 普通子弹的射速收益
    
- 多弹丸收益
    

然后替换成当前伤害严重不足的光束。

“变形后放弃旧弹道”本身可以是合理设计，但前提是新形态必须正确继承主炮的整体输出预算。

## 五、其他装备的触发效率也会下降

这里还有一个次级问题。

普通主炮每发子弹都是一次新的 `AttackInstance`，每次射击都可以触发：

- `onFire`
    
- `onHit`
    
- 附加状态
    
- 连锁
    
- 灼烧区域
    
- 其他装备被动
    

光束则是每 0.9 秒只创建一次 `AttackInstance`。

光束第一次命中某个敌人时，会触发 `onHit`；之后同一道光束的其余 Tick 只造成直接伤害，不会再次运行 `onHit` 和附加效果。相关代码在检测到敌人已经存在于 `attack.hitIds` 后会直接扣血并返回。

现有测试甚至明确固化了这一行为：

- 连锁闪电每道光束只触发一次
    
- 灼烧区域每个敌人每道光束只生成一次
    
- 冻结层数每道光束只增加一次
    

因此，默认情况下：

```text
普通攻击 onFire 频率：约 5 次/秒
光束 onFire 频率：约 1.11 次/秒
```

其他装备技能的触发效率也可能下降约 78%。

这意味着即使单纯把激光的直接伤害调高，某些组合构筑仍可能因为触发频率下降而变弱。

# 推荐修复方案

不建议只把 `damageRatio` 从 1.3 粗暴提高到 4.5。

`4.5` 只能在默认射速 5、弹丸数量 1 时勉强对齐；玩家拿到射速强化后，问题会再次出现。

正确方案是让光束继承普通主炮的**每秒输出预算**。

## 第一阶段：修复光束直接伤害

修改：

```text
src/core/systems/combatSystem.ts
```

把当前的光束伤害计算：

```ts
const damagePerTick =
  totalDamage(state, config)
  * form.deliveryDamageRatio
  / tickCount;
```

改为：

```ts
const baselineDps =
  totalDamage(state, config)
  * totalFireRate(state, config)
  * totalMulti(state);

const cycleDamage =
  baselineDps
  * form.interval
  * form.deliveryDamageRatio;

const damagePerTick =
  cycleDamage / tickCount;
```

换算关系变为：

```text
光束每周期总伤害
= 普通主炮每秒伤害
× 光束周期
× 光束形态倍率
```

这样无论玩家获得多少：

- 基础伤害
    
- 射速
    
- 多弹丸
    

激光都会继承相同的成长。

---

## 第二阶段：重新定义 `damageRatio`

采用上述新公式后，不能继续无脑保留当前的 `damageRatio = 1.3`。

因为新公式下：

```text
damageRatio = 1.3
```

意味着激光在单体 Boss 上就已经是普通主炮的 130% DPS，同时还可以贯穿一条直线上的多个敌人，可能过强。

建议初始改为：

```json
"damageRatio": 1.0
```

设计含义是：

- 单目标 Boss：与普通主炮理论 DPS 持平
    
- 多目标直线：通过贯穿获得额外收益
    
- 6 星价值来自稳定命中、贯穿、持续扫射和构筑形态变化
    
- 不会出现“升到 6 星反而打不动 Boss”
    

建议后续调参范围：

```text
0.95～1.10
```

我倾向先使用 **1.0**。

6 星技能不应在单目标场景下明显降级，但考虑到光束天然拥有多目标能力，也没有必要立即给予 30% 单体增伤。

---

## 第三阶段：明确其他装备的触发规则

直接伤害修好后，还必须决定一条设计规则：

> 光束是否应继承普通射速对应的技能触发次数？

有两个可行方向。

### 方向 A：保持每道光束只触发一次

这是改动最小的方案：

- `onFire` 每次创建光束触发一次
    
- `onHit` 每个敌人每道光束触发一次
    
- 射速和多弹丸只折算进直接伤害
    
- 不额外增加连锁、冻结、灼烧等触发次数
    

优点是不会产生大量连锁、区域和状态效果，性能和数值更可控。

缺点是“直球拒绝 + 其他攻击附加卡”的联动会明显改变。直接伤害虽然不降，但某些依赖高频触发的构筑仍会变弱。

作为当前验证期修复，我建议先采用这个方案，但必须写进形态融合契约。

### 方向 B：加入“虚拟射击触发预算”

更完整的方案是为光束维护：

```text
virtualShotBudget
```

根据：

```text
totalFireRate × totalMulti × dt
```

累积虚拟射击次数。达到一次时，允许光束执行一次附加效果触发。

但必须同时加入 `procCoefficient`，否则持续光束配合连锁、爆炸或灼烧会产生过量触发。

例如：

```text
光束直接伤害继承 100% 普通 DPS
光束附加效果触发系数为 40%～60%
```

这个方案更系统，但实现、测试和数值风险都更高，不适合作为第一步紧急修复。

# 三、对《神池系统 v1》的两项必要修正

整体的“一主神、二副神、本局 11 张、本波 5–7 张”结构是合理的，应该作为实现基线。

但结合实际代码后，需要修正两个技术判断。

## 修正一：神身份必须与 `synergyTags` 分离

现有 `BuildTag` 是：

```ts
projectile | control | domain | defense | utility
```

它们表达的是效果机制，不是流派人格。

一个正式的神卡池需要同时拥有伤害、控制、防御、经济等多类卡。因此不能让：

```text
弹道神 = projectile
控制神 = control
防御神 = defense
```

否则仍然是在把功能类别当作流派，违背本次设计原则。

正确结构应当是：

```ts
type GodId = string;

interface CardDef {
  id: string;
  godId: GodId;
  category: Category;
  synergyTags: BuildTag[];
}
```

其中：

- `godId`：决定卡池归属、选神、遗物池和美术包装；
    
- `category`：决定卡的主要功能与视觉分类；
    
- `synergyTags`：决定哪些广域遗物可以作用于这张卡。
    

可以复用现有 affinity、pity 和掉落加权算法，但不能复用 `BuildTag` 的枚举值来代表神。

---

## 修正二：普通掉落使用本波池，其他奖励至少使用本局池

建议明确三级合法范围：

```text
全局卡库 Global Library
        ↓
本局卡组 Run Roster：主5 + 副3 + 副3
        ↓
本波活跃池 Active Pool：5–7张
```

使用规则：

|奖励来源|合法范围|
|---|---|
|普通敌人掉落|本波活跃池|
|Bounty 奖励|本局卡组，偏向本波重点神和已投入卡|
|波末 Boss 万能卡|不需要卡型|
|validation 高星卡|本局卡组中属于当前重点神的卡|

# 五、统一的构筑决策队列

不建议继续增加：

```ts
pendingGodChoice
pendingEvolutionChoice
pendingWaveReward
pendingRecipe
```

等大量互相冲突的布尔值。

应新增统一状态：

```ts
type RunDecision =
  | GodDraftDecision
  | GodFocusDecision
  | EvolutionBranchDecision
  | RecipeEvolutionDecision
  | RelicDecision;

interface DecisionQueueState {
  current: RunDecision | null;
  pending: RunDecision[];
}
```

处理原则：

1. 规则系统将决策加入队列。
    
2. 只要存在决策，游戏暂停。
    
3. UI 根据 `decision.kind` 显示对应界面。
    
4. 玩家完成选择后，规则层应用结果。
    
5. 自动打开下一项决策。
    
6. 队列清空后才允许继续战斗。
    

这可以取代当前升级系统中特殊化的 `pendingLevelUps + offeredPerks` 逻辑，或者先将其包裹兼容，再逐步迁移。

totalDamage = config.damage + runBaseStats.damageAdd + equipmentAdd;

## 模块 G：单卡进化树

这是当前改造量最大的模块。

### 推荐的首版树形结构

在 6 星上限下，采用：

```text
1★ 基础
 ↓
2★ 数值成长
 ↓
3★ 第一次分叉：3选1
 ↓
4★ 共同强化节点
 ↓
5★ 第二次分叉：3选1
 ↓
6★ 共同终态节点
```

这符合“分叉—合并—分叉—合并”，但这里的“合并”不是清除之前的分支，而是：

> 不同路径都获得同一个公共成长节点，同时保留已经选择的路径效果。

例如：

```text
3★：
A 穿透扩张
B 单体强化
C 命中易伤

4★：
所有路线共同获得伤害保留增强

5★：
A1 击杀扩散
A2 连续命中增伤
A3 穿透后分裂

6★：
所有路线共同变为终极光束形态
```

### 卡牌实例扩展

```ts
interface Card {
  id: number;
  type: CardType;
  star: number;
  evolutionPath: string[];
  affixes: CardAffixRoll[];
}
```

### 进化选择按“本局该卡族”锁定

不建议让同一局内的两张同名 3★卡选择不同分支。否则会造成：

- 合成链碎片化；
    
- 需要分别养两条同名链；
    
- 玩家难以判断哪些卡能够继续合成；
    
- 七手牌槽压力失控。
    

首版采用：

```ts
state.runBuild.evolutionChoices[cardType][checkpointId] = optionId;
```

玩家第一次把该卡升到关键星级时选择一次；之后本局内所有同类卡自动继承相同路线。

这样仍然有每局构筑差异，但不会制造同卡异路径的合成兼容问题。

### 自动合成改造

`autoMergeCards()` 不再直接完成所有星级。

改为：

```text
检测可合成
  → 普通星级：立即合成
  → 关键星级且未选路线：
       创建 provisional result
       移除材料
       加入 EvolutionBranchDecision
       暂停继续连锁合成
  → 玩家选择后：
       完成卡牌
       再次尝试自动连锁合成
```

必须防止一次拾取连续触发两个未处理的分支选择。

## 模块 I：技能效果槽与随机数值槽

### 数据模型

```ts
interface CardAffixPoolDef {
  count: number;
  candidates: Array<{
    stat: CardStatKind;
    weight: number;
    min: number;
    max: number;
    step: number;
    consumableDuration: number;
  }>;
}

interface CardAffixRoll {
  stat: CardStatKind;
  value: number;
  consumableDuration: number;
}
```

### 一个必须提前解决的冲突

当前同名卡会自动合成。如果每一张物理卡都随机出不同词条，那么自动合成可能在玩家无法控制的情况下吞掉一个优质词条。

因此首版建议：

> 同一卡型在一局中第一次出现时随机一次“本局词条模板”，本局后续所有同类卡共享该模板。

即：

```ts
state.runBuild.cardAffixRolls[cardType] = rolledAffixes;
```

物理卡仍保存一份副本用于显示和后续扩展。

这样：

- 不会因为自动合成随机损失词条；
    
- 不需要现在实现词条继承与比较；
    
- 不提前侵入延后的镶嵌系统；
    
- 每局同一卡仍可能形成不同数值方向。
    

### 装备与消耗的不同作用

装备时：

```text
数值词条持续生效
```

消耗释放时：

```text
同一词条转化为限时 Buff
```

例如：

```text
装备：基础射速 +0.25，持续生效
消耗：射速 +0.25，持续 5 秒
```

需要将当前仅支持 `damageMul/fireRateMul` 的 `Buff` 扩展为通用限时修饰器。当前 Buff 类型过窄。

建议统一为：

```ts
interface RuntimeStatModifier {
  sourceId: string;
  stat: CardStatKind;
  operation: 'add' | 'mul';
  value: number;
  remaining?: number; // undefined 表示持续
}
```

装备词条不必写入状态数组，可以由装备聚合器实时读取；消耗词条写入限时数组。

- 修改 `cardSystem.ts`；
    
- 修改效果解释器的装备态解析；
    
- 修改卡面、描述、合成提示；
    
- 新增进化选择弹窗。
    

当前 `resolveEquipBindings()` 固定以 3★、5★、6★锚点解析，4★只对 3★进行数值放大。  
这部分应改为：

```ts
resolveCardBindings(def, card.evolutionPath, card.star)
```

而不是只传 `type + star`。

验收：

- 关键星级出现三个分支；
    
- 同卡本局只需选择一次；
    
- 后续同卡自动继承；
    
- 4★与6★公共节点正确叠加；
    
- 进化选择不会复制或丢失卡牌；
    
- 选择后可继续自动连锁合成。

## 阶段 8：正式五神与约 35 张卡

系统开发时可以先用测试卡验证，但正式验收必须达到至少五神。

原因是只有三神时：

- 第一波虽然是三选一；
    
- 选完主神后，剩余两个神会必然成为两名副神；
    
- 第二、三波实际上不存在阵容选择。
    

因此完整构筑广度至少需要：

```text
5 神 × 每神 7 张 = 35 张
```

每个神的卡池应覆盖：

- 直接伤害；
    
- 范围或弹道；
    
- 控制；
    
- 防御或容错；
    
- 资源或成长；
    
- 一至两个身份锚点；
    
- 至少一个对其他神开放的乘法接口。
    

不能出现“这个神只有控制卡”“那个神只有防御卡”的设计。

每设计一张卡时，应同时填写：

1. 基础技能；
    
2. 装备态；
    
3. 消耗态；
    
4. 3★三个分支；
    
5. 5★三个分支；
    
6. 6★终态；
    
7. 合法随机数值词条；
    
8. 与同神其他卡的乘法协同；
    
9. 与其他神的开放协同；
    
10. 是否需要新增通用效果原子。
    

只有无法用现有原子表达、且能服务多张卡的效果，才允许增加新原子。

# 八、测试与遥测要求

## 必须新增的规则测试

至少覆盖：

1. 未选神卡不会从任何入口掉落。
    
2. 主神固定 5 张、副神固定 3 张。
    
3. 神池第 3 波锁定。
    
4. 活跃池始终去重且不超过 7 张。
    
5. 保护链最多休眠一波。
    
6. 神候选连续两波未出现时触发保底。
    
7. 新神三张卡展示保底。
    
8. 第 8 波后不首次引入基础新卡。
    
9. validation 奖励服从重点神。
    
10. 波末多个基础奖励可同时结算。
    
11. 基础奖励不会重复领取。
    
12. 关键星合成会进入待决状态。
    
13. 分支选择后材料和结果数量正确。
    
14. 同卡后续副本自动继承分支。
    
15. 配方进化精确消耗材料。
    
16. 装备词条持续生效。
    
17. 消耗词条到期失效。
    
18. 遗物候选只来自已选神。
    
19. 多次升级队列不会覆盖选项。
    
20. 固定 RNG 下整局结果可重现。
    

项目当前已经把系统规则测试作为架构契约，新增规则也应遵循“改规则必须补测试”。

# 十、最终建议的实施主线

最合理的开发主线是：

```text
决策队列和波间阶段
→ 波末基础奖励
→ 神池与活跃池
→ 遗物升级
→ 单卡进化树
→ 卡间进化
→ 随机数值槽
→ 五神35张正式内容
→ 整局仿真与平衡
```

其中真正的架构分水岭是前三项：

> 在“波间决策框架、本局卡组、本波活跃池”完成以前，不应开始批量制作 35 张正式卡。

否则新卡仍会进入全局随机池，后续还需要重新修改所有卡牌、奖励和掉落配置。
