## 0. 根因与结论

Codex 报告「规格 §1.0 复用能力清单不完整」，核实**完全正确**，且缺口比报告更大。

### 0.1 引擎真实状况（已核实）

| 事实 | 位置 |
|---|---|
| `interval` 绑定的 ctx.origin 恒为炮台坐标（无 payload.point） | `interpreter.ts:306` baseCtx / `:375` tickIntervalBindings |
| `aura` 只以炮台为心、半径静态（支持 circle/ring，但无位移、无随时间变化） | `runtime.ts:66` tickAuras / `defs.ts` aura 契约 |
| 无「对场上全部带状态 X 的目标各自位置执行效果」通道 | 全仓无实现 |
| 无「按运行时动态量缩放效果参数」通道（`statBuff.maxStacks` 只是自身叠层，不是按外部计数缩放） | 全仓无实现 |

**因此以下六类设计语义在引擎中不存在**：非炮台原点投放（最密处/最近 N）、多目标扇出、跟随位移、半径随时间扩张、按动态量缩放、区域集合迭代。

### 0.2 后果：上一轮 35 卡实装被静默摊平

缺原语时，实装把这些语义压成了炮台中心的静态效果，造成三类缺陷：

| 类 | 缺陷 | 规模 |
|---|---|---|
| **D1** | 设计语义因缺原语被摊平（"最密处"→炮台、"对场上全部 X"→单点一次、"扩张环"→静态圈、"越多越强"→固定 statBuff） | 涉及 **20/35** 张基础卡 |
| **D2** | 触发器被替换，破坏身份契约（设计 `onBreach` 24 处 → 实装 12 处；`retribution` 设计 7 处 → 实装 2 处、3★ 三支全部变成 `onHit`；`sanctum` 5★1 设计 onBreach → 实装 0） | ≥9 处绑定 |
| **D3** | v4 设计稿**自身**存在跨卡重复（我在写 v4 时把若干"传播/转化"分支写成同一句），实装照抄即撞车 | 见 §3 分类为 D3 的组 |

综合结果：**210 支基础卡分支中有 64 支（30%）在不同卡之间字节级完全相同**，27 组。这正是本轮重构要消灭的同质化。V1（卡内两两）、V7（卡内九宫格）、V13（3★ 同 category 跨神、警告级）都拦不住跨卡 5★ 指纹重复。

### 0.3 durable fix：把设计表编译成机器可读期望

根因不是"忘了写某个函数"，而是**设计表是散文、校验器没有设计期望的机器表示**，所以任何实装偏离都无人拦截。修复的核心是 §2 的设计指纹夹具 + V15/V16，此后"实装偷工"会直接红灯。

## 1. 缺失原语契约（T1–T6）

全部属于「服务 ≥2 张卡」的通用能力（每条列服务方数量），实现在效果层通用通道，**禁止按卡内联 if**。

### T1 投放原点选择器 `at`

绑定级/效果级参数，决定 ctx.origin：

```ts
at?: 'turret'            // 默认，兼容现状
   | 'point'             // 事件坐标（onKill/onBreach/onPickup 已有 payload.point）
   | 'densestCluster'     // 场上敌人密度最高处（网格聚类，见下）
   | 'nearestEnemy'       // 最近敌人当前位置
   | 'nearestToBreachLine' // 最接近突破线的敌人（防御类用）
```

密度聚类实现约定：以 `combat.canvas` 划分固定网格（建议 8×6），取敌人计数最高格的质心；平局取距炮台更近者（保证固定 seed 可重现）。每帧最多计算一次并缓存（多绑定共用）。

**服务**：chainLightning 3★C、staticSurge 3★C、stormcall 3★C、frost 3★C、permafrost 3★C、iceTomb 3★C、magmaPool 3★B、ashHarvest 3★B、flashfire 3★C、luckyStar 3★B、hoarfrostTithe 3★C 等 **≥10 张基础卡** + 产物 volcanoCore / thunderRime / rootLoom。

### T2 多目标扇出 `forEach`

效果级包装器：对匹配集合中的每个成员，以其坐标为 origin 执行内嵌效果表。

```ts
forEach: {
  set: { kind: 'enemiesWithStatus'; status: StatusId | StatusId[] }   // AND 语义（与 C4 共用判定）
      | { kind: 'ownZones' }                                          // 本卡本绑定生成的区域
      | { kind: 'ownSummons'; summonKind?: string },
  maxTargets: number,           // 必填，防刷屏；超出取最近 N
  order?: 'nearest' | 'farthest',
  effects: EffectDef[],         // 每个成员各执行一次，origin = 该成员坐标
}
```

红线：内嵌 effects 过 V8（坐标类）；`maxTargets` 必填且 ≤8；扇出内不得再嵌 `forEach`（禁止递归）。

**服务**：permafrost 5★1、magmaPool 5★1、overgrowth 5★1、stormcall 5★2、cinderheart 5★1、hoarfrostTithe 5★2 + 产物 steamBurst / emberSpark / midasChain / thunderRime。

### T3 跟随位移 `follow`

`aura` 新增：`follow?: 'densestCluster' | 'nearestEnemy'`，`followLerp?: number`（每秒趋近比例，默认 0.5，避免瞬移）。缺省 = 炮台中心（现状）。

**服务**：stormcall 3★B + 产物 thunderRime。（仅 2 个使用方，恰好达标；若后续降为 1，按红线并入 T1 的原点选择而非保留独立字段。）

### T4 半径随时间变化 `radiusOverTime`

`aura` / `groundZone` 新增：`radiusOverTime?: { from: number; to: number; easing?: 'linear' }`，在 `duration` 内插值；与 `shape:'ring'` 组合即为扩张环（内圈 = 当前半径 − `ringWidth`）。

**服务**：permafrost 3★B、sanctum 3★B、overgrowth 3★B、frozenBulwark 5★2、galvanicWard 5★2、springOfLife 5★2、cinderheart 5★2 共 **7 张** + 产物 glacialEpoch。

### T5 动态量缩放 `scaleBy`

效果级参数：把运行时计数/比例映射到某个效果参数上。

```ts
scaleBy: {
  source: 'concurrentStatus:<id>'   // 场上带该状态的敌人数
        | 'statusStacks'            // 当前目标身上的层数（冻结层等）
        | 'shieldTier'              // 玩家壁垒剩余档位
        | 'thornsRatio'             // 当前 thorns 累计比例
        | 'auraReduction'           // 当前减伤比
        | 'enemiesOnField'
        | 'enemiesInAura'
        | 'controlledInAura'
        | 'secondsSinceLastBreach'
        | 'killsSinceLastRelease'
        | 'mergesThisRun'
        | 'pickupsThisWave'
        | 'summonsAlive',
  param: string,          // 被缩放的参数键（必须存在于同一效果的 params）
  perUnit: number,
  cap: number,            // 必填
}
```

融合：`scaleBy` 只改本效果参数，不产生跨卡仲裁。校验：source 枚举合法、`param` 存在、`cap` 必填。

**服务**：overcharge 3★A/3★B/5★1、ashHarvest 3★A/3★B/5★1、hoarfrostTithe 3★A/3★B/3★C、sanctum 5★1/5★2、retribution 3★C/5★1、thorns 5★1、ironvine 3★A/5★1、arcSplitter（并发口径）、galvanicWard 5★3、frozenBulwark 5★1 等 **≥7 张基础卡** + 产物 ampereFlow / emberMoat / frostDew / rimeShell / voltBastion / fortuneThorns / stasisLedger。

### T6 线状投放 `shape:'line'` 的绑定侧接入

`groundZone` 契约已有 `shape:'line'`，但无绑定侧的方向来源。新增：`lineFrom?: 'turretToPoint' | 'bulletPath'`，长度/宽度用现有参数。

**服务**：glacialSpike 5★2（沿弹道轴传染）+ 产物 stormLattice / solarPiercer 的 `trailZone`（`trailZone` 实现为 `shape:'line' + lineFrom:'bulletPath'` 的糖，不另起一套）。

> **与 `25配方卡_实装规格_v1.md` §1.1 的关系**：C6（`scaleBy` 枚举扩展）与 C7（`trailZone`）由 T5/T6 取代并统一；C1–C5、C8、C9 不变。该文 §1.0「复用清单」整节作废，以本文 §1 为准。

## 2. 防复发：设计指纹夹具与 V15/V16

### 2.1 设计指纹夹具 `src/config/base/designFingerprints.json`（新增）

把 v4 表的「载体 @ 触发」列编译成机器可读期望，每张基础卡每个分支一条：

```jsonc
{
  "version": "1",
  "cards": {
    "retribution": {
      "identityContract": "突破事件本身是弹药：每次突破在突破点触发审判打击",
      "branches": {
        "retributionA": { "star": 3, "triggers": ["onBreach"], "atoms": ["burstDamage"], "at": "point" },
        "retributionB": { "star": 3, "triggers": ["onBreach"], "atoms": ["aoeOnHit", "knockback"], "at": "point" },
        "retributionC": { "star": 3, "triggers": ["onBreach"], "atoms": ["burstDamage"], "at": "point",
                          "requires": ["scaleBy:secondsSinceLastBreach"] },
        "retribution1x": { "star": 5, "interfaceRole": "payoff", "triggers": ["onBreach"], "atoms": ["burstDamage"],
                           "at": "point", "requires": ["scaleBy:shieldTier"] }
      }
    }
  }
}
```

字段语义：`triggers` = 该分支必须使用的触发器集合（实装可多不可少、不得替换）；`atoms` = 必须出现的核心原子（可多）；`at` = 必须的投放原点；`requires` = 必须使用的原语标记（`forEach:*` / `scaleBy:*` / `radiusOverTime` / `follow` / `shape:line`）。

夹具由**人工**照 v4 表逐条填写（35 卡 × 6 分支 ≈ 210 条），不得从现有 `skills.json` 反向生成——否则会把已摊平的实装固化为"期望"。

### 2.2 新增校验

- **V15 跨卡分支指纹唯一**：任意两张不同卡的任意两个分支，其绑定集合（trigger + triggerParams + 全部 atom + 全部 params，深比较）**不得完全相同**。硬失败。允许的例外：无（若两张卡真该有同一效果，用不同参数体现强度差异）。
- **V16 实装符合设计指纹**：对每张基础卡每个分支，断言 `triggers ⊇ 期望`、`atoms ⊇ 期望`、`at` 一致、`requires` 全部出现。硬失败。缺夹具条目也算失败（防止新卡绕过）。
- **V17 identityContract 触发器一致性**（弱形式，警告级）：若 `identityContract` 文本含"突破/击杀/拾取/合成"等事件词，该卡至少一支分支使用对应触发器。

### 3.1 D2 专项：触发器复位清单

除 G07/G20 外，按 v4 表逐卡复核 `onBreach`/`onKill`/`onPickup`/`onMerge` 期望数（设计 onBreach 24 处 vs 实装 12 处）。已知重点：

- `retribution`：3★ A/B/C 三支 + 5★ 三支全部必须是 `onBreach at:'point'`（当前 3★ 三支为 `onHit`，身份契约被抹除）
- `sanctum` 5★1：`onBreach at:'point'`（当前缺失）
- `galvanicWard` 5★2/5★3、`frozenBulwark` 3★C/5★1/5★2/5★3、`cinderheart` 3★C/5★2、`thorns` 3★C/5★1/5★3、`ironvine` 5★1、`sentinel` 3★C：逐条比对夹具
- **另核**：实装普遍给 `onKill`/`onHit` 分支追加了一条配对 `→statBuff` 绑定（dup 组里成对出现）。若该 statBuff 不是 v4 设计的一部分，一并清除——它是造成跨卡指纹雷同的放大器。

### 3.2 回填后的验收口径

1. V15 全绿（0 组跨卡完全同构）；V16 全绿（210 条夹具全部符合）
2. `scripts/audit_content.py` 复跑：跨卡同构组数 = 0，报告写入提交说明
3. 黄金回放：**允许战斗数值漂移**（本次是内容修复，效果本就该变），但必须逐项列出漂移来源并确认全部对应本工单条目；结构性事件流（波次/掉落节拍/决策队列）不得漂移
4. 前 90 秒检查表（v4 §7.2）复跑：`magmaPool` 3★C 与 `sentinel` 3★C 的波 1 空转风险按 v4 遗留项处理（可加低频 interval 保底）
